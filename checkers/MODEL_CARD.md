# Model Card: Checkers evaluation net (`evalnet.bin.gz`) and endgame database (`egdb4.bin.gz`)

チェッカー（英国式 English draughts）のAIは、探索エンジン `engine.c`（WebAssembly、ブラウザの Web Worker で実行）に、
NNUE 形式のニューラルネットの形勢評価と4駒以下の終盤データベースを組み合わせています。

- **ゲーム**: https://core-calmdust.github.io/aicoding/checkers/
- **バージョン**: v2 — NNUE net-43（2026-11-08）。それまでは v1（2026-10-21、下の「旧ネット v1」）

## 形勢評価ネット（`evalnet.bin.gz`）— NNUE v2（net-43）
2026-11-08 からサイトはこのネットです（ファイル先頭 `CKN2`、548KB、gzip後 約368KB）。エンジンは旧形式 `CKN1` も読めます。

| 項目 | 内容 |
|---|---|
| 入力 | （駒数バケツ4）×（自分の兵・キング、相手の兵・キング）×32マス。黒・白それぞれの目で2組 |
| 構造 | 2×256 → 32 → 32 → 1。L1 以降は駒数で選ぶ8組の重み。1層目は int16 で差分更新、L1 は int16、以降 float |
| 速さ | wasm は SIMD（i16x8 の加減算、L1 は i32x4.dot_i16x8）、ネイティブは自動ベクトル化。整数演算なので SIMD の有無で評価値は1ビットも変わらない。v1 比の局面数/秒：wasm SIMD 約0.56倍（Node 実測 0.53 対 0.95 Mnps）、ネイティブ 約0.8倍。SIMD なしの wasm は 0.12 Mnps（v1 の約0.24倍）だが、局面数で区切るレベルの強さは変わらない |
| 学習 | Mac で強化学習の周回（`tools/nn/loop.sh`）を43周。自己対局は1手5万局面、序盤は3手バロット＋0〜4手ランダム。6駒の終盤DBで勝敗を判定し、6駒以下は終盤DBで答えを付けた局面も毎回の学習に混ぜる（下の「終盤の穴」） |
| 教師 | 探索値と勝敗の混合（`loop.sh` の既定 LAM=0.75：0.75 × 探索値 + 0.25 × 勝敗） |
| 確認 | 学習側の量子化計算（`train.py --check`）・ネイティブ（`native evalpos`）・wasm（`engine.wasm` と `engine_simd.wasm` の `eval_root`）の評価値が 1,428 局面で完全一致。差分更新と全計算も一致（`native acctest2`、21,382 局面で不一致0） |

### 終盤の穴（2026-11-07、net-43 では解消）
自己対局は終盤DBで勝敗が決まった時点で終わるため、自己対局だけのネットは6駒以下を学習していなかった（6駒以下の局面で勝敗の見立てが一致するのは50%＝当てずっぽう、v1 は100%）。
サイトは4駒DBまでなので、30周目（H=512）のネットはサイト条件で v1 に −397 Elo だった。そのあと `loop.sh` は6駒DBで答えを付けた終盤の局面を毎回の学習に混ぜるようにし（`tools/nn/egtune.sh` も参照）、net-43 はサイト条件（4駒DB）でも上の通り v1 より強い。

### 強さの測り方（3手バロット）
強い同士はほとんど引き分けになるため、ランダムな序盤ではなく、互角な3手の序盤266通り（`tools/ballots.txt`）を先後入れ替えで全部指す（532局）。
`tools/nn/match.sh`、同じ持ち時間での比較を最終判断にする（大きいネットは1局面あたりが重い）。

### パズル・レッスンへの影響（2026-11-08 に確認）
- パズル500問：正解の手は変わらない（`puzzle()` は厳密な探索、`tools/audit_puzzles.js` で正しさの不合格0）。評価で決まる目安（0.3秒の解析）は、
  「解いた後の得が小さい（hollow）」が v1 の44問 → 62問、「取り返される（giveback）」が 0 → 4問（step2-11、step3-46、shots-1、crown-13）。問題そのものは差し替えていない。
- レッスンのウォームアップ（`tools/check_lessons.js`）：全問 OK。

## 終盤データベース（`egdb4.bin.gz`）
- 盤上4駒以下（兵・キングのあらゆる組み合わせ、41クラス）の勝ち・負け・引き分けを後退解析で求めたもの（`tools/egdb.c`）。gzip後 約517KB。
- 探索中、取りのない局面で駒が4つ以下になったら引いて読みを打ち切る。白黒を入れ替えた局面で結果が一致することを全件で確認済み。

### レベルの測り直し（2026-11-08、net-43 に替えたとき）
局面数で区切る 4級〜三段は、ネットを替えると強さが変わる。各レベルで「net-43 で N 局面」が「v1 で元の局面数」と同じ強さになる N を、
サイト条件（4駒DB、置換表 2^20）の3手バロット対局（先後入れ替え）で求めた。新しいネットは1局面あたりの読みが正確なので、少ない局面数で同じ強さになる。

| レベル | v1 | net-43 で試した局面数 → 対 v1 の差（Elo） | 採用 |
|---|---|---|---|
| 4級 | 2千 | 800 → −25 ± 24、1,200 → +51 ± 24、2千 → +112 ± 25（各532局） | **900**（−25 と +51 の間を局面数の対数で補間） |
| 3級 | 5千 | 1,500 → −19 ± 23、1,800 → +12 ± 23、3千 → +59 ± 23、5千 → +114 ± 25（各532局） | **1,700**（補間） |
| 2級 | 1万2千 | 2,500 → −59 ± 21、5千 → +63 ± 22、1万2千 → +130 ± 24（各532局） | **3,500**（補間） |
| 1級 | 3万 | 8千 → +20 ± 22、1万2千 → +19 ± 20（各532局） | **8,000**（測った点。どちらも誤差内でほぼ同じ） |
| 初段 | 8万 | 2万 → −2 ± 34、3万2千 → +54 ± 34（各200局） | **2万** |
| 二段 | 20万 | 5万 → +32 ± 44（120局） | **5万** |
| 三段 | 50万 | 12万 → +44 ± 67（48局。重いので局数が少なく、誤差が大きい） | **12万** |

v1 の局面数に対する比は 0.45（4級）→ 0.34 → 0.29 → 0.27 → 0.25（初段〜三段）と、上のレベルほど小さい（読みが深いほど評価の良さが効く）。
二段・三段は1点ずつで誤差が大きい（三段は ±50 に届いていない）が、比 0.25 の流れと合っている（測った値はわずかに強め、誤差の範囲）。
**レーティング戦の基準値（`RT_LV`）は 4級〜三段では変えていない**（強さを v1 のときに合わせたため）。

1手の時間の目安（ブラウザ相当：Node の wasm SIMD で測った速さ v1 0.95 Mnps、net-43 0.53 Mnps から、各レベルの局面数 ÷ 速さ）：

|---|---|---|---|---|---|---|---|

### 四段・五段（時間で区切るレベル）
時間で区切るので、ネットが強くなった分だけ強くなる。ブラウザの速さの比での対局（上の「評価」）で v1 に +92〜+99 Elo（1手 約30〜50ms 相当の局面数）。
1秒 / 2.5秒では引き分けがさらに増えるため差は小さくなるはずで、実際の差はおそらく +50〜+90 Elo 程度（この持ち時間の対局は重すぎて測っていない）。
もともと1級より上は隣のレベルとの差が誤差の範囲（下の表）で、基準値は 50 刻みの目安のため、`RT_LV`（四段 2300、五段 2350）は変えていない。三段（2250）との順序は保たれる。

## 本編のマルチスレッド（2026-11-08）
addendum「本編のマルチスレッド」の方式。`engine.c` を `-DMT` でビルドした `engine_mt.wasm`（Lazy SMP：置換表・学習評価・終盤DBを共有メモリで共有し、補助スレッドは同じ局面を読み続ける。置換表・深さのずらしは下の「見直し」で変更）。スレッドごとの状態は `TLS` マクロ（通常版では空。`engine.wasm`・`engine_simd.wasm` は1バイトも変わらないことを cmp で確認）。NNUE の累積（1手ごとの差分）は各スレッドの枠（4MB：TLS・累積・スタック）に置く。
- スレッドを使うもの：分析・ヒント・コーチ（二段目の四段の読み）・検討ボックス（振り返りの候補手）、時間で考える四段・五段（レート戦も）、PRO の「スレッド数」（どの思考の制限でも）。主スレッドはレベルの時間のまま読み、補助が置換表を埋めるので同じ時間でより深く読む。
- 1スレッドのまま：15級〜三段（深さ・局面数で決めるレベル。もともと一瞬で終わる）。
- 計測（作業環境：共用2コア、負荷が高く時間の比は当てにならない）：同じ深さまで主スレッドが読む局面数 1スレッド 336万 → 2スレッド 189万（12局面、**局面数換算 1.78倍**）、最善手の一致 11/12。正式な効果はユーザーの Mac で `checkers/bench.html`（1・2・4・8…論理コア数、同じ時間の局面数／秒・深さ・最善手の一致、同じ深さまでの時間）を測る。

### マルチスレッドの見直し（2026-11-09、Mac の実測から）
- **Mac の実測（M4 Pro 14コア＝高性能10＋高効率4、Chrome、`bench.html` 3秒）**：局面数／秒は 2・4・8・14スレッドで ×2.05／×4.09／×7.42／×10.01 なのに、同じ深さまでの時間は ×1.40／×1.66／×1.62／×2.34、平均の深さは 16.25 → 17.50、最善手の一致 9〜11/12。
- **点検して問題なかったもの**：置換表・学習評価・終盤DBはスレッド間で共有（TLS ではない）、局面・ヒストリー・キラー手・NNUE の累積・繰り返しの履歴はスレッドごと（競合なし）、表の年齢は主スレッドだけが進める、停止（`gStop`・`ctl[0]`）、補助は主スレッドが終われば止まる、共有の変数への頻繁な書き込み（偽共有）なし。ベンチの測り方（毎回 `newgame` で表を消す、最初にウォームアップ、補助は先に起動済み）も妥当。作業機のシミュレーション（主スレッドが深さ14・16 までに読む局面数を時間とみなす）では、旧版でも 2スレッド ×1.65〜1.80、4スレッド ×3.0〜3.3 で、**Lazy SMP としては働いている**（Mac との差は作業機では再現できず。深さ16 にしても、表を Mac 並みに埋めても同じ）。
- **弱かったところと変更（`engine_mt.wasm` だけ。通常版 `engine.wasm`・`engine_simd.wasm` はバイト一致＝1スレッドの指し手は不変）**：
  - 置換表は1つのキーに1項目（24バイト）で、欄を順に書くため、2つのスレッドが同時に書くと別の局面の値と組み合わさりうる（手は合法手と照合するので害はないが、値・深さは使われる）。→ 2項目のバケット × 2^20 = 48MB（項目数2倍）、1項目は `{ key ^ a ^ b, a, b }` で読むときに XOR で照合（壊れた項目は使わない）。置き換えは同じキー→それ以外は浅い／古い項目。表を Mac 並みに埋めた条件で、旧の1スレッド比 2スレッド ×1.80 → ×2.17、4スレッド ×3.04 → ×3.23。
  - 主スレッドの結果しか使っていなかった → 各スレッドが終えた反復（深さ・値・手）を共有し、最も深い結果で答える（同じ深さなら主スレッド）。深さの上限があるとき、補助が先に届いたら主スレッドも終える。
  - 補助の深さのずらし（奇数番は1手深く始める）はやめ、全スレッド 1, 2, 3… と読む。Stockfish 式に補助ごとに深さを飛ばす方式も試したが、主スレッドの局面数換算で遅かった（4スレッド ×2.14〜2.37、ずらしなし ×2.84〜2.95）。
  - プールの `initial` を 1024 ページに（wasm の宣言が 822 ページになったため）。`engine_mt.wasm?v=2`。
- **作業機での確認（実際の大きさの表、12局面、深さ14）**：旧 2スレッド ×1.65・4スレッド ×2.97 → 新 ×1.60・×3.09（誤差の範囲で同じ）。headless Chromium で `bench.html`・対局ページが分離・スレッド起動まで動くこと（2スレッド）を確認。
- **見込み（Mac）**：2〜4スレッドは大きくは変わらず、表が埋まる 8・14スレッドで少し良くなる見込み（同じ時間の深さ・最善手の一致は、深い補助の結果を使う分だけ上がる）。要再計測：`checkers/bench.html`。
- 最上位のレベルは足さない：チェッカーは完全解析で引き分け（Chinook 2007）で、上の表のとおり1級より上は隣のレベルとの差が誤差の範囲（ほとんど引き分け）。時間を2倍ずつ伸ばしても差を感じられないため。

### マルチスレッドの見直し その2（2026-11-10、モリスの busy marks を移植）
- **原因**：モリス（`morris/MODEL_CARD.md`「その2」）と同じ。全スレッドが同じ木を同じ順に同じ速さで読み、同じ部分木を**同時に**読むので、互いの結果を置換表から受け取れない（Mac：nps ×4.1／×7.4／×10.0 なのに同じ深さまで ×1.66／×1.62／×2.34）。前の見直しの作業機の見積もり（4スレッド ×3.0）は、スレッドが交代で動く楽観的な形だった。

## 探索 v2（2026-11-14、学習なしの強化）
チャンギ・シャンチー・コナネ・ウゴルキの「探索 v2」と同じ考えの枝刈りを `engine.c` に入れた。NNUE・終盤DB・評価は変えていない。
（モリス・ファノロナでは強くならず不採用。チェッカーは取りが義務なので、**取りのある局面・成る手は枝刈りしない**。）

- **入れたもの**（PV 以外の節、取りのない局面だけ。`-DSV_x=0` で個別に外せる）：
  - ヌルムーブ（深さ3以上、R = 2 + 深さ/4。手番側の駒が6枚以上・相手が2枚以上のときだけ＝終盤のツークツワンクを避ける。直後の局面は繰り返しの判定を切る）
  - 逆フューティリティ（深さ4以下、80×深さ）・フューティリティ（深さ2以下、120×深さ、3手目以降）
  - LMP（深さ3以下、`4+2深さ²` 手目より後の静かな手を読まない）
  - LMR の対数表（3手目から、`0.6 + ln(深さ)·ln(順番)/1.8`、PV は1浅く）、置換表の手がない節は1手浅く（IIR）

## 限界
- 学習データは自分自身の対局だけで、人間の名局やプロ用データベース（Chinook の8駒DBなど）は使っていない。
- 4駒を超える終盤は探索で読む。長い終盤（キング同士の追い込みなど）は最善でないことがある。
- 上位レベルの強さの差は小さく、実力は対局環境（端末の速さ）にも少し左右される（4級〜三段は局面数で区切るので端末によらない）。
