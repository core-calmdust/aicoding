# Model Card: Reversi V4 Pattern Evaluation (`weights.bin.gz`)

Reversi V4 の AI が局面の良し悪しを判断するための評価関数（学習済み重み）です。
探索エンジン `engine.js` と組み合わせて、ブラウザ上で動作します。

- **ゲーム**: https://core-calmdust.github.io/aicoding/reversi/
- **作成**: core-calmdust（AIコーディングによる制作）
- **バージョン**: v3（2026-10-18）

## モデル概要

| 項目 | 内容 |
|---|---|
| 種類 | パターンベースの線形評価関数（Logistello / Edax 系の古典的手法）＋着手可能数特徴 |
| 入力 | 手番側から見た盤面（自石 / 相手石 / 空き の3値 × 64マス） |
| 出力 | 手番側から見た予想最終石差（1/32 石単位の整数） |
| パターン | 15種類・対称形を含め計62インスタンス（下表。v3で10マスのパターンを4種追加） |
| 追加特徴 | 手番側の着手可能数、相手の着手可能数、両者の潜在的着手可能数（空きマスに接する相手石・自石の数）。各0〜63をテーブル引きで評価 |
| フェーズ | 手数に応じて30段階（2手ごと）に重みを切り替え |
| パラメータ数 | 30 フェーズ × 403,718 = 12,111,540（Int16） |
| ファイルサイズ | 約24.2MB（gzip圧縮後 約7.8MB） |

## 学習方法

- フェーズごとに、前後1手を含む局面（各フェーズ最大約400万局面）で最小二乗回帰。
- 特徴ごとの出現回数で正規化した勾配法を300反復。学習率は誤差が増えたら減衰。
- 2% の局面をテスト用に除外。
- 序盤の最初の3フェーズ（0〜5手）はデータが極端に少ないため、6〜7手目のフェーズの重みを流用。

## 探索の高速化（2026-11）
中盤の探索（PVS・パターン評価の差分計算・Multi-ProbCut・置換表）と終盤の完全読みを C に移し、WebAssembly で動かすようにしました（`engine.c`、`tools/build-wasm.sh` で `engine-wasm.js` / `engine.wasm` を生成）。
盤面は64ビットのビットボード、着手可能手と裏返る石はシフト演算でまとめて求めます。手の順番・置換表・時間切れの判定まで engine.js と同じ処理なので、読む局面と結果は従来と完全に一致します（ランダムな14局面 × 3設定、深さ指定・完全読みを含めて一致を確認）。
速さはブラウザで約2.5倍（初期局面・深さ11：121ms → 48ms）、Node で約2.6倍。時間で区切るレベル（Lv.15〜20）と検討は、同じ時間でより深く読みます。WebAssembly が使えない環境では従来の JavaScript の探索で動きます。
終盤はさらに、確定石による上限の枝刈り・残り1マスの専用計算・相手の石に接しないマスの除外を入れ、完全読みが約25%速くなりました（結果は同じ）。
Lv.17〜20 は完全読みの手前（Lv.20 は残り22マス、Lv.17〜19 は20〜21マス）で勝ち・引き分け・負けだけを判定する読みを行い、勝てる手があればそれを打ちます（同じ持ち時間の範囲内）。

2026-11 にさらに高速化しました（読む局面と結果は変わらず、局面数まで一致）：着手可能手の計算を Kogge-Stone 法にし、WebAssembly の SIMD で盤とその上下反転を1命令で並べて6方向を同時に計算。裏返る石は方向ごとのマスクと繰り上がり・先頭ゼロの計算でループなしに求め、最後の1マスは行・列・斜めの4本を8ビットに集めた表引きで数えるだけにしました。パターンの添字は16ビットで持ち、子局面へのコピーをベクトル単位に。象限ごとの空きマスの偶奇は折りたたみで一度に計算します。Node の CPU 時間で中盤（深さ15）約1.4倍、終盤の完全読み（残り19マス）約1.2倍速くなりました。SIMD に対応していないブラウザ（Safari 16.3 以前など）では従来の JavaScript の探索で動きます。

Egaroucid for Web（最強のレベル15、定跡あり）との自動対局（Node、1スレッド。序盤6手ランダム・先後入れ替え48局）：Lv.20 は 29勝2分17敗 → 改良後 27勝4分17敗（どちらも勝率60%）。序盤2手ランダム（定跡がほぼ効く条件）では 24勝6分18敗（56%）。

## 探索の改良 v2（2026-11-08）
同じ時間でより深く・終盤の完全読みをより速く。完全読みの結果（石差）はこれまでと同じです。
- **中盤（Multi-ProbCut を使うレベル＝Lv.15〜20・分析・検討）**：置換表の最善手を、ほかの手の並べ替えより先に読む（それで枝刈りできれば並べ替えの浅い探索を省く）。並べ替えの浅い探索を浅めに（深さ 8 以上で1手、12 以上で2手、18 以上で3手読み。以前は 4・6・9）。同じ深さまでの時間が約 2.2〜3 倍速く、読んだ結果（最善手と評価値）は同じでした（下表）。Multi-ProbCut を使わない Lv.1〜14 は以前とまったく同じ探索（局面数まで一致）。
- **石を返す計算**：マスごとの専用コード（`tools/gen-flips.py` で生成。方向ごとのマスクを定数にし、2マス未満の方向は省く）。
- **終盤の最後の7マス**：手の生成をせず、空きマスのリスト（ビット）から直接打つ。奇数の象限を先に、角→辺→内側→X・C打ちの順。残り3・2・1マスは専用の関数（最後の1マスは表引き）。
- **終盤の置換表**：残り8マス以上で使う（以前は10）。1か所に2つの枠を持ち、空きの少ない方を置き換える（今の局面より空きの多い古い枠は空きとみなす）。
- **確定石による枝刈り**：上限で切れる見込みのあるとき（alpha が空き数ごとの閾値以上、Edax と同じ表）だけ確定石を数える。
- 手の並べ替えに使う評価値を、親の局面からの差分で計算（以前は子ごとに全部数え直し）。並べ替えで求めた返る石を本読みで使い回す。
- ルートの読み（engine.js）：勝敗読みなどで上限を超えた手が見つかったら残りの手を読まない。
- WebAssembly が使えない環境の JavaScript の探索にも中盤の変更を同じように入れました（WebAssembly 版と局面数・結果まで一致を確認）。終盤は WebAssembly 版だけ。

## 定石 v2（`book.bin`、2026-11-08）
旧定石（`book.json`、1,927 局面・18,643 手、13手目まで、作り方の記録なし）を、生成ツール `tools/book-gen.js` で作り直しました（手順・Mac での大きな生成：`tools/BOOK.md`）。
- 作り方：初期局面から1手ずつ（幅優先で）広げ、各局面の全部の手をゲームと同じエンジン（`engine.wasm`、Multi-ProbCut あり）の固定深さで読む（最善手は全幅、ほかは「最善 − keep 石」までの窓、上回ったら読み直し）。最善から window 石以内の手の先を加え、片方の手番の損の合計が err 石を超える変化と、1手あたり cap 局面を超える分（損の多い順）は打ち切り。最後に木をたどって評価値を negamax で戻し（定石の局面へ進む手は、その局面の値の符号反転）、最善から3石以内の手を入れる。
- 1局面ごとに置換表を空にして時間制限なしで読むので、同じ設定なら結果は完全に同じ（`verify` で読み直して一致を確認）。読み終わった局面は1行ずつ保存し、止めても続きから再開できます。
- 今回の版（作業環境：2コアを他の作業と共用、約1時間）：深さ16・22手目まで・cap 200・err 3石・window 2.5石・keep 3石、旧定石の10手目までの局面は必ず含める。**3,041 局面・6,939 手（22手目まで）**、ファイル 23KB（gzip 17KB）。旧 book.json は 258KB（gzip 66KB）。
- 形式：`book.bin` は木を深さ優先で並べたもの（1局面 = 手の数＋各手 3バイト：手・子局面が続くかの印・評価値 1/10石）。局面の鍵（8通りの対称形のうち最小）は旧形式と同じで、読み込み時に初期局面から手順をたどって復元（engine.js `decodeBook`、3,000局面で数ms）。`setBook` は旧 JSON もそのまま受け付けます。
- 使い方は以前と同じ：定石を使うレベル（Lv.15 以上・PRO の定石オン）は最善から 0.8 石以内の手から選ぶ。**分析**も、定石の局面では定石の評価値（深い読みを木で戻した値）を表示し、定石にない手は「最善 − 3石」以下として表示（定石の窓より悪いことが分かっているため）。

## 最強解析（複数スレッド、2026-11）
- `pro/`：PC の複数の CPU コアで同時に読む解析ページ。対局ページの棋譜欄の「最強解析」ボタンから、表示中の局面を新しいタブで開きます（標準の初期配置からの対局は手順ごと、それ以外は局面だけ）。
- エンジンは同じ `engine.c` を `-DMT` で作った `engine_mt.wasm`（`tools/build-wasm.sh` の最後の行）。共有メモリの上で、置換表・重み・表を共有し、探索の作業領域はスレッドごと（`TLS`）。探索の外側（反復深化・ルートの手の並べ替え）は各スレッドの `engine.js` が受け持ちます。通常版の `engine.wasm` は変わりません。

## マルチスレッド v4（Lazy SMP をやめて YBW の分割探索に、2026-11-10）

- 中盤：Lazy SMP は「全スレッドが同じ根を読み、置換表だけで助け合う」ので、局面数はスレッド数どおり増えても、主スレッドの木を減らす分は小さい。「本当に同時」のシミュレーション（`tools/mtsim-delay.py`、書き込みは1024局面ごとにしか見えない）で v3 は ×1.22／×1.51／×1.81（時計＝全スレッドの歩み）、Mac の ×1.21／×1.36／×1.37 と 2・4 スレッドで合う（8 は Mac の方が低い：メモリの取り合いなど）。置換表の容量・置き換え、補助のずらし方、busy marks（その2）は試し済みで、残りは方式そのものの限界と判断。
- 終盤：ルート分割は根の手（10個前後）しか分けないので、最初の手（たいてい木の半分以上）を読む間は補助が応手の読み・null window の試し読みで表を埋めるだけ。スレッドが多いほどその「待ちの間の読み」が増え、局面数が膨らむ（同じシミュレーションで 8スレッド 局面数 ×1.66）。

**変更（`engine_mt.wasm`・`engine.js`。通常版 `engine.wasm` は変えていない＝`-DMT` なしの前処理後のソースが一致）**
- `engine.c`（MT のときだけ）に Young Brothers Wait の分割点：中盤の探索（残り深さ5以上）と完全読み（残り14マス以上）の節で、最初の手（置換表の手を先に読んだときはそれ）を読み終えたあと、手の空いた補助がいれば残りの手を分割点（`SPt`、共有メモリに256個）に出し、主と補助が原子的なカウンタで1手ずつ取って、1スレッドと同じ PVS（null window → 上回れば読み直し）で読む。カットが起きたら分割点に停止の印、その下のスレッドは時計の確認（`CHK_Q`＝4096局面ごと、完全読みも同じ間隔にした）で気づいて抜ける。持ち主は補助が全員抜けるまで、自分の分割点の下の分割点を手伝って待つ（helpful master）。
- 根も分割点（`root_mt`、`engine.js` の `rootPVS` と同じ窓。PART 用に途中の最善手を `root_info`）。中盤の反復深化の各深さ・完全読み・勝敗読みとも同じ（終盤のルート分割 `rootSplit` は使わない）。

## やさしいレベル Lv.1〜13（2026-11-10）
ユーザーの声「ポータルで低レベルを遊んだが、どう考えても強すぎる」を受けて、Lv.1〜13 を作り直しました（Lv.14 以上は変えていません）。

**強すぎた原因**（コードの経路のバグではなく、設定そのもの）
- 低いレベルは「全部の手を浅く読んで評価値に一様な乱数（noise）を足し、最大の手」でした。評価関数（パターン学習の v4）は1手読みでも角・X打ちの損得を正しく知っていて、角をわたす手は評価で −10〜−30 石。旧 Lv.1 の noise ±40 石でも角をわたす手や取れる角を見逃す手はめったに選ばれず、旧 Lv.4（±9 石）ではほぼ選ばれません。
- 終盤の完全読み（exact）も Lv.1 から2〜4マスあり、最後の数手は正確でした。
- 実測：旧 Lv.1（「ほぼでたらめ」）でも、でたらめに打つ相手に 90%（+377 Elo）、一番多く返す手だけを打つ相手（初心者・子どもの打ち方に近い）に 79%。
- ポータル（大百科のちゃぶ台 `atlas/games/reversi.js`）も対局ページ（`index.html`）も、Lv.1〜16 は `engine.js` の LEVELS をそのまま1スレッドのワーカーで打っています（定石は `mpc` のあるレベルだけ、マルチスレッドは Lv.17〜25 だけ、PRO の既定値は同じ値）。noise が効かない経路はありませんでした。ただし PRO の「手のばらつき」を既定のままにしたときに新しい項目（下の rnd・greedy）が引き継がれないので、`proCfg` で写すようにしました。

## ファイル形式と読み込み方

- `weights.bin.gz`: gzip 圧縮された Int16（リトルエンディアン）の配列。
  フェーズ順に `PHASE_SIZE`（v3 = 403,718）個ずつ並ぶ。各フェーズ内は「パターンの重みテーブル（403,461）→ 追加特徴4種×64 → バイアス1」の順。エンジンは1フェーズあたりのサイズから v1/v2/v3 を自動判別します。
- `weights.json`: `{"nphase": 30}` などのメタ情報。
- 各パターンの重みテーブル内の位置は、マスの状態（空き=0 / 手番側=1 / 相手=2）を3進数として読んだ値です。

```js
const buf = await (await fetch('weights.bin.gz')).arrayBuffer();
const raw = await new Response(new Blob([buf]).stream().pipeThrough(new DecompressionStream('gzip'))).arrayBuffer();
ReversiEngine.setWeights(new Int16Array(raw), 30); // 1フェーズあたりのサイズから v1/v2 を自動判別
```

詳しくは同じフォルダの `LICENSE` を参照してください。

- この計測は PR #1313（主が補助の結果をすぐ採る）より前の版の可能性がある。#1313 は全レベルに同じように効くので、レベル間の差の見積もりは変わらない見込み。
