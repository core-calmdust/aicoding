# Model Card: Amazons AI（`core.c` → `core-wasm.js`・`core_mt.wasm`、学習した評価 `net.js`）

アマゾンズ（10×10）の AI の仕組み・計測・学習の手順。細かな経緯は `claude/amazons-spec.md`（エンジン・評価 v2／v3・レベルの測り直し・MCTS・αβ を C に）。

## 構成（2026-11-20 時点）

| 部分 | 中身 |
|---|---|
| 評価 | Lieberum の項（クイーン距離・キング距離の陣地 t1／t2、位置項 c1／c2、盤の開き具合 w）＋各アマゾンの自由度。重みは3組：従来（Lv.1〜12・分析・ヒント・パズル）、v2（Lv.13〜15 の αβ）、v3（MCTS：Lv.16〜23・レート戦・PRO の MCTS・コーチの深読み・大百科の3D卓）。距離は 128ビットのビットボード（wasm SIMD）で層ごとに求める |
| 候補手 | 全クイーン移動を評価 → 上位だけ全部の矢を評価（2段階） |
| αβ | PVS・置換表・候補手リストのキャッシュ、残り深さごとに上位 K 手（Lv.9〜15・解析）。スレッドは Praline の YBW |
| MCTS | 葉を1つ展開＝候補リスト（評価数百回）、評価の事前値、プログレッシブ・ワイドニング、implicit minimax、証明（勝ち・負け）、手番の偏りの補正、最後の手は「よく読まれた手のうち値が最良」。スレッドは1本の木を全スレッドで（tree-parallel） |
| **終盤の数え上げ（新）** | 盤が分かれた後（両方が届く空きマスがない）は各領域で動ける回数を正確に数える（`core.c` の `sep*`）。MCTS の木の中では分かれた局面を証明済みの勝ち／負けにし、根では自分の領域を最長に埋める手を指す |
| **学習した評価（新、器のみ）** | `core.c` の評価 `EVM 3`。`amazons/net.js` が空の間は v3 のまま（今は空） |

## 公開されている手法との比較

強い Amazons のプログラムの手法（調べた範囲：Lorentz「Amazons Discover Monte-Carlo」2008（Invader-MC）、Kloetzer・Iida・Bouzy「The Monte-Carlo Approach in Amazons」2007 と「Playing Amazons Endgames」ICGA Journal 2009、Lieberum「An evaluation function for the game of Amazons」2005（Amazong）、Müller らの Amazons 終盤の組合せゲーム理論・Buro の「欠けのある陣地」と NP 困難性、Lanctot ほか 2014 の implicit minimax、近年の深層学習の Amazons（AlphaZero 型の自己対局と価値・方策ネット））と、今の実装：

| 手法 | 今の実装 |
|---|---|
| MCTS＋評価関数（プレイアウトの早い打ち切り、評価の事前値、プログレッシブ・ワイドニング） | あり（2026-11-10〜。プレイアウトは0手＝評価だけが最良だった） |
| implicit minimax（評価の最小最大値を木の値に混ぜる） | あり（A=0.3） |
| Lieberum のテリトリー評価（queen／king 距離、w での重み付け）・自由度 | あり（v2・v3 で重みを調整） |
| 候補の絞り込み（評価での2段階の選別） | あり（クイーン移動 QK=10 → 矢、子 K=24、根 48） |
| 盤が分かれた後の正確な数え上げ・欠けのある陣地 | **今回追加**（下の「終盤の数え上げ」） |
| 学習した評価・方策（自己対局） | **今回、学習の道具一式と読み込みの器を追加**（学習本番はユーザーの Mac） |
| 木の再利用（前の手の木の続き） | なし（見込み +5〜+20 Elo に対して仕組みの変更が大きい：spec「評価 v3」） |
| 組合せゲーム理論での分かれた領域の値（温度・hot な領域） | なし：分かれた盤は「各自が自分の領域で何手指せるか」で決まる（各領域が片方の色だけなら和はただの手数の比べ合い）。両方の色がいる領域が残る間は MCTS に任せる |

## 終盤の数え上げ（2026-11-20）

- **何をするか**：アマゾン同士がキングの一歩でつながる空きマスの塊（領域）を作り、どの領域にも片方の色のアマゾンしかいなければ「分かれた盤」。1手で必ず1マス埋まる（アマゾンが1マス空け、1マス占め、矢で1マス）ので、領域の空きマス E は手数の上限。実際に何手指せるか（欠けのある領域では E より少ない）を深さ優先の読みで求める：手の順は「矢を空きの隣が少ないマスへ」（行き止まりから埋める）、上限 E に届いたら打ち切り、局面（領域の空きマスとアマゾンの位置の64ビットの鍵）ごとの表、節の数の予算（超えたら各節で最初の手だけ＝貪欲の線で下限）。手番の側が勝つのは自分の手数が相手より多いとき。
- **MCTS の中**（`core.c` `P_SEP`、`engine.js` `MC.sep` = 500：1領域あたりの節の予算）：展開する局面が分かれていれば数えて、決まれば証明済みの勝ち／負け（評価しない）。
- **根**（`engine.js` `mctsThink`）：分かれた盤では MCTS を使わず、自分の領域を最長に埋める手（数え上げの最初の手、正確に解けた領域を先に）を指す。勝っていても負けていても、自分の手数を最大にするのが最善（相手と関わらない）。負けの局面で αβ の `resist` に回すより長く粘る。
- **副次的な修正**：評価数で決める探索（`mcts_run` の評価の上限）で、窓の子が全部証明済みになると評価のない訪問がいつまでも続くことがあった（数え上げの証明で起きた）。評価なしの訪問が2万回続いたら止める。
- **計測**（`tools/native_match.c`、MCTS v3 同士、1スレッド、先後入れ替え）：
  - 1手6万評価、盤が分かれて数え上げで勝敗が決まったら終局（`AMZ_ADJ=count`）：数え上げあり 50勝51敗（101局、49.5%）。中盤での証明は強さに効かない（v3 の「閉じた盤で陣地を重く」で分かれかけの判断はすでに正確）。CPU 時間は 1手 +2%。
  - 1手 CPU 0.05秒、判定なしで最後まで（`AMZ_ADJ=none`）：数え上げあり **107勝93敗（200局、53.5%、+24 Elo、2σ で −24〜+74）**。根で分かれた盤を一瞬で指すので1手の平均時間が短い（39ms 対 46ms）。
  - 結論：強さはほぼ同じ（誤差の範囲）で、分かれた盤の指し手が正確・速くなった（負けの局面でも最長に粘る）。レベル表（RT_LV）は変えない。

## 学習した評価（2026-11-20、器と道具。ネットは未採用）

- **形**（`core.c` の `nnOut`、`EVM 3`）：
  - 各マスの種類：空きマスは「手番側のクイーン距離 1／2／3／4／5以上／届かない」×「相手の同じ」×「キング距離でどちらが近いか（手番側・同じ・相手）」（両方とも届かないマスは数えない）、アマゾンは「手番側か相手か」×「動けるマス 0〜5」。種類ごと・マスの対称類（盤の8つの対称で同じマス＝15類）ごとに 32 個の重みの行があり、局面の全マスの行を足す（対称な形なので、ネットの値も盤の回転・裏返しで変わらない）。
  - 密な入力（手番側から）：t1、e·t1、e·t2、e·c1、e·c2、自由度、e、矢の数/92（e＝盤の開き具合）。1/16 にして同じ 32 個にも足す。
  - 隠れ層 32（0〜1 で切る ReLU）→ 出力（マス単位）。出力には密な入力も直接足す（最初は v3 の重み 2・−1・0.85・0.7・0.6・1 なので、学習前のネットは v3 と同じ）。値は手番側から、×100 で今の評価と同じ単位（σ(値/400) が勝つ見込み、MCTS の S と同じ）。
  - 重み 58,409 個、ファイルは float16（117KB、`net.js` は base64 で約156KB）。ネイティブと WebAssembly（SIMD・SIMD なし・core_mt.wasm）で同じ値（float の足す順も同じ、`tools/nnue/check_net.js`）。
  - 速さ：v3 の約 0.65 倍（作業機ネイティブ、`nn speed`。距離の層は v3 と共用、増えるのはマスの種類分け（ビットボードの組み合わせ）と32個の和）。だから「同じ時間」で勝つには評価数あたり約 +70 Elo 以上の伸びが要る。
- **手の予測**：MCTS の子の事前値は「その手を指した後の局面の評価」（1手先の評価＝方策の代わり）なので、評価がネットになれば候補の並び（候補手・事前値・プログレッシブ・ワイドニングの順）もネットで決まる。別の方策ネットは置いていない（全クイーン移動を評価する今の2段階の選別が、そのまま方策になっているため）。
- **学習データ**（`tools/nnue/nn.c selfplay`）：先生は自分のエンジン（MCTS v3、1手2万評価、数え上げあり。2周目からは採用されたネット）。序盤2〜8手は上位10候補からランダム、その後12手までは4回に1回「最多の半分以上読まれた手」から選ぶ。盤が分かれて数え上げで勝敗が決まったら終局（その局面は記録しない）。記録は局面・探索の値（根の手の値）・勝敗（32バイト）。
- **学習**（`nn train`）：目標 = λ·σ(探索の値/400) + (1−λ)·勝敗（λ=0.5）、ロジスティック損失、Adam（lr 1e-3、60%・85% で 0.3・0.1 倍）、バッチ 4096、全コア。最後の2%（最大40万局面）は学習に使わない確認用で、確認の損失が最良のエポックを保存。学習前に v3 の確認の損失も表示する。
- **確認と採用の基準**（`run.sh`、`tools/native_match.c`、MCTS 同士・数え上げあり・先後入れ替え・序盤2手ランダム・盤が分かれて陣地差3以上は判定）：①1手3万評価で 400局、②1手 CPU 0.1秒で 400局。**②で 52% 以上かつ①で 50% 以上**なら `adopt/net.js` を書き出す（採用候補）。サイトに入れるのは Claude が受け取って、ブラウザの速さ（wasm）でも測り直し、レベル表を調整してから。
- **サンドボックスでの確認**（仮ネット、採用しない）：自己対局 約1.8万局面（1手5千評価）で 4エポック → 確認の損失 v3 0.164 → 0.154。読み込み・値の一致（ネイティブ／wasm SIMD／SIMD なし／core_mt.wasm の60局面×3値が全部一致）、Node の worker_threads で core_mt.wasm の2スレッドの MCTS がネットで動くこと（`tools/mt_node.js check 2`）、ブラウザ（headless Chrome、分離あり、COOP モード）で Lv.22 表示（エンジン Lv.19、MCTS のスレッド）の AI 同士が指し、コンソールエラーなし。仮ネットは `net.js` から外した（今の `net.js` は空）。
- **ネットが入ったら変わるもの**：`engine.js` は `net.js` が空でなければ `MC.ev = 3`（MCTS の全部：Lv.16〜23・レート戦・PRO の MCTS・コーチの深読み・大百科の3D卓）。αβ（Lv.1〜15・分析・ヒント・形勢・振り返り・パズル）は今のまま。評価数で決める Lv.16〜18 は評価あたりが強く・時間がかかるようになり、時間の Lv.19〜23 は同じ時間での強さが変わるので、採用のときに隣どうしの対局で測り直す。

## 推論の高速化（2026-11-20、ネット未採用のまま）

- **値は前と完全に同じ**：`core.c` の `nnFast`。マスの種類分け（`nnClasses`）と和（`nnOut`）を1回の走査にまとめ、見つけたマスの行をその場で累積に足す（`NFI` を経由しない）。足す順番は前と同じ（種類の番号順 → マスのビット順 → アマゾン → 密な入力）なので float の和もビット単位で同じ。種類のループは「クイーン距離の種類・キング距離の種類はどちらも空きマスを分け合う」ので、残りのマスがなくなったら打ち切る。マスのビット → 行の先頭の表 `RB`。学習器（`NNFEAT`）は前の道を通る（`nn.c` は変更なし）。NH が 32 以外のビルドは前の道。
- **確認**：ネイティブで新旧の float 値が 40万局面×手番でビット単位に一致。wasm（SIMD・SIMD なし）新旧が乱数盤 2万×8値で一致。`tools/nnue/check_net.js`（ネイティブ／SIMD／SIMD なし／core_mt.wasm）一致。`tools/check_wasm.js`（ネットなし、JS と一致・MCTS 決定的）。1スレッド MCTS の新旧の結果が一致（`tools/mt_node.js check 1`、仮ネット）、2スレッドも動作。ブラウザ（headless Chrome、仮ネットを `net.js` に置いて）で1スレッド（`aicoding-mt=0`）・マルチスレッド（分離あり）とも Lv.21 が指し、エラーなし。
- **速さ**（作業機は共用2コアで揺れが大きい）：1評価の命令数（ネイティブ、callgrind）v3 7,000・ネット 11,400 → 9,950（v3 比 0.62 → 0.70）。wasm SIMD の評価/秒の v3 比 0.55 → 0.60（中央値、約+9%）。SIMD なしは変わらず（約0.33）。残りは1マス 32 個の float の足し算（全体の大半）で、値を変えずに減らせるのはここまで（float の和は順番で丸めが変わるので、差分更新や同じ行のまとめ足しはできない）。
- **時間固定の対局**（ネイティブ、1手 CPU 0.05秒、仮ネット＝自己対局 1.5万局面・4エポック、`tools/native_match.c` 40組×2）：ネット対 v3 が 旧 26/80（32.5%）→ 新 36/80（45%）。仮ネットは弱く誤差も大きい（±11%）ので目安。

## 上位レベルの隣どうしの対局（2026-11-20、終盤の数え上げの後）
MCTS（エンジンの Lv.16〜23）に終盤の数え上げを入れた後で、上位の隣り合うレベルに段差の逆転がないかを確かめた。**逆転はなく、設定・`RT_LV` は変えていない。**

- 測り方：`tools/native_match.c`（1スレッドのネイティブ、時計はプロセスの CPU 時間、序盤2手ランダム・同じ序盤を先後入れ替え、盤が分かれて陣地差3以上は判定）。MCTS のレベルはサイトと同じ `sep=500`（数え上げあり）。
- 時間で考える Lv.20 以上（エンジン）は時間を 1/20 に縮めた相似の条件（ページは wasm・全スレッド）。エンジンの Lv.19 対 18 だけ実時間（1.5秒 対 120万評価）。
- **道具の不具合を直した**：`native_match.c` の `L23` は表（`LVEV`・`LVMC`）の 23 番目が抜けていて、従来の評価（ev 0）で指していた（このときの 60局は 31.7% と逆転に見えた）。サイトの Lv.23 は MCTS の評価 v3 なので、表を足して測り直した。

## Mac で学習を回す

```bash
cd ~/Documents/GitHub/aicoding
bash amazons/tools/nnue/run.sh                                     # 既定：約2000万局面・1周
WORK="/Volumes/Orico A 8TB/amazons-nnue" bash amazons/tools/nnue/run.sh   # データを外付けに
```
