## 本編のマルチスレッド（2026-11-08）
addendum「本編のマルチスレッド」（全タイトル対応）。探索は JavaScript（`engine.js`）のまま、置換表だけを共有メモリに置く：`mt.c` → `engine_mt.wasm`（置換表 2^20 件と `shared/mtengine.js` の求めるスレッドの関数だけ。ビルドは `mt.c` の先頭）。主スレッドは `engine.js?…&mt=1`、補助は同じ `engine.js?…&mt=2`（評価ネットは各スレッドが自分で持つ）。共有の置換表は同じ探索の深いものを残す（深さ優先の置き換え。世代は `ctl[12]`）。スレッドなしのときの探索は今までと1手も変わらない（3ルール×4局面×3レベルで手・評価値・深さが一致）。
- **解析（`rootList`：分析・ヒント・コーチの採点・検討ボックス）**：深さごとに候補手（12手）をスレッドで分け合う（原子的なカウンタ `ctl[15]` で取り合い、各候補を全幅で読む。値は `ctl` に書き、主スレッドが集める）。同じ深さまでに主スレッドが読む局面数 1スレッド 21.6万 → 2スレッド 12.6万（10局面、**局面数換算 1.72倍**、全スレッドの合計は1.13倍）、最善手は 10/10 一致。
- **1手の読み（コーチの深読み Lv.14、PRO のスレッド数）**：当初は Lazy SMP（補助は同じ局面を1つおきに1手深く始めて読み続ける）。2026-11-09 に下の「スレッドを増やすと浅くなる問題」で Young Brothers Wait に変更。
- AI のレベルは局面数で決める（6級〜五段、時間はその上限）ので1スレッドのまま（レート戦も）。最上位レベルは足さない：五段は1スレッドで28万局面（PC で約5〜10秒）とすでに重く、時間を2倍ずつ伸ばすと上限の約20秒を超えるため。
- 計測（作業環境：共用2コア、負荷が高く時間の比は当てにならない）。正式な効果はユーザーの Mac で `gomoku/bench.html`（1・2・4・8…論理コア数、1手の読みの局面数／秒・深さ・最善手の一致、解析の同じ深さまでの時間）を測る。

### スレッドを増やすと浅くなる問題と修正（2026-11-09）
ユーザーの Mac（14コア＝高性能10＋高効率4、Chrome）の `bench.html`（3秒）：局面数／秒は 2・4・8・14スレッドで ×2.20／×3.98／×6.76／×9.69 と伸びるのに、平均の深さは 7.90 → 7.50／6.80／7.10／7.20 と下がり、解析の同じ深さまでの時間は ×0.92／×0.63／×0.82／×0.60（1スレッドより遅い）、1スレッドと同じ最善手は 5〜7/10。局面10（標準・9手目、1スレッドは深さ11で i10）では 4・8スレッドが深さ3、14スレッドが深さ1で負けの手 j9 を返した。原因は3つ：
1. **共有の置換表の書きかけ・順序の入れ替わり（j9 の原因）**：ロックなしの共有メモリに、照合キー・値・深さ・フラグを別々の配列へ普通に書いていたため、別のスレッドが書いている途中の項目や、ARM（Apple シリコン）で順序が入れ替わって見えた項目を読むと、照合キーは合っていても**別の局面の値・深さ・フラグ**を使ってしまう。この局面は勝ち・負けの値だらけで、偽の「負け」が深い深さの印付きで表に入ると全スレッドがそれを信じ、ルートの全部の手が負けに見えて浅い深さで打ち切り、粘りの手（j9）を返していた。→ 項目を1語（値18ビット｜深さ7｜フラグ2｜年齢5）にまとめ、照合キー k2 に「キー XOR その語」を入れる（`shared/mttt.js` と同じ考え方）。読むときキーと語が合わなければ使わない。2項目のバケット（深さ優先＋常に置換）。補助は主スレッドが探索ごとに上げる年齢を、始めた後に読み直す（以前は補助が古い年齢で書き、深い項目がすぐ上書きされていた）。
2. **手の並べ替えの履歴（history）がスレッドごと**：幅を絞る探索（各節点で上位8〜16手だけ読む）なので、履歴が違うとスレッドごとに読む手そのものが違い、置換表を共有しても互いに助けにならなかった（補助の履歴は前の仕事のまま消えてもいなかった）。→ 履歴も共有メモリに置く（`mt.c` の `HIST`、`engine_mt.wasm?v=2`）。作業機のシミュレーションでは、これだけで同じ深さまでの時間が 2スレッド ×0.8 前後 → ×1.4〜1.5 になった。
3. **解析で遅いスレッドを待つ**：解析は深さごとに候補手を分け合い、全部の手がそろうまで主スレッドが待っていたため、高効率コアなど遅いスレッドが持つ1手が深さ全体を止めていた。→ 取る手がなくなったスレッドは、まだ読まれている手を自分でも読む（共有の表で安く済む）。どれかが読み終えたら他は止める。値は最初に終えたスレッドが compare-exchange で1回だけ書く。

**1手の読みの方式**：Lazy SMP から、主スレッドの読み筋（PV）の節点で手を分け合う **Young Brothers Wait** に変更。PV の節点（窓が全幅、残り深さ2以上）で主スレッドが最初の手を1スレッドと同じに読み、残りの手を全スレッドで取り合って、それまでの最善値（共有、原子的に最大を取る）の null window で試し、上回った手だけ窓を開けて読み直す（減らし方も1スレッドと同じ）。β 以上が出たら残りの手は読まない。主スレッドは一度に1つだけ分け、分けた手の中ではさらに分けない。補助は根からの手順（`ctl` に最大31手）で節点の局面を作る。共有の最善値は分担の番号で印を付け、前の分担を読み終えていないスレッドが新しい分担の値を上げられないようにした（これがないと、まだ読んでいない手を「β 以上で不要」と飛ばして偽の詰みが出た）。

**計測（作業機：共用2コア。各スレッドの CPU 時間を時計にし、スレッドが同じ速さで並ぶよう歩調を合わせるシミュレーション `node` worker_threads）**：
| | 1スレッド | 2スレッド | 4スレッド |
|---|---|---|---|
| 1手の読み：同じ深さまでの時間（未決着の31局面、合計の比） | 1.00 | 修正前 ×0.80 → **×1.48** | 修正前 ×0.78 → **×2.01** |
| 同上で1スレッドと同じ手 | 31/31 | 30/31 | 29/31 |
| bench の10局面・2秒：平均の深さ | 7.40 | 修正前 7.20 → **7.60** | 修正前 7.00 → **7.90** |
| bench：解析の同じ深さまでの時間 | 1.00 | 修正前 ×0.97 → **×1.85** | 修正前 ×1.61 → **×3.37** |
| 解析：4スレッドの1つが2.5倍遅いとき（5局面） | 1.00 | — | 修正前 ×1.07 → ×1.67（遅いスレッドを待たない、履歴の共有前） |

2スレッド対1スレッドの対局（同じ0.5秒、VCT 9・防御 5、16の開局×先後＝32局）：修正後 17勝15敗（修正前 16勝16敗。開局でほぼ勝敗が決まる局面が多く、判定力は低い）。

局面10は修正後、深さを決めた読みで 1スレッドと同じ値（i10、-10118）を 4スレッドで約3分の1の時間で出し、2秒の読みでは 2スレッド深さ10、4スレッド深さ11で i10。スレッドなし（ふつうの1スレッドの Worker）の探索は1手も変わらない（3ルール×10局面×2レベル＋解析で手・評価値・深さが一致）。Mac での再計測待ち。

### 14スレッドで浅くなる問題（2026-11-09、2回目の Mac 計測から）
修正後の Mac（14コア＝高性能10＋高効率4）の `bench.html`：平均の深さ 7.80 → 8.00／8.20／7.90／**7.30**（2・4・8・14スレッド）、1スレッドと同じ最善手 6〜8/10。局面ごとの行では、3秒の読みが**ごく短い時間で浅いまま終わっていた**（局面7 の14スレッド：26ms・深さ2・評価 -14930、1スレッドは深さ7で -99984＝負けを読み切り。局面4 の14スレッド：179ms で深さ8、局面5 の8スレッド：30ms で深さ4）。時間切れではなく、主スレッドがその深さの読みを「止められた」として捨てていた。原因は Young Brothers Wait の分担の印：
1. **遅いスレッドの古い書き込み**：ある分担（split）の手を読んでいたスレッドが、主スレッドがその分担を終えて次の分担を出した後に読み終えると、「その手は読み終えた」の語（`ctl[SP_DW + k]`）を古い分担の番号で上書きしていた（書く前の確認が「自分の番号でなければ書く」だったため）。新しい分担のその手は「未完了」に戻り、主スレッドが最後に全部の手の値を集めるときに未完了の手を見つけると探索を止めたことにして、その深さを丸ごと捨てていた。高効率コアのスレッドは止まる合図（1024局面ごとの確認）に気づくのが遅いので、14スレッドで頻繁に起きた。
2. **分担の手の読み違い**：補助スレッドが分担の番号を確かめた後に主スレッドが次の分担を出すと、補助は新しい分担の手（別の局面の手、空いていない点のこともある）を自分の局面で打つことがあった。
3. **置換表の読み直し**：照合した項目の語をもう一度配列から読んでいたため、その間に別のスレッドが同じ場所を書き換えると別の局面の値を使えた。

**直し**（`engine.js`）：分担を出すとき各手の語を「その分担で未完了」（番号 ≪ 18、値の欄 0）にし、読み終えた値は**その未完了の語からだけ** compare-exchange で書く（`spDone`）。補助は手を読む前に分担の番号がまだ同じで、その手がその局面で打てることを確かめる。置換表は照合に使った語をそのまま使う。スレッドなしの探索は変わらない（共有メモリを使わない）。

**確かめ方（作業機：共用2コア）**：同時に動くスレッドが少ない作業機では起きにくいので、補助が値を書く前に半分の確率で1〜4ms止まる（高効率コアの遅れの模擬）シミュレーション（`node` worker_threads、本編と同じ `engine_mt.wasm` の表、bench の10局面・深さ7まで・各3回）：修正前は8スレッドで **30回中13回**が1スレッドより浅く終わり（局面7は深さ4・-17957 など Mac と同じ形）、修正後は **0/30**（14スレッドの解析も 0/20）。
