# Model Card: Hex search engine (`engine.c` → `engine.wasm`)

ヘックスのAIは、モンテカルロ木探索（MCTS）に、決まった連結を確実に読む「強制連結ソルバー」と、
自己対局から学習した「手の予測」（2026-11 追加、下記）を組み合わせた探索エンジンです。`engine.c` を clang で WebAssembly にしたもの（`engine.wasm`、約27KB）を
ブラウザの Web Worker で動かします。

- **ゲーム**: https://core-calmdust.github.io/aicoding/hex/
- **バージョン**: v1（2026-10-25）
- **ビルド**: `tools/build.sh`（wasm32、初期メモリ64MB・最大128MB）。同じソースから `tools/native.c` でネイティブ版（調整・生成用）も作れる

## 探索
| 項目 | 内容 |
|---|---|
| 木探索 | UCT + RAVE（AMAF）。RAVE_B = 0.0009、UCT の探索項 0（RAVE のみで広げる）、事前知識 8 回分（ブリッジ・自分の石の隣を高めに） |
| ノード | 最大 120万。長い探索ではノードを作る訪問回数のしきい値を自動で上げて、プールを使い切らないようにする |
| プレイアウト | 盤を最後まで埋める。相手がブリッジに割り込んだら必ずもう片方に打つ（辺は仮想の石として扱う）。盤が埋まれば必ずどちらかが勝つので、結果は勝ち負けだけ |
| MCTS ソルバー | 1手で勝てる手・止めなければ負ける手を木の中で確定させる |
| 強制連結ソルバー | 「手番側がN手以内に必ずつながるか」を、証明集合（キャリア）と最短路上のマスへの絞り込み・置換表つきで正確に読む。レベルに応じて根の候補手の絞り込み（must）と、詰めパズル・レッスンの判定に使う |
| 速さ | ネイティブ版 11×11 の空盤で約10万プレイアウト/秒、ブラウザ（wasm）で約4.5万〜10万/秒 |

### ソルバーの検証
5×5（残り3手 1,886局面・4手 1,262局面）と 6×6（3手 1,124局面）で、総当たりの結果と全件一致（`tools/test_solver.js`）。

## 学習した手の予測（2026-11）
木を広げるときの各手の事前知識（仮想の RAVE 結果）を、手作りの数項目から学習した手の予測に置き換えました。
| 項目 | 内容 |

## AIの強さ（20段階）
| レベル | 設定 |
|---|---|
| 15級〜11級 | 40〜200プレイアウト。手の選び方に温度（0.9〜0.5）、一定の確率（30%〜7%）でランダムな手。12級から「1手で勝つ・1手で負けを止める」を必ず指す |
| 10級〜1級 | 300〜11,000プレイアウト。温度を下げていき（0.42〜0）、ランダムな手は9級まで（4%・2%）。4級から2手以内の強制連結も読む |
| 初段〜三段 | 16,000 / 25,000 / 40,000プレイアウト、3手以内の強制連結も読む。1手目とスワップの判断は1手目マップ（下記）を使う |
| 四段・五段 | 1手 1.5秒 / 3秒（端末の速さで強さが変わる） |

スワップの判断は全レベル共通で1手目マップを使う（赤の勝率50%超ならスワップ）。上位レベルは毎局変化をつけるため、勝率50%に近い1手目からランダムに選ぶ。

全対局からまとめて Elo を推定すると（15級＝450 基準）、15級→10級で約 +950、10級→1級で約 +840、1級→四段で約 +210。
1級より上は1段階の差が小さく、この対局数では誤差に近い（スワップありでは同じくらいの強さ同士だと先後の差が出やすい）。
自己対局の Elo は人間相手より差が大きく出るので、レーティング戦の基準値（`app.js` の `RT_LV`）は推定値を 0.75 倍に縮め、
1段階 +40 以上になるようにならした：15級 450、10級 1165、5級 1690、1級 1875、初段 1915 … 四段 2035、五段 2095（五段は推定）。（2026-11 の学習した手の予測で上乗せ。上の節）

## 1手目マップ（`openings.json` の `first`）
7×7・9×9・11×11・13×13 の全マスについて「赤がそこに打ち、青がスワップしない」局面をAIで探索した赤の勝率。
探索値なので理論値ではなく、値は 46〜54%（11×11）程度に圧縮されている。7×7 では中央が理論上の勝ちであることなど、大まかな傾向は既知の結果と合う。

## 生成したデータ
- **詰めパズル**（`puzzles.json`、403問）：自己対局の局面から、強制連結ソルバーで「N手でつながる」「止める手が1つだけ」を確かめ、正解の初手が1つのものだけを採用（`tools/mine_puzzles.js`、`tools/build_puzzles.js`）。
- **レッスン**（`lessons.json`、13ステップ×5問）：ソルバーで正解を一意に確認、作戦の問題はAIの評価値で採点（`tools/gen_lessons.js`）。
- **定跡**（`openings.json`、10の手順）：エンジン同士で打った手順と、各局面の候補手の評価（`tools/gen_openings.js`）。

## 限界
- 評価関数を学習していないので、MoHex などの研究用プログラムよりはずっと弱い。11×11 の上位レベルでも、強い人間には序盤の大局観で負けることがある。
- 1手目マップの勝率は探索で求めた推定値で、理論的な勝ち負けではない。
- 四段・五段は時間で区切るため、遅い端末では弱くなる。

## 本編のマルチスレッド（2026-11-08、addendum「本編のマルチスレッド」）
- エンジンは同じ `engine.c` を `-DMT` で作った `engine_mt.wasm`（`tools/build.sh`）。MCTS なので Lazy SMP ではなく、**全スレッドで1本の探索木を育てる**（tree-parallel MCTS）：木を降りるスレッドは通ったノードの訪問回数を先に数え（virtual loss：結果が戻るまで「勝ちなしの訪問」）、他のスレッドは別の枝を試す。ノードは原子的なカウンタで確保、葉の展開は1スレッドだけ（`exp` を 0→2→1）。木・根の局面・盤の形は共有、1回の降下とプレイアウト・強制連結ソルバーの作業領域はスレッドごと（`TLS`）。強制連結ソルバー（must の判定）は主スレッドだけが使う。**通常版の `engine.wasm` は1バイトも変わらない**（cmp で確認）ので、レベルの指し手は不変。
- 主スレッドは `search()` の最初に木を補助へ開き（`gTree`）、最後に閉じて補助が全員出るのを待ってから結果を読む。補助（`mt-helper.js` → `mt_help()`）はジョブの間、主スレッドが開く木に次々と加わる。プレイアウトの上限は全スレッドの合計（`gHPO`）。
- 対局ページ：`shared/mtengine.js`＋`sw.js`（`shared/mt-sw.js`、light モード）。主スレッドは `engine.js?…&mt=1`。
- 対象：分析・ヒント・コーチ（深読みは Lv.19 = 1.5秒）・検討ボックスと、時間で考える**四段・五段（レート戦も）**。15級〜三段はプレイアウト数で決めるので1スレッドのまま（強さは不変）。PRO のスレッド数はどの制限でも効く（既定は四段・五段が全スレッド、他は1）。情報行の「· NNk playouts/s」は全スレッドの合計。
- 測定（2コアの機械を他の作業と共用、負荷平均 8〜13。このプロセス群に回る CPU は約0.25コア分で、スレッド数を増やしても増えないため、壁時計での速さの比較はできなかった）：
  - CPU 時間あたりのプレイアウト数（11×11 の空盤と8手目の局面、3秒×3回ずつ）：2スレッドの各スレッドは1スレッドの 0.90〜0.98 倍（共有の木への書き込みの競合）。コアが2つ空いている PC では **約1.8〜1.95倍のプレイアウト/秒** の見込み。
  - 同じ時間に相当する対局（プレイアウト数で換算：2スレッド＝合計1万4,400、1スレッド＝8,000、must 3、11×11・スワップあり、初手ランダムで先後入れ替え）：**2スレッド 36勝24敗（60%、約+70 Elo）**。
  - 同じプレイアウト数（合計8,000 対 8,000）：2スレッド 26勝14敗（65%）。木の並列化による読みの質の低下は見られなかった（virtual loss が探索項0の UCT に少し幅を与えている可能性。局数が少なく誤差は±8%程度）。
  - 四段・五段（1.5秒／3秒）は1手あたりのプレイアウトがもっと多いので、伸びは同程度と見込む（本番の時間では測っていない）。コアが多い PC ほど伸びる。
- 最強解析ページ（`pro/`）はヘックスには置いていない（任意のため今回は見送り）。

### マルチスレッドの点検（2026-11-09、チェッカー・モリスの置換表の件を受けて）
- **確認して問題なかったもの**（tree-parallel MCTS）：葉の展開は1スレッドだけ（`exp` 0→2→1 の CAS、展開中の葉に当たったスレッドはそこからプレイアウト）、ノードの確保は原子的なカウンタ、子は確保したスレッドだけが書き `exp=1` を最後に置く、主スレッドは木を閉じて補助が全員出るのを待ってから読む（`gTree`／`gActive` の二重確認）、プレイアウトの上限は全スレッドの合計（`gHPO`）、停止。
- **訪問数・勝ち数の加算**は原子的でない（float の `+=`）が、作業機の測定でルートの子の訪問数の合計 ÷ プレイアウト数は 4スレッドで 0.9996（取りこぼし 0.04%）。原子的な加算（CAS）にした版も試したが、同じプレイアウト数での最善手の一致は良くならなかった（下）ので戻した。
- **木の大きさ**（ノード 120万＝約34MB、11路は1回の展開で約100ノード）はスレッドが増えるほど早く満杯になるが、満杯に近づくと展開のしきい値（`expT`）を上げて読み続ける作りで、探索は止まらない。`-DMT` だけノードを4倍（480万）にした版も試した。
- 作業機での比較（11路、ランダムな12局面、プレイアウト数で揃えた。基準は480万ノード・1スレッド 24万プレイアウトの最善手）：1スレッド 3万 6/12、**今の版 4スレッド 合計12万 9/12**、原子的な加算 5/12、原子的な加算＋4倍のノード 8/12（12局面なので ±2 程度は誤差）。→ 変えていない（engine_mt.wasm は変更なし）。
- **計測ページ `hex/bench.html`**（新設、noindex・どこからもリンクしない。囲碁と同じ形：11路の10局面、1・2・4・8…論理コア数でプレイアウト数／秒と、基準（1スレッドで時間×2〜4）との最善手の一致）。Mac で測る：`hex/bench.html`。

### スレッドが伸びない問題（2026-11-09）
- **ユーザーの Mac（14コア＝高性能10＋高効率4、Chrome）の実測**（`hex/bench.html`、11路・3秒）：1スレッド 15.8万プレイアウト/秒、2スレッド ×1.56、4 ×1.67、8 ×2.25、14 ×2.63（効率19%）。同じ方式の囲碁は 14スレッドで ×8.1。
- **原因：共有の木への書き込みによるキャッシュラインの取り合い**。ヘックスの1プレイアウトは約6µs（囲碁のネット評価の約3000分の1）と非常に軽いのに、1回ごとに
  - 経路上の**すべての**ノードで、子の約半分に RAVE の結果を書く（11路の根の子は約120個＝約3.4KB＝53ライン。1プレイアウトで1段あたり約50ライン）、
  - 通った子に訪問数（virtual loss）と勝ち数を書く、根の訪問数を書く、補助はプレイアウトごとに共有カウンタ `gHPO` を原子的に足す（同じラインに停止フラグ・木の番号）、ノード数 `nNodes` が読み取り専用のパラメータ（RAVE_B など）と同じラインにある、
  ため、根に近いノード（全スレッドが通る）のラインがスレッド間を行き来し続けていた。前の点検（作業機、共用2コア）ではスレッドが実際には同時に動いていなかったので見えなかった。
- **作業機での再現**：①実スレッド（`tools/mtbench.c speed`、pthreads で engine_mt.wasm と同じコード）で、空いているときの 2スレッドの CPU 時間あたりのプレイアウトが1スレッドの 73%（別々の2プロセスなら 99%）。②**キャッシュラインのモデル**（`tools/mtsim.c`：T スレッドを順に1回ずつ、全員が降りてから全員が戻る＝T個のプレイアウトが同時進行、読み書きを MESI 風に数える。機械の混み具合に左右されない）で、1プレイアウトあたりのライン移動が 2スレッド 417、8スレッド 524、14スレッド 663（ほぼ全部が RAVE の書き込みと、それを読む選択）。
- **直したこと（`engine.c` の `-DMT` 部分だけ）**：
  - **訪問の多いノードの結果をスレッドごとにためてまとめて足す**（`RBuf`、スレッドごとに16枠）：訪問数 n のノードについて、子の RAVE の結果と、子ごとの訪問・勝ちをスレッドの枠にため、選ぶときはためた分も足して使う。訪問・勝ちは n ÷ (16 × スレッド数) 回ごと（最大2048、全スレッドで止めておく分は n の 1/16 以下、書くのは通った数個の子だけ）、RAVE はその4倍ごと（約1/4、ほぼ全部の子。RAVE は多くのプレイアウトの平均なので、この遅れでは動かない）に木へ足す。この枠のあるノードの子には virtual loss を書かない（n ≥ 64 × スレッド数なので1訪問で選択はほぼ変わらない。スレッドは下の、訪問の少ないノードで分かれる）。それより訪問の少ないノードは今まで通りすぐ書く。根の訪問・勝ちは64回ごと。
  - 補助のプレイアウト数は32回ごとにまとめて足す（主の上限の判定は回数の上限があるときだけ読む。終わりに端数も足すので合計は正確）、停止フラグ・木の番号・根の証明は8回ごとに見る、共有の変数（`gStop`・`gTree`・`gActive`・`gHPO`・`nNodes`）をそれぞれ別のキャッシュラインに置く、virtual loss が1のときの不要な書き込みをやめた。
  - 1スレッドのとき（木に補助がいない）は何もためないので、**同じ探索**（作業機で、前の engine_mt.wasm と1スレッドの手が一致）。**通常版 `engine.wasm` はバイト一致**（`tools/build.sh` と同じコマンド・同じ出力名で作って cmp）。engine_mt.wasm は 171KB → 176KB。
- **作業機での確認**：
  - ライン移動（`tools/mtsim.c`、bench.html の局面、60万〜100万プレイアウト）：2スレッド 417 → **12**、4スレッド 461 → **11**、8スレッド 524 → **32**、14スレッド 663 → **51**。
  - 実スレッドの2スレッド（`tools/mtbench.c speed 2 2000`）：壁時計 11.6万 → 19.6万/秒（同じ時の1スレッド 12.2万）、CPU 時間あたり 73% → 81%（このときはまだ RAVE だけをためる版。作業機はほかの仮想マシンと CPU を取り合っていて、その後は2スレッドが同時に動かず測れなかった）。
  - 同じプレイアウト数の対局（`tools/mtbench.c match`、11路・スワップあり、1手2万プレイアウト、must 3、初手2手ランダム、先後入れ替え、相手は1スレッド）：**直した版 8スレッド 20勝20敗、前の版 8スレッド 19勝21敗**（作業機の2コアに8スレッドなので、スレッドは時分割で動き結果がたまる時間は Mac より長い）。同じプレイアウト数での強さは前の版と同じで、1スレッドとも差がない。

### スレッドの伸び（続き）（2026-11-10）
- **現状**：上の「直した版」（#1316、`engine_mt.wasm?v=2`）は main に入っているが、Mac での測り直しの記録はまだない。まず Mac で `hex/bench.html` を測ってもらう（今回 `engine_mt.wasm?v=3`）。比べる前回の数字（#1316 より前の版）：1スレッド 15.8万プレイアウト/秒、2 ×1.56、4 ×1.67、8 ×2.25、14 ×2.63。
- **作業機（2コア）で確かめたこと**：
  - 空いているときの実スレッド（`tools/mtbench.c speed 2 3000`、10局面×3秒）：今の版の2スレッドは壁時計 ×1.92、CPU 時間あたり 1スレッド比 0.97（#1316 の前は 0.73）。2スレッドは十分伸びている。
  - ライン移動／プレイアウト（`tools/mtsim.c`、bench.html の4局面、60万プレイアウト）：2スレッド 8.6、4スレッド 11.8、8スレッド 30.4、14スレッド 52.8。
  - **プールの大きさ**：1スレッドで 300万プレイアウト（Mac の14スレッド・3秒の見込みに相当）でもノードの使用は約58%（`expT` が探索の初めに約300まで上がり、その後は木がゆっくり育つため）。3秒の計測ではプールは足りていて、アマゾンズのような「プールが埋まって待ちが増える」ことはない。
  - 高効率コア：MCTS は各スレッドが自分のペースでプレイアウトし、他を待たない（遅いスレッドは回数が少ないだけ）。作業機では測れない。
- **残っている取り合い**：ノードは訪問が `expT`（長い探索では約300）になってから展開するので、木のノードはどれも数百訪問ある。まとめて足す枠（`RBuf`）を使うのは訪問 64 × スレッド数 以上（14スレッドで896）なので、14スレッドでは2〜6段目のノード（訪問300〜900）が毎回 RAVE を書く。14スレッドの 53 のうち約40（RAVE の書き込み 20、それで読み直しになった選択の読み 20）がこれ。
- **試したが入れなかったもの**：
  - **RAVE の結果だけを 16 × スレッド数 の訪問からためる**（訪問・勝ちと virtual loss はすぐ書く。RAVE を木に足すのは n ÷ (4 × スレッド数) 回ごと、枠は16→32）：ライン移動 2スレッド 8.6 → 4.9、4 → 8.1、8 → 16.0、**14 → 31.3**（Mac の見込みで14スレッド 1割前後、8スレッド数%の上乗せ）。最善手の一致（`mtsim.c` のモデル、ランダム局面）は 8スレッド合計3万 19/30（前 18/30、1スレッド 17/30）、14スレッド合計10万 7/12（前 6/12）と落ちなかったが、**同じプレイアウト数の対局**（`tools/mtbench.c match 8 20000`、相手は1スレッド、同じ初手で前の版と並べた。シード11・12）で **試した版 31勝39敗、前の版 39勝31敗**（70局、勝敗が分かれた局は 7 対 15、偶然でも p≈0.13）。少ない訪問のノードで「訪問はすぐ・RAVE は遅れて」入るのが選択をずらしている可能性があり、強さが落ちないと言えないので入れていない。
  - ためる幅を小さくした版（RAVE を n ÷ (16 × スレッド数) 回ごと・下限2）は14スレッド 46.3、(8 × スレッド数) 回ごとは 42.3 で、効果が小さい。訪問・勝ちのためる下限を 4 → 2 にする案も効果は小さい（上の版と合わせて 31.3 → 29.9）。
- **入れたもの**：プールが満杯のときは葉の `exp` に CAS を書かずに戻る（満杯のあと、展開できない葉に来るたびに共有の行へ2回書いていた。長い検討で満杯になったとき用。結果は同じ）。1スレッドは前の engine_mt と10局面の手・訪問数・ノード数が一致、通常版 `engine.wasm` はバイト一致。headless Chrome（Playwright）で `hex/bench.html` を2スレッドで動かし、分離・2スレッドの起動・結果の表が正しいことを確認。
- **次の手**：Mac の測り直しで 8・14スレッドがまだ見込み（8 ×6前後、14 ×6〜7）より低ければ、上の RAVE の取り合いが残りの原因の候補。その場合は対局を多くして（200局程度）強さを確かめてから入れる。
