# オンライン対戦の改ざん対策：設定手順

対象は世界のボドゲ大全のオンライン対戦ゲーム、まいにち数独・すぴーど数独・さめが〜めのランキング、共通アカウントです。

## 0. 現在の状態

- 新しいクライアントのコードは `main` に公開済みです。
- データベースが**旧ルールのままでも、これまでどおり動きます**。本番の各プロジェクトで、非公開ルームを使って確認済みです。
- 新ルールを公開すると、各ページはそれを自動で検出して新しい精算方式に切り替わります。ページを開き直すだけで切り替わり、コードの再公開は不要です。
- ルールを貼り替えた瞬間に進行中だったレート戦は、旧方式で作られた対局のためレート対象外になることがあります。利用者が少ない時間帯に公開してください。
- ルールは手で編集せず、`shared/tools/secrules.py` を直して `python3 shared/tools/secrules.py` で作り直す前提です。

### 新しいゲームのプロジェクトを作るとき（アゴンの例）
- Authentication：匿名と Google を有効化。承認済みドメインに `core-calmdust.github.io` を追加。
- Realtime Database（asia-southeast1）を作成し、(a) のルールを貼り付け。
- App Check：reCAPTCHA Enterprise のキーを登録（サイトキーは `<game>/firebase-config.js` に設定済み）。

### (a) ルールの貼り付け（ゲームごとに1回）

1. https://console.firebase.google.com で該当のプロジェクトを開きます。
2. 「構築 → Realtime Database → ルール」タブを開きます。
3. 表のファイルの中身を**全部**貼り付けて「公開」します。ファイルは次の URL からまとめてコピーできます（`<game>` はフォルダ名）。

   `https://raw.githubusercontent.com/core-calmdust/aicoding/main/<game>/database.rules.json`

4. 公開後にゲームページを開き直すと、自動で新方式になります。

### (b) App Check（reCAPTCHA v3）

1. **reCAPTCHA v3 のキーを作る**（全プロジェクト共通で1つで構いません）
   - https://www.google.com/recaptcha/admin/create を開き、種類は「スコアベース（v3）」を選びます。
   - ドメインは `core-calmdust.github.io` です。localhost は入れず、ローカル確認には手順5のデバッグトークンを使います。
   - 作成すると「サイトキー」（公開して問題ない）と「シークレットキー」（非公開）が表示されます。
2. **各プロジェクトに登録する**（上の表のすべてのプロジェクト）
   - Firebase コンソールで「App Check → アプリ」を開きます。
   - 該当のウェブアプリで「reCAPTCHA」を選び、**シークレットキー**を入力して保存します。
3. **サイトキーを Claude に送る**
   - Claude が各 `<game>/firebase-config.js` の `window.FIREBASE_APPCHECK_SITE_KEY` に設定して公開します。共通アカウントは `shared/atlas-firebase-config.js` の `ATLAS_APPCHECK_SITE_KEY` です。
   - 現在は `null` で、App Check は動いていません（何も壊れません）。
4. **キー入りのページが公開されてから、強制を有効にする**
   - 「App Check → API」で Realtime Database の「確認済みリクエスト」の割合が十分高くなるまで、1〜2日待ちます。古いキャッシュのページは未確認として数えられます。
   - 割合が十分になったら「**Realtime Database だけ**」を「適用（強制）」にします。Authentication は当面強制しなくて構いません。
   - 注意：強制後は、reCAPTCHA を遮断する一部の広告ブロッカーを使っている人はオンライン機能が使えなくなります。
5. **ローカルで試すとき**
   - `http://localhost:…/<game>/?appcheckdebug=1` を開くと、ブラウザのコンソールにデバッグトークンが出ます。
   - そのトークンを「App Check → アプリ → ︙ → デバッグトークンを管理」に登録します。

## 2. 守られるようになること（新ルール公開後）

- **レートの直接書き換え不可**
  - レート、対局数、勝敗数は、自分が実際に対戦した終局済みのレート戦を「精算」する書き込みと一緒にしか変えられません。
  - 1局につき1回だけです。増減は K（40／32／24）以内で、勝ちならプラス、負けならマイナスです。
  - 新規の記録は 1500 からしか作れません。
- **結果の相互確認**
  - 盤上で終わった対局は、両者が自分の結果を `res/<uid>` に申告し、一致した時だけレートが変わります。
  - 食い違った時は「結果が一致しないためレート対象外」と表示されます。
  - 投了は本人だけが書けます。時間切れと放棄はサーバー時刻で検証します。合意の引き分けは相手の申し出を受けた側だけが書けます。
- **負けの精算を逃げられない**
  - レート戦は作成時に両者へ紐付けられます（`open/<uid>`）。
  - 精算（または無効化）するまで次のレート戦は組めません。
  - 精算は起動時、毎分、対戦相手を探す前に自動で行われるため、途中でタブを閉じても結果は失われません。
- **対局記録の保護**
  - 書き込めるのは対局者2人だけです。手順は追記のみです。
  - 対局者、レート、持ち時間、ルール種別、レート対象フラグは変更できません。
  - 終局後は状態を変えられません。自分の持ち時間を増やすこともできません。
  - チェス、将棋、五目並べ、チェッカー、モリス、ウゴルキ、アゴンは手番順もルールで強制します。ウル王朝のゲームは追加手番があるため、記録の「次の手番（nt）」に従って手番を判定します。
- **レート戦の作成制限**
  - 2人とも対戦待ち（lobby）に入っていて、現在の正しいレートを使い、未精算の対局がない場合だけ作れます。
  - 架空の相手や、いない相手とのレート戦は作れません。
- **稼ぎ（ファーミング）対策**
  - 同じ相手とのレート変動は1日3局までです（UTC 基準）。
  - 対局数3未満の新規アカウントが相手の場合、K は半分になります。
- **その他**
  - チャットは同じ人が3秒に1回までです（サーバー時刻で判定）。
  - presence、プロフィール、同期データは本人だけが書けます。文字数とサイズの上限もあります。
  - 匿名から既存の Google アカウントへ切り替える時のレート引き継ぎは、本人だけが知る使い捨ての鍵で守られます。
- **App Check（強制後）**：このサイトのページ以外（スクリプトや改造クライアントからの直接アクセス）を拒否します。

## 3. まだ可能なこと（サーバー側の検証が必要）

- **不正な手の検出**：ルールでは盤面の正しさまで判定できません。リバーシのパス、ドット＆ボックスの連続手番、バックギャモンの手番も、ルールでは厳密に縛れません。
- **改造クライアントによる「無効化」**：盤上の終局でわざと食い違う結果を申告すれば、その対局をレート対象外にできます。レートを**得る**ことはできませんが、負けを無効にすることはできます。
- **複数アカウント**：匿名ログインで別アカウントを作ること自体は止められません（新規は 1500 から、相手のレートへの影響は半分）。
- **ランキング系**：まいにち数独、すぴーど数独、さめが〜めのスコアは自己申告で、ルールでは範囲と書き込み回数のチェックだけです。
- **App Check の限界**：本物のブラウザでページを操作する不正は防げません。

## 4. 将来のオプション3（Blaze プラン＋Cloud Functions）で加わること

- 終局時に Cloud Functions が手順をサーバーで再生し、正しい手と結果を判定してレートを計算します。
- その段階で players はクライアントから完全に書き込み禁止にします。
- データの形（`games/<gid>` の `moves`・`res`・`j`・`lm`、`open/<uid>`、`pc/<uid>/<opp>`）はそのまま使えます。
  - 関数は `games/{gid}/status` の変化で起動します。
  - 判定結果で `players` を書き、`open` を消します。
  - その後 `players` のルールを `.write: false` にするだけで切り替えられます。
- 合わせて次のことができます。
  - バックギャモンのサイコロをサーバーで振る
  - 不正の疑いがある行動（食い違いの多発など）の記録と通知
  - 古い対局データの自動掃除
  - ランキングスコアの再検証

## 6. 共通仕様への追加案（game-conventions 用の1段落）

> **オンライン対戦の改ざん対策（全オンラインゲーム共通）**：オンライン対戦を持つゲームは、`shared/tools/secrules.py` で生成した Realtime Database ルールを使い、クライアント側は `shared/onlinesec.js` で精算する。プレイヤーのレート・対局数・勝敗は、自分が対局者で終局済みのレート戦（作成時に `open/<uid>` で両者へ紐付け）を精算する一括書き込みでしか変えられない（増減は K 以内、対局数＋1、同一相手は1日3局まで、新規アカウント相手は K 半分）。盤上の終局は両者が `res/<uid>` に自分の結果を申告し、一致したときだけ有効とする（食い違いはレート対象外と表示）。投了・時間切れ・放棄・合意引き分けは記録とサーバー時刻で判定する。対局記録は対局者のみ・手順は追記のみ・対局者／レート対象／持ち時間は不変・終局は一度だけとする。精算は起動時・毎分・検索前に再試行し、途中で閉じても結果が失われないようにする。チャットは3秒に1回。新しいゲームを足すときは `secrules.py` の GAMES に設定を追加してルールを生成し、エミュレーターのテストを通してから公開する。各ゲームの `firebase-config.js` には `FIREBASE_APPCHECK_SITE_KEY`（null＝無効）を置き、App Check（reCAPTCHA v3）を有効化できるようにする。
