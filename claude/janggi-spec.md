# チャンギ（janggi/）仕様

韓国将棋。シャンチー（xiangqi/）のページを土台にしたフォーク。共通ルールは game-conventions(-addendum).md に従う。

## ルール（janggi/engine.js・engine.c）
- 9×10 の交点。川なし。両陣の九宮に斜め線。楚（Cho・青緑）が先手、漢（Han・赤）が後手。
- 将・士：九宮の中を線にそって1歩（斜め線も）。象：直1＋斜2（途中がふさがると不可）。馬：直1＋斜1（足しばり）。
- 車：直線どこまでも＋九宮の斜め線。包：必ずちょうど1枚（包以外）を跳び越えて動く・取る。包は包を越えられず取れない。
- 兵（楚は卒）：前か横に1歩。相手の九宮では斜め線にそって前へも。
- 상차림：対局前に各自4通りから選ぶ（0 마상상마・1 상마마상・2 마상마상・3 상마상마）。AI は自分でランダムに選ぶ。オンラインと3D卓は 3/3 固定。
- 引き分けなし。詰みで勝ち。同一局面3回か200手で点数判定（車13・包7・馬5・象3・士3・兵2、漢+1.5）。パスは動かせる手がないときだけ。

## エンジン（engine.c → engine.wasm、`tools/build.sh`）
- xiangqi と同じ探索（PVS・置換表・静止探索）、手作りの評価関数。強さは局面数（`nk`）で決まるレベル（13〜20）と深さ＋ノイズのレベル（1〜12）。
- **探索 v2（2026-11-13）**：枝刈りを強めた（下の「探索 v2」）。Lv.1〜12（`values`）は前の探索のまま。
- 高速化（2026-11-08）：駒の位置を色ごとの90ビット集合（`BB`）で持ち、指し手生成・評価・`bigPieces` は盤の90点を走査せず駒だけを点の昇順で回す（走査と同じ順なので結果は1手も変わらない）。九宮の危険度は九宮の9点だけを見る。48局面の固定深さ6・7で最善手・評価値・局面数が完全一致のまま **約1.9倍**（WASM、約82万→約158万局面／秒）。`-msimd128` は効果なし（±2%）で使わない。

## ページ
- 14言語。文言は xiangqi/i18n.js ＋ janggi/tools/i18n_jg_*.json の上書き（node janggi/tools/build_i18n.js で janggi/i18n.js を生成）。
- 棋譜表記：韓国式座標（段1〜0・筋1〜9、楚から見て）＋駒名。韓国語はハングル、それ以外は漢字。
- 引分提案ボタンは非表示。定跡タブなし（定跡集は未作成）。
- コーチ：xiangqi のコーチを流用し、チャンギ向けの文言・点数（janggi/coach-jg.js）。川・飛将・格言系のヒントは無効。
- パズル：janggi/tools/native.c の `jg mates` で自己対局から収集（tools/mates/run*.txt）→ janggi/tools/build_puzzles.js で検証・テーマ分け（1〜3手詰め・連続王手4〜5手）。289問。
- レッスン：15ステップ×5問（はじめて7：車・馬・象・包・卒で取る／逃げる／1手詰め、戦術4：得な交換・両取り・王手で得・守る、詰み2：2手・3手詰め、終盤2：車と馬・卒2つ）。`jg dump`（自己対局の局面）→ `node janggi/tools/gen_lessons.js dump.txt tools/mates/run2.txt,tools/mates/run1.txt` で自動生成・エンジン検証（パズルと重複なし）。文言は tools/i18n_jg_lessons.json（14言語）。準備ステップ（ramp）はなし。

## 対局設定の Pro モード（2026-11-08）
対局設定の「AIの強さ」の PRO ボタン（`shared/proset.js` の `ProSet.ladder()`、addendum「対局設定の Pro モード」）。項目：思考の制限（時間／深さ／局面数）、手のばらつき（深さで読むときだけ。弱い段の既定はその段のノイズ、変えると 小＝いちばん弱いノイズ／大＝弱い段の中ほどのノイズ）。変えた値は engine.js `think` の `cfg`（LEVELS と同じキー。強い段の最大深さは `dx`）で渡す。レート戦では使わない。戦績のキーは `ai:pro<レベル>`、相手名に「PRO」。
- 先読み（2026-11-11、既定オフ、`shared/ponder.js`）：AI が指した直後から人の手番中もスレッドのプールで読む。`pv_line`の2手目（予想手）を指した後の局面を読み、予想どおりならその読みを置換表から引き継ぎ、外れても置換表は残る。AI 自身の手も同じプール（置換表）で読む。着手・待った・新規対局・終局・タブ非表示で即停止。

## 本編のマルチスレッドと最強解析（2026-11-08、addendum「本編のマルチスレッド」「最強解析ページ」、手本：シャンチー）
- `engine.c` を `-DMT` で作った `engine_mt.wasm`（`tools/build.sh`）。置換表・評価の重みは共有、局面・履歴・キラー手などはスレッドごと（`TLS`）の Lazy SMP。補助の奇数番は1手深く読み始め、置換表の世代は主スレッドだけが進める。`MT(m)`（手の行き先）と名前がぶつかるので `-DMT` は先頭で `JG_THREADS` に読み替え。**通常版 `engine.wasm` は1バイトも変わらない**（レベルの指し手は不変）。
- 対局ページ：`shared/mtengine.js`＋`sw.js`（light）。主スレッドは `engine.js?…&mt=1`、補助は `mt-helper.js`（同じ局面を `best(99, 0, 0)` で読み続ける）。対象は分析・ヒント・コーチ（深読み）・検討ボックスと、時間の上限のある Lv.19・20（250万／700万局面、最大8／12秒、レート戦も）。主スレッドは段の設定のまま読み、補助が置換表を埋めて同じ時間でより深く読む。Lv.1〜18 は1スレッド。PRO のスレッド数はどの制限でも効く（既定は Lv.19・20 が全スレッド）。情報行に「· NNN nps」（全スレッドの合計）。
- 最強解析 `pro/`（`pro/coi-sw.js`）：棋譜欄の「最強解析」ボタン（14言語、`xiangqi/i18n.js` から生成）で表示中の局面を新しいタブで開く。レート戦の対局中は無効、オンラインでは非表示。
- 測定：2コアの機械を他の作業と共用（負荷平均 8〜10）。深さ9までの時間（24局面）は壁時計では 0.84倍（実質1コアで、各スレッドの速さが半分）だが、局面数換算では2スレッドの主スレッドが1スレッドの約63%の局面数で届く（**約1.60倍**、空いたコアがある PC の目安）。最善手は24局面中20で一致。主スレッド1手15万局面同士の2スレッド対1スレッド24局（序盤2手ランダム・先後入れ替え）：**16勝8敗（66.7%、約+120 Elo）**。

### マルチスレッドの見直し（2026-11-09、チェッカー・モリス・タフルの置換表の件を受けた点検）
- シャンチーと同じ作り・同じ問題（1キー1項目の構造体を欄ごとに書く置換表、主スレッドの結果だけで答える、補助の深さのずらし）で、同じ直し（`engine_mt.wasm` だけ、通常版 `engine.wasm` は cmp 一致）：4項目バケット × 2^20 = 64MB、`{ key ^ w, w }` の XOR 照合、深さと年齢で置換、最も深い結果で答える、ずらしなし。宣言 1092 ページ → `initial` 1152（`app.js`・`pro/pro.js`・`bench.html`）、`engine_mt.wasm?v=2`、`pro/` `?v=2`。停止・TLS・補助の止まり方は問題なし。
- 作業機（共用2コア・負荷が高いので、主スレッドが同じ深さまでに読む局面数を時間とみなす。Node の worker_threads で本編と同じ共有メモリの組み方、乱数の12局面、毎回表を空に。倍率は各自の1スレッド比）、深さ10：実際の大きさの表 旧 2・4スレッド ×1.89／×3.24 → 新 ×1.90／×3.09。表を Mac 並みに埋めた条件 旧 ×1.71／×3.29 → 新 ×1.72／×2.62、別の乱数の12局面では 旧 ×1.84／×2.59 → 新 ×1.78／×3.13（局面による揺れが大きい）。旧の置換表も「深い項目を守る」置き換えだったので速さの差は誤差の範囲。直したのは主に壊れた項目を使わないことと、補助の深い結果を使うこと。
- 計測ページ `janggi/bench.html`（新設、初期局面から乱数で 10〜39手の12局面）。要計測（Mac）。

## 探索 v2（2026-11-13、学習なしの強化）
ユーザーの方針：Mac の CPU が将棋の学習で埋まっている間は、学習のいらない強化をする。タフルの探索 v2（`tafl/MODEL_CARD.md`）と同じ考えで `engine.c` の枝刈りを強めた。評価関数は手作りのまま。

| 項目 | 前 | v2 |
|---|---|---|
| LMR（後ろの静かな手を浅く） | 手の順番で 1〜3 | 対数の表 `floor(0.3 + ln(深さ)·ln(順番)/2.2)`、PV は −1、ヒストリーが高い手は −1・低い手は +1 |
| LMP（浅い所で後ろの静かな手を読まない） | なし | 深さ5以下・PV 以外・王手なしで `6 + 3×深さ²` 手目より後 |
| ヌルムーブ | R = 2（深さ7以上は3） | R = 3 + 深さ/4 + min(2,（静的評価 − β）/200) |
| 逆フューティリティ | 深さ3以下・110×深さ | 深さ6以下・90×深さ |
| フューティリティ | 深さ2以下・150×深さ | 深さ4以下・120×深さ+60 |
| 置換表の手がない節 | そのまま | 深さ4以上は1手浅く（IIR） |
| ヒストリー | カットした手に加点 | 加えて、その前に試した静かな手を減点 |
| 静止探索 | 全部の取り | 静的評価＋取る駒＋250 が α に届かない取りは読まない |
| 静的評価 | 評価関数の値 | 置換表の値で補正 |

- 各項目は `-DSV_LMR=0` などで個別に外せる（計測用）。LMR・LMP の強さは `-DLMR_BASE`・`-DLMR_DIV`・`-DLMP_A`・`-DLMP_B`。
- **計測**（`tools/duel.py`：前のビルドと新しいビルドを別プロセスで対局。`jg serve`。ランダムな상차림＋序盤4手ランダム、同じ序盤を先後入れ替え。作業機・ネイティブ・1スレッド）：

|---|---|---|
| 同じ局面数 1手1万（300局） | +184 −116 | +80（+41 .. +122）、平均の深さ 4.6 → 5.4 |
| 同じ局面数 1手2万（180局） | +111 −69 | 約 +83、深さ 5.4 → 6.4 |
| 同じ局面数 1手10万（160局） | +111 −49 | **+142**（+85 .. +205）、深さ 7.2 → 8.8 |
| 同じ時間 1手0.06秒（180局） | +108 −72 | 約 +70、深さ 7.1 → 8.1 |

## NNUE の準備（2026-11-14、学習は Mac で）

評価関数を学習（NNUE）に置き換えるための仕組みを先に入れた。**ネットワークはまだ無いので、いまの対局は手作りの評価のまま**（動作は前と同じ。初期局面の Lv.14・16・18 と解析で指し手・局面数が一致）。

- **形はシャンチーと共通**：(1260→256)×2視点→1、SCReLU。盤 9×10・駒7種・駒コードが同じなので、`engine.c` の NNUE 部分（差分更新つき）・ファイル形式（"NUEX"）・学習器（`xiangqi/tools/nnue/train.c`）・記録（`xq.h`、1局面 56バイト）をそのまま使う。チャンギ固有の違いはパス（動ける手が無いとき）で、アキュムレータをそのまま引き継ぐ
- **先生は自分のエンジン**（`jg datagen`）：初期配置 16通り＋序盤 2〜9手のランダムな合法手から、1手 8,000局面の自己対局。各局面の探索の評価値（勝率に直す：手作りの評価は 430点 = 1ロジット、`jg scale` で測定）と対局の勝敗を記録。外部エンジン（Fairy-Stockfish など）は、パス・点数判定などルールの差とライセンスの確認が要るので使っていない
- **Mac での手順**：`bash janggi/tools/nnue/run.sh`（`janggi/tools/nnue/README.md`）。10万局 ≒ 900万局面、10コアで 2時間前後 → 学習 → `nnue.bin.gz`
- **採用の手順**：`janggi/nnue.bin.gz` に置き、`janggi/engine.js` の `NET` に版を入れる（空文字の間はネットワークを取りに行かない）。1スレッドは `engine_simd.wasm`、マルチスレッドは `engine_mt.wasm`（リードが共有メモリに読み込み、ヘルパーは `mt-helper.js` で同じ評価）。使うのは探索レベル（Lv.13〜20）・解析・コーチで、Lv.1〜12 は手作りの評価のまま（`wNN`）。最強解析ページ（`pro/`）は未対応（採用時に `xiangqi/pro/pro.js` と同じ読み込みを足す）。`bench.html` の説明文「手作りの評価」も採用時に直す
- **採用の基準**：同じ持ち時間・同じ局面数の両方で手作りの評価に勝ち越すこと（`python3 janggi/tools/duel.py /tmp/jg@nnue.bin /tmp/jg n 20 400 1`、`jg nmatch`）。NNUE は 1局面の評価が重い（シャンチーで約 0.5〜0.6倍の速さ）ので、同じ時間で勝てるかが要点。採用したら Lv.13〜18 の局面数を同じ強さに合わせ直し、Lv.19・20 の RT_LV を上げる
- **確認したこと**（サンドボックス、12万局面だけの仮ネット）：差分更新と全計算の一致（`jg nncheck`、パスを混ぜた 2万6千局面で不一致 0）、ブラウザでの読み込み（`engine_simd.wasm`＋`nnue.bin.gz`、マルチスレッドのリード）。仮ネットはデータが少なすぎて手作りの評価に 0−100 で負ける（強さの見込みは Mac の本番データで判断する。先生が自分自身なので、伸びる保証は無い：だめなら 2周目（`NET=`）か、データ・局面数を増やす）
