# 将棋 評価関数の強化：手法の調査（2026-11-15）

本将棋（`shogi/`）の評価関数（NNUE、駒だけの入力 2534 → 中間層 512 → 出力）をこの先どう強くするかの調査結果です。
方針は「**自力で作る**」（他作の評価関数ファイルはサイトに載せない。強い AI を**教師として使う**のは可）。
実験の記録は `shogi/MODEL_CARD.md`、学習の手順は `shogi/tools/TRAIN.md`。

## 0. 結論（先に）

1. **幅を広げる案は、実はブラウザでは割に合う可能性が高い。** 1024 が「同じ持ち時間で −86 Elo」だったのは、計測用のターミナル版エンジンだけ出力層が遅い作りだったため。ブラウザ版（wasm）で測ると 1024 の速さの損は **約12〜15%**（ターミナル版は 40% と出ていた）。同じ局面数では +62 Elo なので、差し引きプラスの見込み。→ 計測ツールを直した（§1）。**最優先で測り直す。**
2. **学習の目標の作り方（勝敗の重み）に、同じデータでの実証済みの改善がある。** tanuki- の実験では、いま使っているのと同じデータで「手数が進むほど勝敗を重く、評価値を軽く」が最良だった（§3.1）。こちらは一律 0.75 のまま。→ 学習器に対応を入れた。
3. **DL 系（dlshogi 型）の評価値で付け直す「蒸留」が、いまの将棋 AI の主流の強化法。** 深さ12 の探索で付け直す（効果なしだった）のとは別物で、同じデータで R+95〜104 の報告がある（§3.2）。Mac でも現実的な速さで作れる見込み。
4. **強い小型の評価関数は「広い第1層＋小さな中間層＋進行度で切り替える層」という形。** つようら王11micro は駒だけの入力で 2048 幅（§2）。こちらの「512 → 出力」は、器としてかなり小さい。
5. チェスの Pentium Pro の実験（§5）の教訓：**探索のパラメーターを今のネットと速さに合わせて調整し直す（SPSA）**、**自分の探索が実際に評価する局面を強い教師で付け直す**、が効いている。

## 1. 計測の誤りの訂正：幅の広いネットの「遅さ」

| | 512 | 768 | 1024 |
|---|---|---|---|
| ブラウザ版（wasm SIMD、同じ探索、6回の最良） | 2559 ms | 2862 ms（−11%） | 2896 ms（−12%。平均では −15%） |
| ターミナル版・直す前（x86、素のループ） | 610 千局面/秒 | — | 394（**−36%**。Mac では −40%） |
| ターミナル版・直した後（SSE2） | 1070 千局面/秒 | — | 880（−18%） |

- サイトの wasm は出力層（`nueEval`）を SIMD で書いてあるが、対局ツール（`usimatch`・`kptool`）は同じ `engine.c` の素のループで動いていた。出力層は幅に比例する計算なので、**幅の広いネットほど実際より遅く測られていた**。
- `engine.c` に NEON（Apple silicon）と SSE2 の出力層を足した（ネイティブのビルドだけ。wasm は作り直してもバイト単位で同じ）。探索は同じ（チェックサム一致）で、512 でも 1.7倍速くなる。Mac での確認は `bash tools/nnue/simd-check.sh`。
- これで「同じ持ち時間」の対局が、サイトの実態に近い条件になる。**これまでの「同じ持ち時間」の結果は、どれも幅の広い側・評価の重い側に不利な条件だった**（HalfKP の −87 → +17 の揺れ、1024 の −86 など）。同じ局面数の結果は影響を受けない。

## 2. 強い小型評価関数の形（公開情報から）

- **つようら王11mini / micro**（2026-10、MIT）：評価関数タイプは `SFNN_ka2_4096_8_64_progress8`（mini、約8.5MB）と `SFNN_ka2_2048_8_64_progress8`（micro、約4.5MB）。水匠5 より R150〜200 強い。入力は「実質的に駒の情報だけ」（玉との組み合わせなし＝こちらと同じ系統）で、入力層付近のパラメーターが従来の 1/81。
  - 読み方：SFNN＝Stockfish 型の NNUE、`ka2`＝駒だけの入力、2048 / 4096＝第1層の幅、8 と 64＝そのあとの小さな中間層、`progress8`＝進行度で8つの層の組を切り替える。
  - 進行度は「玉の位置×駒」の線形の式（`progress.bin`：81×1548 の重み）で求め、7つの境界で8区分にする。持ち駒の枚数のような手作りの区分ではなく、学習した進行度。
- **示唆**：駒だけの入力でも、(a) 第1層をずっと広く、(b) 出力の前に小さな非線形の層、(c) 進行度ごとに層を丸ごと切り替える、で水匠5 を超える。こちらが試した「出力の重みだけを持ち駒の枚数で8区分」（効果なし）は、(b) が無いので区分の効き目が小さかったと考えられる。
- **計算量の見方**：第1層の更新は「動いた駒の数 × 幅」の足し算で、幅に比例するが軽い。重いのは出力側。Stockfish 型は、第1層の出力を2つずつ掛け合わせて半分にし（pairwise）、次の層を 8〜16 出力・int8・ゼロを飛ばす疎な計算にして、広い幅でも出力側を軽く保っている。

## 3. 学習の作り方

### 3.1 勝敗の重み（lambda）— 同じデータでの実証あり

tanuki-（いま使っているデータ `tanuki-.nnue-pytorch-2024-07-30.1` の作者）の一連の実験：

- 目標 ＝ lambda × 評価値 ＋ (1 − lambda) × 勝敗。**収束後に lambda を下げるほど強くなった**（0.5 → 0.4 → 0.3 → 0.2 → 0.1 の順に改善）。理由は「このデータを作った評価関数が強く、勝敗の精度が高いから」。
- 最良は**手数で変える**形：60手目まで lambda を 1.0 から 0.0 へ直線的に下げ、以降は 0.0（勝敗だけ）。ランダム初期値からで R+20.7、Fine-tuning で R+12.9（5000局、有意。直前の最良比）。
- 学習の設定：SGD（momentum 0.9）、学習率 0.5 → 収束後 0.05、Warmup 1万バッチ、Newbob 風の減衰、バッチ 16384、score-scaling 511、勝敗の教師信号 1 − 1e-8、量子化は収束後、qsearch の末端の局面に置き換えてから学習。ネットは `halfkp_512x2-8-96`。
- **こちらの現状**：lambda 0.75 の一律、Adam、学習率 1e-4。→ `trainkp --lambda 1 --lambda-end 0 --lambda-ply 60`（`run-kp.sh` では `LAMBDA=1 TRAIN_OPTS="--lambda-end 0 --lambda-ply 60"`）を追加した。小さいネットでは勝敗だけの目標は荒れやすいので、`--lambda-end 0.3` などの中間も試す。

### 3.2 DL 系の評価値で付け直す（知識蒸留）

- やり方：既存の教師局面を、**DL 系の将棋 AI（dlshogi 型）の Value で付け直す**。探索はせず、1局面につき推論1回。2024年末に tanuki- が発表し、2025年以降の主流（水匠10 もこの方法で WCSC35 優勝）。
- 効果：同じデータを DL水匠で付け直して学習 → ランダム初期値から **R+104.3**、Fine-tuning で **R+94.6**（5000局、有意）。lambda=1.0 に固定（勝敗を使わない）と逆に R−41.4：終盤は深さ9の対局の勝敗のほうが正確、という考察。→ **付け直した評価値＋手数で変える lambda の組み合わせ**が要点。
- なぜ深さ12 の付け直し（こちらで効果なし、相関 0.961）と違うか：探索を深くしても同じ系統の評価値が少し正確になるだけ。DL 系は別の種類の大局観（序中盤の形勢判断が良い）で、NNUE が自分の探索からは得られない情報が入る。「正解は互いに似ているが、誤りはばらばら」＝どのソフトで作ったかではなく、真の形勢にどれだけ近いかが効く、という整理。
- 手に入るもの：強い DL モデル（DL水匠、Ryfamate）は支援者向け頒布。**無償なら dlshogi の公開モデル**（GCT 電竜2020、第2回電竜戦エキシビジョン `model-dr2_exhi` など）。ツールは dlshogi の `hcpe3_re_eval` 系と、やねうら王 ScriptCollection の `convert_teacher.py`（hcpe3 ↔ psv）。
- Mac での速さの目安：M4 Mac mini で dlshogi の ONNX モデル（29MB）を onnxruntime＋CoreML で動かして約1700 NPS（探索つきの対局時）。M1 の Neural Engine でバッチ16・1329 サンプル/秒（2022年、別モデル）。バッチを大きくした一括推論なら毎秒数千局面が見込め、深さ12 の付け直し（毎秒317局面）より1桁速い。**要実測。**
- こちらの小さいネットでどれだけ効くかは未知（報告は 512x2-8-96 など大きいネット）。器を広げる（§1・§2）のと組み合わせる前提で考える。

### 3.3 局面の選び方

- **qsearch の末端に置き換える**：評価関数が実際に呼ばれるのは、駒の取り合いが収まった局面。教師局面をそこへ置き換えてから学習する（やねうら王の `qsearch_psv`、tanuki- のシャッフルルーチン）。こちらは「王手でない・最善手が駒取りでない局面だけ残す」で近いことをしているが、置き換えではなく間引き。
- **自分の探索が見る局面で学ぶ（on-policy）**：チェスの実験（§5）で、エンジン自身の探索に出てくる局面を強い教師で付け直して学習し直すと +28〜64 Elo。こちらのデータは最強クラス同士の対局の局面で、サイトのエンジンが読みの中で出会う「崩れた局面」が少ない。`kptool gen`（自己対局）で作った局面を `relabel.sh` で付け直す形で試せる。
- 詰みの局面・進行度の低い局面を除く、角換わりの比率など、分布の調整も行われている。

### 3.4 そのほか

- 学習器：nnue-pytorch と bullet（Rust、GPU）が主流。やねうら王は bullet 版（BulletOu）に移行。こちらの `trainkp.c` は CPU の自前実装で、いまの規模（4億局面×数エポック、512〜1024 幅）なら足りている。
- 量子化を見越した学習、重みのクリップ、活性化関数（CReLU / SCReLU / pairwise）の選び方が、チェスの小型ネットで細かく研究されている。第1層の出力がゼロになる割合（疎さ）が速さに直結するので、活性化関数の選択は速さの問題でもある。

## 4. 探索と評価関数の合わせ込み

- **SPSA で探索の定数を調整し直す**：枝刈りの余裕などの定数は、評価値の尺度・精度・1局面あたりの時間に最適値が依存する。チェスの実験では最初の調整で +202（1秒）/+100（10秒）、ネットを替えるたびの再調整で +4〜+90。こちらは v5 → v7 でネットも尺度も変えたが、定数は v6 のときに尺度を合わせただけ。
- **評価値のキャッシュ**・ヌルムーブ時の差分の共有：こちらは遅延計算をすでに入れてあり、キャッシュは wasm では効果なし（計測済み）。
- **コンパイラの設定**（リンク時最適化、コードの配置）で +27〜35 の例。wasm では `wasm-opt` などが相当。未着手。

## 5. 参考：チェスの「Pentium で Kasparov に勝てたか」実験（N. Carlini、2026-11-01）

200MHz の Pentium Pro・64MB で、改造した Stockfish 17 が 1手30秒で 3180±80。1996年の Crafty に現代の手法を足していく実験も行い、+1335 のうち +720 がソフトウェアの進歩によるもの、という内容。こちらに関係する点：

| 手を入れたところ | 効果（1手1秒 / 10秒） |
|---|---|
| 探索と評価の定数の調整（SPSA、Texel） | +202 / +100 |
| NNUE を自己対局の評価値で学習 | −32 / +45（これだけでは伸びない） |
| **教師を強いエンジン（Stockfish）に替える** | **+228 / +147** |
| ネットを6倍に広げる、評価のキャッシュなど | +210 / +98 |
| 再調整、駒数で切り替える出力、中間ユニットの追加、データ2倍 | +90 / +128 |
| （Stockfish 側）評価を3倍速くする（ネットを小さく） | +162 / +45 |
| （同）自分の探索の局面を教師で付け直して学習 | +28 / +64 |
| （同）探索とネットを一緒に最適化 | +35 / +4 |
| （同）コンパイラ・配置だけ | +27 / +35 |

教訓として書かれていること：**持ち時間が短いほど評価の速さが、長いほど評価の質が効く**。強い教師を使うと必要な計算が桁で減る。コードは LLM のコーディングエージェントに書かせ、対局で1つずつ確かめている。

## 6. 進め方（提案、効果の見込みと手間の順）

| 順 | 内容 | 手間 | 根拠 |

| 4 | **探索の定数の SPSA** | 仕組み作り＋Mac で一晩 | §4・§5 |

## 7. 実測の結果（2026-11-15 追記）

- **§0 の 1（幅を広げる案）は外れ**：計測ツールを直して測り直しても、1024 は 300ms で −69（対照 −20）。浅い読み（3万局面）では +32〜62 だが、深い読みで差が消える。ツールは主因ではなかった。
- **§3.1（勝敗の重みを手数で変える）も、512 幅では改善なし**：300ms で −42、尺度を合わせて −75。
- 分かったこと：**浅い読みで効く改善（探索すれば分かることの先取り）は、実戦の強さにならない**。採否は 300ms で決める。残るのは教師の質（§3.2）と、器の作り（§2）・探索の合わせ込み（§4）。
- §3.2 の道具を用意した：`shogi/tools/nnue/dlrelabel.py`・`dlrelabel.sh`（onnxruntime＋CoreML、無償の GCT モデル）。
- 教師モデルの条件：GCT（dlshogi WCSC31 版に同梱の `model-0000225kai.onnx`、10ブロック）は配布ページに利用条件の記載なし。dlshogi の `dr2_exhi`（15ブロック）は、私的利用は自由・学習用の棋譜生成は可、商用利用・直接の対局・再配布・追加学習は不可（https://tadaoyamaoka.hatenablog.com/entry/2021/08/17/000710 ）。

- **§3.2（DL 系の評価値で付け直す）も、512 幅では改善なし**（2026-11-16）：1.5億局面を GCT で付け直して学習、300ms・480局で −3（−33 〜 +28）。240局で +58 と出たのは偶然だった。採否の対局は480局以上にする。
- ここまでで学習データ側の案はすべて効果なし。次は §4 の探索の定数の調整（`shogi/tools/match/spsa.py`）、そのあと §2 のネットの形。
