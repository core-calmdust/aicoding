# 将棋：本ソフトの探索と、やねうら王（Stockfish 系）の探索の違い（2026-11-17）

「1つ直せば強くなる」ではなく、**仕組みどうしがどう噛み合って強さになっているか**を比べるための資料です。
本ソフト＝ `shogi/engine.c`（2026-11-17 時点）。比較相手＝やねうら王の現行ソース（`yaneuraou-search.cpp`・`movepick.cpp`・`history.h`・`tt.cpp`、Stockfish 17 系の移植）。
評価関数側の調査は `claude/shogi-eval-research.md`、実験の記録は `shogi/MODEL_CARD.md`。

## 0. 決定的な実測：同じ評価関数で、探索だけを入れ替える（2026-11-17）

やねうら王の探索に**本ソフトの評価関数（v7）をそのまま載せた**ものを作り（`shogi/tools/match/yo-ours.sh`。評価値が本ソフトと一致することを 2000局面で確認）、本ソフトと対局させた。評価関数が同じなので、差は探索だけ。

| 本ソフトの局面数 | やねうら王の探索（同じ評価関数）の局面数 | 本ソフトから見た結果 | Elo 差 |
|---|---|---|---|
| 3万 | 3万 | 8勝 111敗（120局弱） | **約 −460** |
| 3万（相手に渡す評価値を ×1.24） | 3万 | 4勝 115敗 | 約 −580 |
| **30万（10倍）** | 3万 | 20勝 25敗 1分（46局） | 約 −40 |

- **同じ評価関数・同じ局面数で、探索だけで約 460 Elo の差がある。本ソフトが 10倍読んで、まだ少し足りない。**
- やねうら王の探索は、本ソフトの評価関数で 10万局面のとき深さ14（選択的には20）に届く。本ソフトが深さ14 に届くのは約250万局面。
- 評価関数を良くしても強くならなかったのは、これで説明がつく：今の強さを決めているのは探索。**評価関数の改善（幅・中間層・DL の教師）は、探索が追いついてから測り直す。**
- 注意：局面数の数え方は両者で少し違う。やねうら王側は評価を毎回最初から計算する遅い作りなので、時間ではなく局面数で比べている。実際の速さ（本ソフトは 1スレッドで毎秒約200万局面）を考えても、差の大半は残る。
- 下の §3 の「置換表を大きくすると…」は、Mac の多スレッド（10スレッド・5秒）では確認できなかった（64MB / 256MB / 1GB で深さ 19.38 / 19.12 / 19.25）。**置換表の大きさは主因ではない。** 差は §2 の仕組み全体（手の統計・枝刈り・読みの短縮・延長の噛み合わせ）にある。

## 0.5 どの仕組みが効いているか（2026-11-17）

**(a) やねうら王の探索から、仕組みを1つずつ外す**（評価関数は本ソフトの v7。相手は本ソフト。本ソフト 10万局面 対 やねうら王側 1万局面、各100局。`OURABL=<番号> bash tools/match/yo-ours.sh 10000 100000 50 2`）

| やねうら王側から外したもの | 本ソフトの勝ち（100局中） | 読み方 |
|---|---|---|
| なし（そのまま） | 75 | 基準 |
| **手を選ぶループの中の枝刈り**（手数・評価値・駒損・履歴で後ろの手を捨てる） | **100** | 最大。外すと全敗 |
| **静かな手の並べ替えに履歴を使わない** | **97** | 最大級 |
| 子の節点での評価値による打ち切り（RFP） | 90 | 大 |
| 読みの短縮（LMR） | 89 | 大 |
| 評価値の補正 | 83 | 小（誤差に近い） |
| 飛び抜けた手の延長 | 80 | 誤差内 |
| ヌルムーブ | 79 | 誤差内 |
| 置換表に手がないときの短縮（IIR） | 79 | 誤差内 |
| 見切り（razoring） | 78 | 誤差内 |
| 並べ替えの履歴を「手番×移動＋1・2手前との組み合わせ」だけに減らす | 72 | 差なし |
| ProbCut | 65 | 誤差内（外したほうが良いかもしれない） |

（100局の誤差は ±9 勝ほど。）

- **差を担っているのは4つ：履歴による並べ替え、ループの中の枝刈り、RFP、LMR。** 飛び抜けた手の延長・補正・追加の履歴・IIR などの「新しめの手法」は、この条件では誤差の範囲。
- 履歴は、本ソフトと同じ種類（手番×移動＋1・2手前）だけに減らしても弱くならない。**足りないのは履歴の種類ではない。**
- この4つは本ソフトにも全部ある。つまり差は「有るか無いか」ではなく、**効かせ方（どこまで刈るか・どれだけ短縮するか・履歴の更新の仕方）と、その噛み合わせ**にある。

**(b) 逆に、強いソフトの手法を本ソフトに1つずつ足す**（`engine.c` の `set_param` 28〜39、既定は切。本ソフトどうし、2万局面、各200局）

| 足した手法（番号＝値） | 結果（Elo） |
|---|---|
| ヌルムーブの短縮を大きく（28=4 / 28=5） | +10 / +7 |
| 評価値による見切りを、短縮後の深さ8未満まで（30=8） | +16 |
| **後ろの手を捨てる、どの深さでも（29=1）** | **−149** |
| **駒損の静かな手を捨てる（33=20）** | **−51** |
| **駒損の駒取りを捨てる（34=100）** | **−102** |
| 置換表に手がないとき1手浅く（35=6） | +31 |
| 王手の延長をやめる（36=1）／PV だけ（36=2） | −14 / −19 |
| 2手目から短縮（37=1） | +26 |
| 駒損の駒取りも短縮（38=1） | +10 |
| カット節点でもう1手短縮（39=1） | −17 |

（200局の誤差は ±48 ほど。誤差を超えたのはマイナスの3つだけ。）

- (a) で最大だった「ループの中の枝刈り」を本ソフトに入れると、逆に大きく弱くなる。**同じ枝刈りが、やねうら王では最大の武器で、本ソフトでは毒。** 噛み合わせの差がここに出ている。
- 次に調べること：なぜ本ソフトでは刈ると弱くなるのか。候補は、(1) 履歴の値の質（更新の仕方・値の幅）、(2) 刈る基準に使う「短縮後の深さ」の中身、(3) 静止探索（置換表なし・最初の1手だけ王手を読む）で刈った手の穴を埋められない、(4) 刈ったあとに残る手の数え方。本ソフト側でも同じ「1つずつ外す」計測をして、どの仕組みが実際に働いているかを見る。

## 0.6 本ソフトの探索の中で、何が働いているか（2026-11-17 夜）

**(c) 本ソフトから、仕組みを1つずつ外す**（本ソフトどうし、2万局面、各200局。誤差 ±48）

| 外したもの | 結果（Elo） | やねうら王で同じものを外したとき（§0.5） |
|---|---|---|
| 評価値での打ち切り（RFP） | **−166** | 大 |
| 手の統計（履歴 v2） | −35 | **最大級** |
| 読みの短縮（LMR を単純な式に） | −23 | 大 |
| 後ろの手を捨てる・評価値での見切り（深さ1 だけに） | −42 | **最大** |
| 静止探索の最初の1手の王手 | −42 | （なし） |
| ProbCut | +3 | 誤差内 |
| 1手詰めの検出 | +5 | — |

- **本ソフトの探索は、ほぼ「評価値での打ち切り」だけで立っている。** 履歴・読みの短縮・枝刈りは、あっても無くても 20〜40 Elo しか変わらない。やねうら王ではこの3つが主役で、外すと壊滅する。
- つまり本ソフトでは、履歴 → 並べ替え → 短縮・枝刈り、という連鎖が**回っていない**（形はあるが、効くほど強く使っていない）。

**(d) 打ち切りが、並べた手の何番目で起きるか**（同じ中盤12局面、1局面 30〜50万局面。`usimatch stat`、やねうら王側は `OURSTAT=1`）

| | 本ソフト | やねうら王の探索（同じ評価関数） |
|---|---|---|
| 届く深さ | 11 | 17〜20 |
| 静かな手で打ち切ったとき、それが1番目だった割合 | 35〜39% | **70%** |
| 同、深さ 4〜7 の節点での平均の順位 | **7.4** | 1.9 |
| 打ち切りが置換表の手だった割合 | 18% | 32% |
| 静かな手での打ち切りが起きた節点の深さ（1〜3 / 4〜7 / 8〜） | 98% / 2% / 0.05% | 50% / 43% / 7% |

- 本ソフトの木は「浅いところに葉が大量にある」形。やねうら王の木は、深い節点にも仕事が分散している（大胆に短縮・枝刈りするので、同じ局面数で深くまで届く）。
- 並べ替えの差の一部は、本ソフトが**駒損の駒取りを静かな手より先に読む**ことから来ていた（`set_param 40`）。王手を先に（41）、履歴の加点を深さに比例（42）と合わせると、1番目の割合は 70% になり、数字の上ではやねうら王と並ぶ。

**(e) それでも強くならない**（本ソフトどうし、2万局面、各200局）

| 設定 | 結果（Elo） |
|---|---|
| 40（駒損の駒取りを後に） | −10 |
| 41（王手を先に） | −5 |
| 42（履歴の加点を深さに比例） | +35 |
| 40＋41＋42 | −63 |
| 35＋37＋42＋30（IIR・2手目から短縮・加点・見切り） | +35 |
| 上の全部＋ヌルムーブ・上向き・カット節点・王手の延長なし（枝刈り2つは除く） | +5 |
| さらに「どの深さでも後ろの手を捨てる」「駒損の手を捨てる」も入れた全部 | −23 |

- 「どの深さでも後ろの手を捨てる」は、単独では −149 だったが、全部入りの中では約 −30 に縮む。**組み合わせで効き方が変わる**ことは確認できた。ただし、切り替えを全部入れても差し引きゼロで、やねうら王の +460 には届かない。
- 切り替えで足せる範囲（既存の探索への継ぎ足し）では埋まらない。まだ入れていないのは、静止探索での置換表・置換表の評価値・駒取りの履歴・履歴による枝刈りと短縮量の加減・短縮の大きさそのもの。

**方針**：継ぎ足しをやめ、**探索の関数を新しく書く**（`search2`：Stockfish 系の手順どおりに、置換表 → 評価値 → 打ち切り → 手を選ぶループ（枝刈り・短縮）→ 履歴の更新、を一式そろえる。コードは自作、数値は SPSA で合わせる）。既存の探索は残し、切り替えで比べる。ものさしは「同じ評価関数のやねうら王の探索」との対局（§0）で、互角に近づくまで詰める。

## 0.7 新しい探索の関数（search2）の最初の版と、測り方の落とし穴（2026-11-18）

## 1. 結論（先に）

- 強いソフトの探索は、**4つの仕組みが互いを前提にして**成り立っている：
  ① 大きな置換表（前に読んだ結果と、その局面の最善手・評価値を覚えておく）
  ② 手の良し悪しの統計（履歴）を何種類も持ち、手の並べ替えを正確にする
  ③ その並べ替えを信頼して、後ろの手を大胆に浅く読む・捨てる
  ④ 評価値の癖を対局中に補正する
  ①②が弱いまま③だけ強めると、良い手を捨てて弱くなる。
- **本ソフトは①と②がかなり簡素で、そのため③を強くできない状態**。定数の自動調整（SPSA）が「枝刈りを控えめにする」方向に動いたのは、これと整合する（並べ替えの情報が足りないので、刈ると損をする）。
- 評価関数を良くしても強さに出なかったのも説明がつく：探索の主な節点の 6〜7割は「評価値が十分良いので打ち切り」で終わっており（下の実測）、打ち切りの基準は粗い。評価値が少し正確になっても、探索の形はほとんど変わらない。
- （訂正）「最初に直すべきは置換表の大きさ」と書いていたが、Mac の計測で否定された（§0）。置換表は「評価値を入れる・静止探索で使う」の中身の話に絞る。

## 4. 進め方（噛み合わせの順に）

1つずつ足して対局で確かめるが、**順番が大事**（前の段が次の段の前提）。各段は、時間で区切る対局・480局以上で確かめる。段ごとに定数を SPSA で合わせ直す。

| 段 | 内容 | 狙い |
|---|---|---|
| 1 | **置換表**：大きさを端末に合わせて増やす（多スレッド版 64MB → 256MB〜）、1スレッド版も束にする、評価値を入れる、静止探索でも使う | 長い持ち時間・多スレッドでの伸び。以降の段の土台 |
| 2 | **手の統計を増やす**：駒を取る手の履歴、直前の手との組み合わせを 4 手前まで、評価値の補正、節点の種類（カット／オール）と ttPv | 並べ替えと短縮量の精度 |
| 3 | **大胆に刈る・短縮する**：全部の手を短縮の対象に、深さによらない手数・評価値・駒損での枝刈り、ヌルムーブの短縮を大きく、飛び抜けた手の延長（王手の一律延長はやめる） | 同じ時間で深く読む |
| 4 | 定数の SPSA をやり直す → 評価関数に戻る（幅・中間層・DL の教師は、探索が良くなってから測り直す） | |

- 段1 の最初の確認（Mac、約3分）：多スレッド版の置換表を 64MB / 256MB / 1GB にして、同じ時間で届く深さを比べる（`TRAIN.md` ではなく下のコマンド）。
  ```sh
  cd shogi && gzip -dc nnue.bin.gz > /tmp/site.bin
  for b in 20 22 24; do cc -O3 -DNATIVE -DMT -DNUE_H=512 -DTTM_BITS=$b -w -o /tmp/um-mt$b tools/match/usimatch.c -lpthread && /tmp/um-mt$b /tmp/site.bin bench 5000 10 tools/match/openings.txt; done
  ```
- 深さの数字は強さそのものではない（ソフトごとに意味が違う）。採否は対局で決める。
- 比較相手の数字（置換表の当たる割合など）は、こちらでは測っていない（評価関数ファイルが作業環境にない）。必要なら Mac の教師用のやねうら王で測る。
