# 3Dレッスン（日本語）の品質ループ

2026-11-21 開始。対象：3Dレッスンのある全ゲーム（atlas/lessons3d.js の DATA：dots, morris, mancala, tafl, shogi, chess, reversi, gomoku, go, checkers, xiangqi, backgammon, hex, amazons, connect4）。

## 目標
- キャラクターの口調で自然な会話にする。文末に「〜だよ」「〜よ」が続かない。キャラらしい言い方（口ぐせ：ケロ・コン・ワン・ピョン・ペン・カニ など）を、くどくならない程度に。
- 問題の起承転結：問題を出す → ヒント → 正解ならほめて理由を言う → 不正解なら、正しい手（印・矢印・手の名前）と「なぜだめか（見落とし・デメリット）」を具体的に言う。
- 1つのレッスンの中でも、問いかけ・ほめ言葉・指摘の言い回しにバリエーションを持たせる。キャラの一貫性は保つ。
- 座標は3D盤にないので書かない（チェス・将棋の手の名前は可）。
- 文章量はスマホとPCの両方でバランスよく：吹き出しは1ページ（スマホ44字・PC58字が目安）に収め、1つの吹き出しはスマホで4ページ・PCで3ページまで。正解・不正解の解説は150字以内。長い1文は読点で区切れるように書く（区切れない長文は吹き出しが大きくなって盤を隠す）。
- 実機確認：スマホ（390×844）とPC（1440×900）の両方で吹き出しを開き、文字がはみ出さず盤を隠しすぎないことを見る。
- **問題そのものの良し悪しも検証し、必要なら問題を作り直す**（2026-11-23 ユーザー：セリフの書き直しで対応できないものは問題を柔軟に改良する。問題の良し悪しも合わせて検証する）。セリフだけでは直らない減点（同じ局面・全問が同じ点を教える・答えが正しくない など）は、問題の局面・答え・選択肢を差し替える。見るところ：
  - 正しさ：答えが合法で、エンジン／盤面で本当にいちばん良い手（`tools/lesson-facts.js`）。
  - 答えがはっきりしている：答えと2番目の手の差が十分ある（同じくらい良い手が複数あるなら、どれも正解にするか局面を変える）。
  - 簡単すぎない：打てる手・選択肢が1〜2しかない、置いた瞬間に分かる、などの問題は作り直す。
  - レッスンの主題に合っている：題名・導入で教えたことを使わないと解けない。主題と関係ない手が答えになっていない。
  - 重ならない：ほかの問題と同じ局面・1〜2手違いの局面にしない。同じ狙い（同じ手筋）ばかり5問並べない。
  - 並び：1問目から少しずつ難しく。最後の問題はレッスンのまとめ。
  - 不正解の手が意味のある失敗になる：よくある間違い（見落とし・欲張り）を選んだとき、何が起きるかを盤で見せられる。
  - 問題データ（`<game>/lessons.json` など）は2D版と共用。差し替えると2D版の問題も変わるので、2D版でも表示と正誤が正しいことを確かめる（2D版の文言 i18n も合わせて直す）。
  - 見つけた検証は、できるだけ `tools/lesson-facts.js`（ゲームごとの盤の事実・唯一解）や `tools/lesson-quality.js`（問題の重なり・主題のかたより）のチェックとして足して、次の回から自動で見張れるようにする（基準を甘くする変更は不可）。

- **理由はAIの評価ではなく、盤の上の事実で言う**（2026-11-22 ユーザー指示：「AIの評価が下がるから取りたくない」などは最悪）。不正解なら「その手のあと相手に何をされるか（詰まされる・動かした駒をただで取られる・ねらわれていた駒を取られる・王手で攻めこまれる・成りこまれる）」や「正解の手が何をする手か」を具体的に。「AIの評価・見立て・形勢・評価値・勝つ見込み○%」を理由にしない（評価ツールで大きく減点）。将棋のレッスンは shogi/tools/lesson-replies.js で全合法手への相手の応手を前もって調べ（shogi/lesson-replies.json）、atlas/lessons3d.js の shReplyCore が文にする。定跡は盤面から（shStaticWhyJa・shContrastJa）。
- **定跡の手順は、全部の手にひとことガイドを付ける**（2026-11-22 ユーザー指示：指すごとに何も言わない手があるのはやめて）。将棋は shStepNotesJa が盤面から作る（「☗先手：まずは歩を突いて角道を開ける手…」）。ほかのゲームの定跡も同じようにする。

- **盤の事実が正しいことも評価する**（2026-11-22 ユーザー指示：アマゾンの「緑の印はそれぞれの方向でいちばん遠いマス」が実際は1マス手前だった。文章と合わせて問題のチェックもきちんと評価する）。`node tools/lesson-facts.js [game]` が各ゲームのエンジンで、答え・許される手が合法か、印が文章の言うとおりか（届く／いちばん遠い など）を確かめる。lesson-quality.js はこの結果を読み、事実がまちがっているレッスンは −60 点（不合格）。**いまはアマゾンだけ**。ほかのゲームは、品質ループでそのゲームを直すときに、まず lesson-facts.js にそのゲームのチェックを足してから文章を直す（答えの合法性・正解手の一致・印や数（何マス・何枚・何%）が文章と盤で一致するか）。

## 第2期：問題の検証ループ（2026-11-23 16:50〜、ユーザー指示）
ユーザー：「問題の検証＋問題がある場合は修正＋修正に必要な本文の改変、改良（並びに品質を担保するための評価、検証）を厳しい採点でループ作業」。セリフの点（lesson-quality.js）は全ゲーム pass 95 に到達済み。これからは**問題そのもの**を全ゲーム・全レッスン・全定跡で検証する。

- **対象と順番**：下の「検証の進み具合」表で未検証のものから。深い検証がまだのチェス・将棋・チェッカー・リバーシ・五目並べ・シャンチー・マンカラ・ドット・アンド・ボックス・タフル・アマゾン・コネクト4、一部だけ済みの囲碁・バックギャモン・モリス、そして各 `<game>/open`（定跡）。1回に1ゲーム（大きければ数レッスン）。
- **厳しい採点（問題ごとに全部満たして合格。1つでも欠ければ不合格）**：
  1. 答えが合法で、エンジン／ソルバー／全探索でいちばん良い手（または目的を達する手の集まりと一致）。
  2. 答えがはっきりしている：同じくらい良い手がほかにない（あるなら全部正解にするか局面を変える）。2番目の手との差を数値で確かめる。
  3. 簡単すぎない：合法手・選択肢が3つ以上あり、置いた瞬間に分かる形でない。
  4. 主題に合う：レッスンの題名・導入で教えたことを使う手が答え。
  5. 重ならない：同じゲームのほかの問題（レッスン・定跡・2D版を通して）と同じ局面・1〜2手違いでない。同じ手筋を5問くり返さない。
  6. 並び：1問目から少しずつ難しく（エンジンの読みの深さ・候補の数などで確かめる）。
  7. 不正解の手を選ぶと、そのあと盤で何が起きるか（取られる・詰まされる・つながる 等）を本文で正しく言えている（盤の事実で確認）。
  8. 本文（問いかけ・ヒント・正解・不正解・手順のメモ）が盤の事実と合っている。
  9. 2D版でも同じ問題が正しく表示・判定される（lessons.json 共用のため）。
- **自動化**：見つけた検証はゲームごとに `tools/lesson-facts.js`（または新しい `tools/lesson-verify.js`）のチェックとして足し、上の1〜8を機械で確かめる。わざと答えを変えたデータで検出できることも確認する。チェックを甘くする変更は不可。
- **直し方**：不合格の問題は局面・答え・選択肢を作り直し（エンジンで確認）、それに合わせて本文（3D・2D、14言語）を書き直す。直したあと lesson-quality.js（セリフ）でも pass 95 を下回らないこと。lesson-progress.js の進行チェックと3D（スマホ・PC）・2D の表示確認まで行う。
- **記録**：ログ表に「問題検証済み（対象）」と、見つけた問題・作り直した問題・機械チェックの結果（何問中何問合格）を書く。下の表も更新する。
- **担当を2つに分ける（2026-11-24 03:25〜、ユーザー指示：作業量が多いので担当を1人増やしてよい）**：1時間ごとの定期実行を2本にする。
  - **担当A**（毎時16分 UTC、ブランチ `lesson-loop-…`）：各ゲームのレッスン（/open 以外）。未の shogi・xiangqi・tafl と、一部済みのゲームの残りのレッスン。
  - **担当B**（毎時46分 UTC、ブランチ `lesson-open-…`）：各ゲームの定跡・定石 `<game>/open`（とコネクトフォーの定跡レッスン op1〜op3）。
  - 重複の防止はそれぞれ自分のブランチ名だけで見る（相手の PR があっても止まらない）。相手の担当範囲には手を出さない。同じファイル（このファイル・atlas/index.html や lessons3d.js の版番号・lesson-verify.js）を両方が触るので、マージ前に main を取り込み、衝突はどちらの変更も残して解消する（版番号は大きいほうに +1、ログ行は両方残す）。
  - 自分の範囲がすべて「検証済み」になった担当はログに「担当A 完了」「担当B 完了」と書いて以後何もしない。両方そろったら「第2期 完了」と書く。

#### 追加の基準（すべての問題・定跡に、①〜⑨と同じく合否で当てる）
- **追1 準備・見本と同じ局面**：1問目が準備（ウォームアップ）の解説・見本と同じ局面（答えを見せたあと同じ問題）。チェッカー・シャンチー・シャンチー詰み。→ 重なりの比較に準備・見本・練習・パズル・詰将棋・2D版・他レッスンのすべてを入れる。
- **追2 対称を見落とした重なり**：回転・左右上下の反転・色の入れかえで同じ局面・同じ手（from→to も対称で比べる）。タフル・リバーシ・チェッカー。
- **追3 採点で2番目が正解扱い**：選択肢が多いと2番目の手が16点などで「正解」「惜しい（緑）」になる。マンカラ・ドット。→ 正解は答えの集まりだけ。2番目の手を選んだときの3D・2Dの判定と点を機械で確かめる。100点換算の合格判定も。
- **追4 保存値・評価表示が深い読みとずれる**：盤に出すエンジン値が浅い読みのまま。マンカラ・コネクトフォー。→ 完全読みできる局面は完全読み、それ以外は2つ以上の深さで同じ最善・同じ順位であること。読みの深さで最善が入れかわる局面は使わない（タフル定跡）。
- **追5 手番が主題の側でない**：定跡で、その戦法・本の側でなく相手の手を当てさせる。将棋定跡・タフル定跡。
- **追6 主題の手段で勝っていない**：答えが主題と違う勝ち方（王手でなく困毙、捕獲でなく包囲、角でなく玉座）、または導入の条件（盤の大きさ・「4方向かこまれると」など）と問題が合わない。シャンチー・タフル・ドット。
- **追7 問いかけ・ヒントの前提が盤と合わない**：「いくつかありそう」「アマゾンごとに」「2本同時に」などの数・前提が盤の事実と違う、ヒントが問題の番号で決まっていて盤を見ていない。アマゾンズ・マンカラ・タフル・シャンチー。→ 問いかけ・ヒントの数量や前提の語を盤で数えて照合。
- **追8 不正解の解説が全合法手で正しくない**：選んだ手を名指ししない・盤と逆の理由・決めつけ（「先に逃げ道をふさいだから」）・負けや取られることを言わない。アマゾンズ・チェッカー・タフル。→ 不正解の文を**全合法手**について盤の事実（取られる・詰む・引き分け・負け）と照合。
- **追9 出題の順がばらばら**：プールからランダムに引いて易→難にならない（2D・3D どちらも）。リバーシ・将棋・タフル定跡。→ 出題後の並びで⑥を確かめる。
- **追10 言葉づかい・向き**：文法の誤り（「〜なの／だから」）、駒の向きと合わない言い方（後ろに引いた手に「上げる」）、理由が「定跡どおり」だけ。将棋定跡。
- **追11 進行表示**：問題に入っても見出しに「準備 4/4」が残るなど、表示が今の段と合わない（全ゲーム共通）。→ lesson-progress.js で段ごとの見出しを確かめる。
- **追12 作業の重なり**：2つの回が同じ対象を重ねて作業（開始時に相手の PR がまだない）。タフル・マンカラ。→ 対象を決めたらすぐ、進み具合表の備考に「作業中（担当・開始時刻 JST）」と書いた最初のコミットで作業ブランチを push し、次の回は未マージの PR だけでなく origin の `lesson-loop-*`/`lesson-open-*` ブランチ（直近2時間）の作業中の印も見て、同じ対象を選ばない。
- **追13 複数手の問題で2手目以降の文が段階に合わない**：2手目・3手目の不正解やヒントが「{m}から始めれば」と1手目を前提にする・残りの手数や王の動けるマスを問題の最初の局面で言う。タフル（王を角へ逃がす・王を捕らえる）。→ 複数手の問題は、手順の**各段階の局面**で全合法手の不正解文・ヒントを作り、残りの手数・その局面の事実と照合する（go の詰碁・五目並べの勝ち手順など複数手の問題を持つ全ゲーム）。
- **追14 準備（ウォームアップ）・見本の説明が盤と合わない**：準備の「光っている駒を緑の点へ動かすと詰み」が実際は王手でない困毙勝ちなど、問題ではなく準備・見本・例の盤と説明・答えの矢印が食い違う。シャンチー「1手で詰ます」。→ 準備・見本・例の局面も①④⑧（答えが主題の手段で目的を達する・説明の語が盤の事実と合う）で機械チェックする。
- **追15 定跡の手順そのものの重なり・名前違い**：名前の違う2本の定跡が同じ手順（または一方が他方の前半と同じ）、手順がその名前の定跡として成り立たない。タフル定跡（角固めと外への展開が同一）。→ 同じゲームの全定跡の手順を対称込みで比べ、同一・前半一致を不合格にし、手順の各手が合法で名前の形（src の pat 等）に合うことを確かめる（全 /open、担当B）。
- **追16 勝率（AIの評価）を理由文のひな形にしている**：2D版の lessons.json・puzzles.json の msg が「勝率 {a}%（次善 {b}%）」「この手の勝率は {x}%」で理由を言う（盤の事実がない）。ur・senet・patolli（ほかのゲームの lessons/puzzles.json には「勝率・勝つ見込み・評価値」なし、grep で確認）。→ 理由文は盤の事実（取る・ロゼット・ゴール・次に取られる確率（出目の数え上げ））だけにし、不正解の手のどれかを事実で言えない局面は使わない。lesson-verify の各ゲームで msg を勝率の語の正規表現で検査（ur：lesson-verify-ur.js。senet・patolli は対応時に）。
- **追17 印で絞れる選択肢の中で正解が多すぎる**：盤の印（光るマス・赤い印の駒）で選ぶ駒やマスが決まると、合法手全体では正解が少なくても、印に関わる手の中では大半が正解（壁のすき間に矢を撃つ手13中11、赤いアマゾンの手92中63）。アマゾンズ s_wall・s_escape・s_trap。→ ③を印に関わる手の中でも確かめる（印の駒の手の正解は半分以下・不正解3以上、印のマスに撃つ手の正解は4分の3以下・不正解3以上、印の駒のとなりにふれる不正解3以上）。
- **追18 採点の条件（数のしきい値）を言っていない**：正解の条件に「となりの空き4マス以上」などのしきい値があるのに、3D の導入・問いかけで言っていない（2D は言っている）。アマゾンズ s_escape。→ 採点の条件に数があるときは、3D・2D の導入か問いかけにその数があることを機械で確かめる。
