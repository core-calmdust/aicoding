# アマゾンズ（amazons/）仕様

URL: https://core-calmdust.github.io/aicoding/amazons/ ／ トップは「囲碁」の前（cat: line、also: chess、定番タグ、BETA）。テーマ色 #3f8a5c（ジャングルグリーン、アクセント #d6ec86）。

## ルール（10×10、標準ルールのみ）
- 白のアマゾン a4・d1・g1・j4、黒 a7・d10・g10・j7。白が先手。
- 1手＝アマゾン1体をクイーンのように動かす（縦横斜め・何マスでも・何も飛び越えない）＋着いたマスから同じ動きで矢を放つ（元いたマスにも撃てる）。矢のマスは最後まで使えない。
- 自分の番にどのアマゾンも動けない側の負け。引き分けはない（引分提案なし）。
- 出典（2026-11 確認）：Wikipedia「Game of the Amazons」（考案 Walter Zamkauskas、アルゼンチン 1988年、初出はアルゼンチンのパズル雑誌 El Acertijo 1992年12月、英訳 1994年、コンピューター・オリンピアードの種目、簡単な終盤でもNP困難）。
- 名称：スペイン語の「El Juego de las Amazonas」は Ediciones de Mente の商標なので使わない（各言語の表記は「Amazons／アマゾンズ」と各言語の一般名）。ルール自体の実装は自由。

## エンジン（engine.js、純JS、Web Worker）
- 手 m = from + 128×to + 16384×arrow。表記「d1-d7/g7」。Pos は play / unplay（探索は複製しない）。
- 評価（約100＝陣地1マス）：Lieberum の項（クイーン距離・キング距離の陣地 t1/t2、位置項 c1/c2、盤の開き具合 w で重み付け）＋各アマゾンの自由度（動けるマスが少ないほど減点）。
- 候補手は2段階：全クイーン移動を評価 → 上位だけ全ての矢を評価（`cands`）。αβ（PVS・置換表）で残り深さごとに上位 K 手だけ読む（K=8〜10）。
- 23段階（Lv. 表記）：Lv.1〜8 は1手読み＋ノイズ（弱い段ほど見るクイーン移動も少ない）、Lv.9〜18 は評価する局面数の予算（LEVELS の `nk`＝千局面、2千〜7.5万）、Lv.19・20 は 1.5秒／3秒、最上位 Lv.21〜23 は 6・12・20秒（MCTS の組のスレッド、レート戦も。スレッド数の既定は性能コアまで＝下の「MCTS」。1スレッドのときはその時間で1スレッド）。**Lv.19〜23 は 2026-11-10 から MCTS**（下の「MCTS」）。RT_LV（レート戦の基準値）は作業機での短い対戦からの仮の値（Lv.19〜23 は αβ のときの値 +200＝2170・2240・2300・2350・2390 の仮置き。ユーザーの Mac で測り直す）。
- 高速化（2026-11-10）：評価の距離計算を 12×12 の番兵つき盤で行う（範囲チェック・線の表なし）、クイーン距離の幅優先で「もっと近いマスに当たったらその先は打ち切り」、盤が分かれたら（w = 0）キング距離を測らない、探索の候補手リストをキャッシュ（反復深化で同じ局面の候補を作り直さない、`CC`）。値は前の版と全局面で一致（評価・陣地）。作業機で評価 約1.5倍、同じ時間の局面数 約1.5〜2倍。
- WebAssembly（2026-11-10）：評価と候補手リスト（全クイーン移動の評価 → 上位の全部の矢）を core.c に。距離は 10×11 のビットボード（列10が番兵）で層ごとに求め、「白が i 手・黒が j 手で届く空きマスの数」の表から決まった順で足す（engine.js の JS 版 `fromCounts` も同じ式・同じ順なので値は完全に一致。`node tools/check_wasm.js` で評価・候補・探索を照合）。`tools/build.sh` が core-wasm.js（base64）を作り、ワーカーと Node は同期で読み込む（ページ本体は JS のまま）。作業機で同じ時間の評価数 約8倍（2秒で深さ5→6、ブラウザの Lv.19 で 16万→126万局面・深さ5→7）。局面数で決める Lv.9〜18 の手は変わらない（速くなるだけ）。時間で考える Lv.19〜23 は強くなったので RT_LV の見直しが要る。
- マルチスレッド（shared/mtsplit.js、コナネと同じ方式）：エンジンは `mtPlan`／`mtV`／`mtKids`／`mtFin`／`mtpv`。最善手はルートの候補（16手）と本筋（残り深さ4以上、`splitMin: 4`）を YBW で分担、解析は候補を全幅で分け合う。分離できたページ（`sw.js`、Document-Isolation-Policy）では置換表を共有（shared/mttt.js。手は21ビットなので16ビット＋追加部16ビットに分けて入れる）。スレッドの「局面数」は評価の回数。時間で考える Lv.19〜23・分析・ヒント・コーチ・検討ボックスがスレッドで読む。Lv.1〜18 は1スレッド。
- 計測ページ `amazons/bench.html`（2026-11-10、`bench-all.html` の一覧にも）：本編と同じ `MTSplit.pool`（`engine.js` の URL も app.js の `ENGINE_URL` と同じ、Worker 内で core-wasm.js）で、1・2・4・8・性能コア数・論理コア数スレッド。局面は Lv.9 対 Lv.10 の2局（固定の乱数）の10・20・30・40手目の8局面（局面数で決めるレベルなので JS／WASM のどちらでも同じ手）。最善手（深さ固定：軽い6・ふつう8・重い9）の時間・1スレッド比（合計と局面ごとの幾何平均）・nps・1スレッドと一致、解析（1・2・4秒で読めた深さ）を共有（YBW）と非共有で。1行目に `core wasm`／`core js`。作業機（共用2コア、軽い）：2スレッドで最善手 約1.5倍・一致 8/8、`core wasm`。
- **手の空いたワーカーの手伝い（2026-11-10、`shared/mtsplit.js` の共有モード、addendum「YBW の手の空いたワーカーの手伝い」）**：仕事のないワーカーが走っている仕事の後半の子（候補）を先に読んで共有の置換表に入れる。歩調合わせのシミュレーション（`shared/tools/mtstep.js amazons`、深さ6・4局面）：2/4/8スレッド ×1.65/2.34/2.84（busy 95/91/67%）→ ×1.55/2.36/3.69（98/98/95%）。エンジンは変えていない（手伝いの候補は `mtKids` の10手。深さ2・3の節点では探索が8・9手しか見ないので最後の1〜2手の手伝いは無駄になりうる）。計測ページに `kn`・`b`・`busy`、`?help=0` で手伝いなし。
- PRO モード（shared/proset.js の ladder）：読みの上限（時間・深さ・局面数）・スレッド数・ばらつき・**探索の方式**（MCTS／αβ、14言語。既定は Lv.19〜23 が MCTS、ほかは αβ。深さの上限は常に αβ）。
- 振り返りの分析は実際に指した手を `extra` で必ず評価に含める（候補に入らない手も判定できるように）。

## MCTS（2026-11-10、ユーザー決定「強い Amazons プログラムの MCTS＋評価関数を作り、αβ と対局で比べて強い方を採用」）
- 手本：Invader-MC（Lorentz「Amazons Discover Monte-Carlo」CG 2008、プレイアウトを数手で打ち切って評価関数で勝率）、Kloetzer・Iida・Bouzy「The Monte-Carlo Approach in Amazons」（2007）、MCTS-EPT と implicit minimax backups（Lanctot ほか 2014、Lorentz 2016「Using evaluation functions in MCTS」）。強い Amazons プログラムは MCTS＋評価関数（打ち切ったプレイアウト・評価での候補の事前絞り込み・評価の事前分布・プログレッシブ・ワイドニング）が主流。
- 実装（core.c の後半、`mcts_*`。評価と候補手は αβ と同じ `ev`／`cand`）：
  - 1回の訪問＝葉を1つ展開：`cand`（全クイーン移動を評価 → 上位 QK=10 に全部の矢）の上位 K=24 手を子に（根は QK 20・K 48）。子の事前値 p = σ((評価 − 偏り) / S)、S=400（約4マス）。1回の展開は評価 約200〜400回＝αβ の葉（残り深さ1の候補リスト）と同じ単位。
  - **手番の偏りの補正**：手を指した直後の評価は指した側に寄る（中盤で約3マス。最善手の評価も、それへの最善の応手の評価もプラス）。深さの違う葉が混ざる MCTS ではこれが偶数・奇数手の偏りになるので、葉の値は「その局面の評価」と「最善の応手の評価」の平均（(sc − 応手) / 2：1手と2手の平均で偏りが消える）、事前値はこの探索で見た偏りの平均 (sc + 応手) / 2 を引く（最初は 300）。
  - 選択：(1 − A)·(w + NP·p)/(n + NP) + A·mm + C·√(ln N / (n+1))、A=0.3（implicit minimax の値 mm＝最善の子の mm の裏返し、戻るときに更新）、NP=2、C=0.25。プログレッシブ・ワイドニング：p の順の先頭 PWA + PWK·N^PWB（3 + √N）手だけ。相手が動けなくなる手は証明済みの勝ち（すぐ選ぶ）、候補が全部そろっている（全クイーン移動 ≤ QK かつ全部の手 ≤ K）節点で全部の子が負けなら負け。
  - プレイアウト（PO 手の乱数の手のあと評価、`po`／`pom`）も入れられるが既定は 0（作業機の対局で効かなかった。下の表）。
  - 木の大きさ：1スレッドは最大 400万ノード（128MB、ワーカーのメモリを必要なだけ増やす `mcts_alloc`）、スレッドは 8コア以上かつメモリ 8GB 以上で 1,600万（512MB）、8コア以上で 800万（256MB）、それ未満 400万（engine.js の `?mt=1` の `maxNodes`）。必要な大きさは「この探索で使う時間 × スレッド数 × 1ms・1スレッドあたりのノード数（`MC_RATE`、最初 120、探索ごとに実測で更新。置き場の半分を超えた探索は実測の2倍）× 1.3」（2026-11-10 から。それまでは 1ms・1スレッド 115 ノードの決め打ち × ページの論理コア数で、上限 400万）。半分を超えたら展開のしきい値を上げ（1・2・4・8・32 訪問）、96% で止める。
  - 決定性：乱数の種（`seed`）と訪問数・評価数の上限が同じなら同じ木（`node tools/check_wasm.js` で確認）。時間の上限・スレッドでは再現しない。
- マルチスレッド（`core_mt.wasm`＝同じ core.c を `-DMT`、`tools/build.sh`）：囲碁・ヘックスと同じ **1本の木を全スレッドで育てる tree-parallel**（降りるときに子へ virtual loss 1、葉の展開は1スレッドだけ＝`exp` 0→2→1 の compare-exchange、ノードは原子的なカウンタで確保、盤・作業領域はスレッドごと `TLS`）。主スレッド＝`engine.js?v=6&mt=1`（`mcts_run` が木を開閉し、補助が全員出るのを待ってから読む）、補助＝`mt-helper.js`（`mt_help`）。ページは `shared/mtengine.js` の `MTEngine.use`（app.js `MCP`、分離できたページだけ。αβ の `MTSplit` とは別の組）。1回の訪問が約0.2〜0.5ミリ秒（評価 100〜400回。ヘックスのプレイアウト約6µsの数十倍）なので、addendum の⑥（根付近の書き込みの取り合い）は起きにくく、まとめ書きはしていない（共有のカウンタはキャッシュライン1本ずつ）。評価数・訪問数の上限は全スレッドの合計。
- 本編：**Lv.19〜23 を MCTS に**（`LEVELS` の `mc: 1`、レート戦も）。スレッドがあれば MCTS の組で、なければ1スレッド（core-wasm.js）。**スレッド数の既定は性能コアまで**（2026-11-10、app.js `mcThreads()`＝`ProSet.defThreads()`＝`MTEngine.perfThreads()`、M4 Pro で 10。ほかのゲームの時間で考えるレベル（#1299）と同じ。レベル対局・レート戦・コーチの深読み・PRO の既定（Lv.19〜23）。αβ のレベル・解析は今までどおり自動の数＝最大8）。コーチの深読み（Lv.19＝1.5秒）も MCTS。Lv.1〜18（1スレッドの局面数のレベル）・分析・ヒント・形勢・振り返り・検討ボックスは αβ のまま（全部の候補の値が要る。αβ の解析は候補ごとに同じ深さの値を出す）。
- 比較（作業機、共用2コア・負荷高。時間はプロセスの CPU 時間：`tools/mcts_match.js` が `Date.now` と core の `now()` を CPU 時間にする。序盤2手は上位10候補からランダム、同じ序盤を先後入れ替えて2局、盤が分かれて陣地差3以上は判定）：
  - 評価数をそろえて（Lv.15 相当、1手 2.4万評価）：MCTS 44勝16敗（73%、約 +176 Elo）。CPU 時間は MCTS 45ms／αβ 50ms（MCTS のほうが少ない）。
  - CPU 時間 0.5秒／手：MCTS 33勝7敗（82.5%、約 +270 Elo）。1.5秒／手（Lv.19 の時間）：MCTS 15勝1敗（94%）。どちらも MCTS の使った CPU 時間のほうが少し短い（0.47／0.50秒、1.30／1.46秒）。
  - → **採用**：同じ時間で明確に強いので、時間で考える Lv.19〜23 を MCTS に切り替えた（評価数で決める Lv.9〜18 でも MCTS が強い（上の 73%）が、1スレッドの既存レベルは変えない決定なので αβ のまま）。RT_LV の Lv.19〜23 は +200 の仮置き（0.5秒で +270、1.5秒でもっと大きいが局数が少ない）。
  - MCTS の調整（評価数 2.4万、MCTS 同士、各50局、既定との比）：プレイアウト4手（`po=4`）48%、implicit minimax なし（`a=0`）38%（−85 Elo）、強め（`a=0.6`）38%、K=16 50%、C=0.1 52%、S=250 48%、S=650 40%。→ 既定（PO 0・A 0.3・K 24・C 0.25・S 400）のまま。
  - スレッド（`tools/mt_node.js match`：Node の worker_threads で本編と同じ形、2コアに8スレッド＝時分割で、木の上には常に何本もの読みが同時に走る）：8スレッド（合計1,500訪問）対1スレッド（1,500訪問）13勝11敗（54%）＝同じ訪問数で木の並列化による弱化は見えない。`tools/mt_node.js check`：ルートの子の訪問数の合計 ÷ 訪問数は 1・2・4スレッドとも 1.0000、CPU 時間あたりの訪問数はスレッド数で変わらない（プロセスの CPU 時間で）。
- 計測ページ `amazons/bench.html` に MCTS の表と「測るもの」（両方／αβ／MCTS）。本編と同じ `core_mt.wasm` の組。**主の指標は評価/s（全スレッドの評価数 ÷ 時間）の1スレッド比と効率**、ほかに「1スレッドで16倍の時間読んだ手との一致」「1スレッドとの一致」、参考に visits/s と「評価なしの訪問」の割合（`core.c` の `mcts_vk`：0 展開、1 証明済みの節点、2 置き場が半分を超えて展開を待つ葉、3 ほかのスレッドが展開中・置き場が満杯、4 深さの上限、5（1 のうち）窓の子が全部負けで負けの子へ）。1行ごとの局面の行にも評価数・訪問数・待ち・証明済みの割合。見込み 軽い3・ふつう6・重い12分（`bench-all.html` の見込みは 14分に）。作業機（共用2コア・負荷高、headless Chrome、軽い）：2スレッド 評価/s ×1.30、評価なしの訪問 1%。
- **スレッド数と visits/s の超線形の点検（2026-11-10）**：ユーザーの Mac（M4 Pro、性能10＋効率4）の bench.html（ふつう、2秒）で評価/s は 2/4/8/10/14スレッド ×2.0/3.8/6.6/7.5/7.9 と素直に伸び、visits/s だけ ×2.24/9.05/51.7/65/77 と超線形、「1スレッド×4倍の時間との一致」はスレッド数によらず 5〜6/8。
  - 原因（`mcts_vk` で数えて確認）：**木の置き場が半分を超えたあとの「展開を待つ葉」への安い訪問**（評価なしで葉の値を戻すだけ）。証明済み（読み切った）節点への訪問ではない（作業機の8局面で 0%）。当時の置き場はページの論理コア数（14）× 2秒から見積もった約320万ノードで、8スレッド以上だと2秒で半分を超え、30・40手目では訪問の 80〜95% がこの待ち（作業機の1スレッド・置き場23万でも同じ形：30・40手目で待ち 94%、評価/訪問 3〜5、展開のときは 100〜200）。96% に達すると時間が残っていても止まる。visits/s はこの安い訪問を数えるので超線形に見えた。
  - 解決済みの子へ繰り返し降りる無駄：選択は証明済みの負けの子を飛ばし、勝ちの子があれば親がすでに証明済み（そこで止まる）。窓の子が全部負けのとき（候補が全部そろっていないので親は負けと証明できない）だけ負けの子へ降りる（`mcts_vk` 5）が、作業機の8局面では 0%。virtual loss は子の n に足して戻りで引くだけで、証明済みの子に集中する形はない。→ 直すところはなかった。
  - 直したこと：置き場の見積もり（engine.js `mcts`）を「この仕事のスレッド数（`mtThreads`）× 実測の 1ms・1スレッドあたりのノード数」に、上限を 1スレッド 400万（128MB）・スレッドは 8コア以上かつメモリ 8GB 以上（`deviceMemory`、Safari は 10コア以上）で 1,600万（512MB）、8コア以上で 800万、ほかは 400万に。置き場を大きくし直すときはメモリの末尾にあるので前の置き場ごと伸ばす（`mcts_alloc`、以前は新しく取り直していた）。Lv.23（20秒）を10スレッドで読むと必要なのは数千万ノードなので、それでも途中で満ちて止まりうる（ユーザーの Mac で Lv.23 の実際の思考時間を見る）。
  - 一致の指標：比べる相手（1スレッド×4倍）は 8スレッド以上の2秒より評価数が少なく、弱い相手との一致なので伸びが見えなかった。→ **1スレッドで16倍の時間**（14スレッドの約2倍の評価数）に変えた。
  - 同じ実時間なら多スレッドが強いか（作業機は共用2コアで実時間では比べられないので、評価数で代用：Mac の評価/s の伸び 4スレッド ×3.8 に合わせて、4スレッドに1スレッドの3.8倍の評価数。`node tools/mt_node.js match 4 nk=228 10 nk=60`）：**4スレッド（22.8万評価）対1スレッド（6万評価）17勝3敗（85%）**。同じ評価数（どちらも24万）では4スレッド 9勝11敗（45%）＝木の並列化による弱化は小さい（誤差の範囲）。→ スレッドを増やすほど同じ時間で強い。
  - 置き場が満ちたときの強さ（`tools/mcts_match.js` の `pool=`、1スレッド・0.6秒、`mcts_limit` で使う置き場を絞る）：置き場 100万 対 3,000：16勝0敗（3,000 の側は満ちてすぐ止まり、1手 平均40ms しか読まない）、100万 対 8,000：6勝6敗（8,000 の側は 1手 平均95ms で止まるのに互角。局数が少ない）。極端に小さいと明確に弱いが、「途中で満ちる」程度の差は作業機の局数では見えなかった。大きくした置き場で弱くなる理由はない（時間いっぱい読み、待ちの訪問が減るだけ）。

## 画面（konane/ から派生、共通部品はそのまま）
