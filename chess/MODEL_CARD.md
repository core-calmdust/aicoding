# Model Card: Chess evaluation (`nnue.bin.gz`)

チェスのAIが局面の良し悪しを判断するための評価関数（学習済み重み）です。
探索エンジン `engine.c`（WebAssembly にビルドした `engine.wasm`）と組み合わせて、ブラウザ上（Web Worker）で動作します。

- **ゲーム**: https://core-calmdust.github.io/aicoding/chess/
- **作成**: core-calmdust（AIコーディングによる制作）
- **バージョン**: v2（2026-11-09、ユーザーの Mac で学習し直した版。v1 は 2026-10-19）

## モデル概要

| 項目 | 内容 |
|---|---|
| 種類 | NNUE（効率的に差分更新できるニューラルネット） |
| 構造 | (768 → 384) × 2視点 → 1、活性化 SCReLU、出力は残り駒数で8つに分岐 |
| 入力 | 駒の種類（6）× 色（2）× 升（64）。手番側の視点と相手側の視点（盤を上下反転）の2つ |
| 出力 | 手番側から見た評価値（センチポーン相当。勝率 ≒ sigmoid(評価値/400)） |
| パラメータ数 | 約30万（第1層は Int16 で ×255、出力層は Int16 で ×64 に量子化） |
| ファイルサイズ | 約600KB（gzip圧縮後 約390KB） |

### king buckets（玉の位置で入力を分ける、HalfKA 風）— 予定（2026-11-09 準備済み、本番は未反映）

ユーザーの判断（2026-11-09）：中間層は 384 のまま、第1層を自玉の位置の区分ごとに持つ方式で強くする（見込み 同じ持ち時間で +30〜60 Elo）。エンジン・学習器・自動の手順（`KB=4 tools/nnue/run.sh`、`tools/TRAIN.md` の「9.」）を用意し、ユーザーの Mac で学習・対局してから採用を決めます。**本番の `nnue.bin.gz`・`engine.wasm`・`engine_mt.wasm` は変えていません。**

| 項目 | 内容 |
|---|---|
| 区分（既定 4） | 自分の側から見た自玉の升で：1・2段目の f〜h筋 ／ 1・2段目の a〜c筋 ／ 1・2段目の d・e筋 ／ 3段目より前。中盤のよくある玉の動き（Kg1・Kh1・Kg2・Kf1）は同じ区分なので、計算し直しが少ない。8区分（1段目と2段目を分け、前を2つ）・16区分（1段目は筋ごと）・32区分（全升、左右反転あり）も選べる（`engine.c` の `NN_KB` は読める区分数の上限、ネットのファイルが実際の区分数を持つ） |
| ファイル | W1（区分×768×384）・B1・W2・B2 の後ろに16バイトの末尾（`CKB1`・区分数・384・0）。区分なしの v1・v2 には末尾がなく、そのまま読める。4区分 2,372,400バイト（gzip 後 約1.5MB）、8区分 4,731,696バイト（約3.1MB）。今は 602,912バイト（約0.39MB） |
| 学習の出発点 | v2 を全区分に写す（4・8・16 は左右反転なしなので、出発点は v2 と完全に同じ評価。学習器の検証損失も v2 と同じ値から始まることを確認） |
| エンジン | 玉が同じ区分の中で動いたときは差分更新。区分が変わったときはその視点だけ、区分ごとに覚えておいた前回の計算結果からの差分で作り直す（Finny テーブル。int16 の和なので結果は全部計算と同じ）。差分更新は視点ごとに遅延 |
| 確認（この作業環境） | ①区分なしの v2 で、新しい `engine.c` の通常版・マルチスレッド版の wasm とネイティブ版が今の配信版と同じ評価・同じ探索（12局面×30万局面の最善手・評価値・深さ・局面数が一致）②v2 を4・8区分に写したネットで、区分の仕組みを通っても v2 とまったく同じ探索（差分更新の誤りがあれば木が変わる）③学習器（Python の整数計算）とエンジンの評価が4・8・16・32区分で一致、色を入れ替えた局面で同じ評価④全部計算と毎回照合するテスト版（`-DNN_VERIFY`）で自己対局・対局が通る⑤小さいデータ（自己対局34万局面）で学習が収束（v2 からの学習で検証損失 0.00425 → 0.00395、区分なしの同じ学習は 0.00393）し、一致確認と対局まで `run.sh` が自動で回る |
| 速さ（wasm SIMD、Node.js、24局面×15万局面×4回、同じ探索になるネットで交互に） | 今（区分なし）100% → 4区分 **約97%**、8区分 約95%。ネイティブ版ではほぼ同じ |
| wasm の大きさ | 通常版のメモリ 401 → 444ページ（8区分 480）。マルチスレッド版の宣言 1041 → 1069ページ（8区分 1105。プールの `initial` 1152 のままで足りる）、スレッドごとの TLS 412KB → 426KB |

- 採用するとき（Claude 側）：区分に対応した `engine.c` で `engine.wasm`・`engine_mt.wasm` を作り直し、ページの読み込みを `nn_load(長さ)` に（今の `nn_size()` は区分なしの大きさのまま。区分なしのネットはこれまでどおり `nn_ptr()` に入れて `nn_enable(1)` で読める）、キャッシュ番号、ブラウザでの一致確認、`nnue.bin.gz` の差し替え、レベルの見直し。
- 見つけたこと：`engine.wasm` のスタックがリンカの既定の 64KB で、深い探索ではそれを超えて静的なデータの領域に入っていた（配信中の版は、試した局面では大きなスタックの版と同じ結果）。`tools/build-wasm.sh` を 1MB・先頭配置（あふれたら止まる）に直した。次に `engine.wasm` を作り直すときに入る（マルチスレッド版はスレッドごとに 2MB の枠があるので関係なし）。

## 学習データ（v1）

[Lichess の評価済み局面データベース](https://database.lichess.org/#evals)（`lichess_db_eval.jsonl.zst`、**CC0**）の先頭から約1億2千万局面を使いました。各局面には Lichess ユーザーのクラウド解析（Stockfish）による評価値が付いています。

- 最も深い解析の最善手の評価値を教師値にしました（±3000で打ち切り、詰みは±3000）。
- 王手がかかっている局面と、最善手が駒取り・昇格の局面は除外しました（静かな局面のみ）。
- 解析の深さが12未満の局面は除外しました。
- 条件を満たした約1億800万局面すべてで学習しました。

## 学習方法（v1）

- 損失: 予測勝率 sigmoid(出力) と教師値 sigmoid(評価値/400) の二乗誤差。
- 最適化: Adam、ミニバッチ16,384、8エポック（後半で学習率を 0.3倍・0.1倍に減衰）。
- 重みは ±1.98 に制限して量子化しても精度が落ちないようにしています。
- 学習器は C で自作しました（`engine.c` と同じ特徴量の定義）。

## 高速化（2026-11）
- NNUE の差分更新と評価を WebAssembly SIMD で明示的にベクトル化（`tools/build-wasm.sh`）。計算結果は従来と完全に同じで、同じ探索ノード数を約1.5倍の速さで読みます（8局面×30万ノード: 4.2秒 → 2.8秒）。
- 時間で区切るレベル18〜20は、同じ持ち時間でより深く読めるようになりました。

## 最強解析（複数スレッド、2026-11）
- `pro/`：PC の複数の CPU コアで同時に読む解析ページ。対局ページの「最強解析」ボタンから、今の局面を新しいタブで開きます。
- エンジンは同じ `engine.c` を `-DMT` で作った `engine_mt.wasm`（`tools/build-wasm-mt.sh`）。共有メモリの上で複数スレッドが同じ局面を読む Lazy SMP です。
  置換表・NNUE の重み・各種の表を共有し、局面・手順・履歴・キラー手などはスレッドごと（`TLS`）。補助スレッドは1つおきに1手深い深さから読み始めます。
  通常版の `engine.wasm` はこの変更で1バイトも変わりません（`TLS` は通常版では空）。
- 共有メモリ（SharedArrayBuffer）にはページの「クロスオリジン分離」が必要です。GitHub Pages ではヘッダーを設定できないため、
  `pro/coi-sw.js`（Service Worker）が `pro/` の中だけ COOP / COEP を付けます。対局ページ（オンライン対戦・ログイン）は対象外で影響しません。
  分離できないブラウザでは、通常のエンジン（1スレッド、レベル20）で動きます。
- 確認：2スレッド対1スレッド、1手0.3秒、ランダム4手の序盤から先後入れ替えで40局 → +13 =23 −4（得点率0.613、約 +80 Elo。局数が少ないので幅は大きい）。
  同じ深さまでの時間は 2スレッドで約1.24倍速。1スレッドでは通常版と同じ速さ。
- 探索をメッセージで分担する方式（共有メモリなし。候補手の分担、PV分割）も試しましたが、Worker ごとに置換表が分かれるため速くなりませんでした。


## 本編のマルチスレッド（2026-11-08）
- 対局ページでも `engine_mt.wasm` の複数スレッドを使います（共通部品 `shared/mtengine.js`・`shared/mt-sw.js`、addendum「本編のマルチスレッド」）。`sw.js` がページに `Document-Isolation-Policy` を付け、Chrome / Edge（PC）は COOP なしで分離（ログイン・オンライン対戦はそのまま）。Safari・Firefox などはオプション「マルチスレッド」で COOP / COEP モードに切り替え（その間ログイン・オンライン対戦は停止）。スマホはオンにするまで1スレッド。
- 主スレッドは `engine.js?…&mt=1`（同じワーカー API、共有メモリの `engine_mt.wasm`）、補助は `mt-helper.js`（同じ局面を `think(0,0,64,0)` で読み続ける）。
- 対象：分析（`analyze`）・ヒント・コーチの深い読み（Lv.21 相当、約1.25秒）・検討ボックス（`mpvLoop`）、AI の Lv.18〜25（時間で考えるレベル。2026-11-08 のユーザー判断でレート戦も、端末差は許容）。Lv.13〜17（局面数で決めるレベル）は通常の `engine.wasm`・1スレッドのまま。
- 計測（この作業環境：2 vCPU の Linux・headless Chromium 153。独立した2ワーカーでも合計速度は1.37倍どまりのため、深さの伸びはほぼ出ない）：旧 Lv.20（4秒）の1手で 1スレッド 約60万 nps → 2スレッド合計 約79万 nps（深さは同じ18）。同じ深さまでの時間はほぼ同じ。複数コアの PC での効果は上の最強解析の計測（2スレッドで約1.24倍速、約 +80 Elo）が目安です。

### マルチスレッドの見直し（2026-11-09、チェッカー・モリス・タフルの置換表の件を受けた点検）
- **見つかった問題**（モリス・タフルと同じ種類）：①共有の置換表が「1キー1項目」の24バイトの構造体で、欄（キー・値・静的評価・深さ・種類・手）を順に書いていた。2つのスレッドが同時に同じ所へ書くと、ある局面のキーに別の局面の値・深さ・上下限が付いた項目ができ、それを正しい値として使いうる。②置き換えは本探索で常に上書き、静止探索も別の局面の項目を上書きしていたので、スレッド数倍の浅い項目が深い項目を追い出す（表を Mac 並みに埋めた条件では 2・4スレッドでも**速くならなかった**：×0.86／×0.95）。③主スレッドは自分の結果だけで答えていた。④補助の1つおきに1手深く始める「深さのずらし」。
- **確認して問題なかったもの**：停止（`gStop`・`ctl[0]`）、局面・ヒストリー・キラー手などはスレッドごと（`TLS`）、置換表・評価関数・表は共有、表の年齢は主スレッドだけが進める、補助は主スレッドが終われば止まる（`mt-helper.js` は `think(0,0,64,0)` を繰り返す）、プールの `initial`（512 ≥ 宣言 401。新しい表では下のとおり上げた）、ネットの有効フラグは共有。
- **変更（`engine_mt.wasm` だけ。通常版 `engine.wasm` は同じ設定のビルドで cmp 一致＝1スレッドのレベルの指し手は不変）**：
