# Model Card: Chess evaluation (`nnue.bin.gz`)

チェスのAIが局面の良し悪しを判断するための評価関数（学習済み重み）です。
探索エンジン `engine.c`（WebAssembly にビルドした `engine.wasm`）と組み合わせて、ブラウザ上（Web Worker）で動作します。

- **ゲーム**: https://core-calmdust.github.io/aicoding/chess/
- **作成**: core-calmdust（AIコーディングによる制作）
- **バージョン**: v1（2026-10-19）

## モデル概要

| 項目 | 内容 |
|---|---|
| 種類 | NNUE（効率的に差分更新できるニューラルネット） |
| 構造 | (768 → 384) × 2視点 → 1、活性化 SCReLU、出力は残り駒数で8つに分岐 |
| 入力 | 駒の種類（6）× 色（2）× 升（64）。手番側の視点と相手側の視点（盤を上下反転）の2つ |
| 出力 | 手番側から見た評価値（センチポーン相当。勝率 ≒ sigmoid(評価値/400)） |
| パラメータ数 | 約30万（第1層は Int16 で ×255、出力層は Int16 で ×64 に量子化） |
| ファイルサイズ | 約600KB（gzip圧縮後 約380KB） |

## 学習データ

[Lichess の評価済み局面データベース](https://database.lichess.org/#evals)（`lichess_db_eval.jsonl.zst`、**CC0**）の先頭から約1億2千万局面を使いました。各局面には Lichess ユーザーのクラウド解析（Stockfish）による評価値が付いています。

- 最も深い解析の最善手の評価値を教師値にしました（±3000で打ち切り、詰みは±3000）。
- 王手がかかっている局面と、最善手が駒取り・昇格の局面は除外しました（静かな局面のみ）。
- 解析の深さが12未満の局面は除外しました。
- 条件を満たした約1億800万局面すべてで学習しました。

## 学習方法

- 損失: 予測勝率 sigmoid(出力) と教師値 sigmoid(評価値/400) の二乗誤差。
- 最適化: Adam、ミニバッチ16,384、8エポック（後半で学習率を 0.3倍・0.1倍に減衰）。
- 重みは ±1.98 に制限して量子化しても精度が落ちないようにしています。
- 学習器は C で自作しました（`engine.c` と同じ特徴量の定義）。

## 高速化（2026-11）
- NNUE の差分更新と評価を WebAssembly SIMD で明示的にベクトル化（`tools/build-wasm.sh`）。計算結果は従来と完全に同じで、同じ探索ノード数を約1.5倍の速さで読みます（8局面×30万ノード: 4.2秒 → 2.8秒）。
- 時間で区切るレベル18〜20は、同じ持ち時間でより深く読めるようになりました。

## 最強解析（複数スレッド、2026-11）
- `pro/`：PC の複数の CPU コアで同時に読む解析ページ。対局ページの「最強解析」ボタンから、今の局面を新しいタブで開きます。
- エンジンは同じ `engine.c` を `-DMT` で作った `engine_mt.wasm`（`tools/build-wasm-mt.sh`）。共有メモリの上で複数スレッドが同じ局面を読む Lazy SMP です。
  置換表・NNUE の重み・各種の表を共有し、局面・手順・履歴・キラー手などはスレッドごと（`TLS`）。補助スレッドは1つおきに1手深い深さから読み始めます。
  通常版の `engine.wasm` はこの変更で1バイトも変わりません（`TLS` は通常版では空）。
- 共有メモリ（SharedArrayBuffer）にはページの「クロスオリジン分離」が必要です。GitHub Pages ではヘッダーを設定できないため、
  `pro/coi-sw.js`（Service Worker）が `pro/` の中だけ COOP / COEP を付けます。対局ページ（オンライン対戦・ログイン）は対象外で影響しません。
  分離できないブラウザでは、通常のエンジン（1スレッド、レベル20）で動きます。
- 確認：2スレッド対1スレッド、1手0.3秒、ランダム4手の序盤から先後入れ替えで40局 → +13 =23 −4（得点率0.613、約 +80 Elo。局数が少ないので幅は大きい）。
  同じ深さまでの時間は 2スレッドで約1.24倍速。1スレッドでは通常版と同じ速さ。
- 探索をメッセージで分担する方式（共有メモリなし。候補手の分担、PV分割）も試しましたが、Worker ごとに置換表が分かれるため速くなりませんでした。


## 本編のマルチスレッド（2026-11-08）
- 対局ページでも `engine_mt.wasm` の複数スレッドを使います（共通部品 `shared/mtengine.js`・`shared/mt-sw.js`、addendum「本編のマルチスレッド」）。`sw.js` がページに `Document-Isolation-Policy` を付け、Chrome / Edge（PC）は COOP なしで分離（ログイン・オンライン対戦はそのまま）。Safari・Firefox などはオプション「マルチスレッド」で COOP / COEP モードに切り替え（その間ログイン・オンライン対戦は停止）。スマホはオンにするまで1スレッド。
- 主スレッドは `engine.js?…&mt=1`（同じワーカー API、共有メモリの `engine_mt.wasm`）、補助は `mt-helper.js`（同じ局面を `think(0,0,64,0)` で読み続ける）。
- 対象：分析（`analyze`）・ヒント・コーチの深い読み（Lv.21 相当、約1.25秒）・検討ボックス（`mpvLoop`）、AI の Lv.18〜25（時間で考えるレベル。2026-11-08 のユーザー判断でレート戦も、端末差は許容）。Lv.13〜17（局面数で決めるレベル）は通常の `engine.wasm`・1スレッドのまま。
- 計測（この作業環境：2 vCPU の Linux・headless Chromium 153。独立した2ワーカーでも合計速度は1.37倍どまりのため、深さの伸びはほぼ出ない）：旧 Lv.20（4秒）の1手で 1スレッド 約60万 nps → 2スレッド合計 約79万 nps（深さは同じ18）。同じ深さまでの時間はほぼ同じ。複数コアの PC での効果は上の最強解析の計測（2スレッドで約1.24倍速、約 +80 Elo）が目安です。

### 強さの推定（方法と結果）
1手数秒〜20秒の対局を十分な数こなすのはこの作業環境（2コアを他の作業と共用、負荷4〜9）では無理なので、隣り合うレベルに相当する「時間2倍の対局」を短い方から測り、長い方は外挿しました。
- 計測：ネイティブ版（`engine.c`）・1スレッド、**時計はプロセスの CPU 時間**（`CLOCK_PROCESS_CPUTIME_ID` に置き換えたビルド）、時間指定はページと同じ0.55倍／上限。ブラウザの1スレッド（約60万局面/秒）に局面数を合わせるため、ネイティブ版（この機械で CPU 時間あたり約100万局面/秒）にはページの時間の0.6倍を与えました。開始局面はランダム8手から評価±60cp 以内のもの、同じ局面で先後入れ替え、評価±10ポーン以上が6手続いたら判定。#1166 の計測（同じ方法、時間0.1〜0.8秒）も合わせています。

|---|---|---|---|---|---|
| Lv.18 → 19 | 0.09 → 0.18秒 | 約14万 | 24 | +13 −1 =10 | +191（+133/−95） |

- 局面数が増えるほど2倍あたりの伸びは減ります（14万で約 +180、25万で約 +140、50〜60万で約 +130、110万で約 +110。1回の2倍ごとに約10〜20ずつ減る）。この傾向で外挿すると、Lv.22 → 23（約230万局面）+85〜110、Lv.23 → 24（約450万）+70〜100、Lv.24 → 25（約900万）+55〜90。
