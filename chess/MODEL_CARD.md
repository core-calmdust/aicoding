# Model Card: Chess evaluation (`nnue.bin.gz`)

チェスのAIが局面の良し悪しを判断するための評価関数（学習済み重み）です。
探索エンジン `engine.c`（WebAssembly にビルドした `engine.wasm`）と組み合わせて、ブラウザ上（Web Worker）で動作します。

- **ゲーム**: https://core-calmdust.github.io/aicoding/chess/
- **作成**: core-calmdust（AIコーディングによる制作）
- **バージョン**: v3（2026-11-11、king buckets 4区分。v2 は 2026-11-09、v1 は 2026-10-19）

## モデル概要

| 項目 | 内容 |
|---|---|
| 種類 | NNUE（効率的に差分更新できるニューラルネット） |
| 構造 | (768 × 自玉の区分4 → 384) × 2視点 → 1、活性化 SCReLU、出力は残り駒数で8つに分岐（v3。v1・v2 は区分なしの 768 → 384） |
| 入力 | 駒の種類（6）× 色（2）× 升（64）。手番側の視点と相手側の視点（盤を上下反転）の2つ。第1層は視点ごとに自玉の位置の区分（1・2段目の f〜h筋／a〜c筋／d・e筋／3段目より前）で別の重み（king buckets、HalfKA 風） |
| 出力 | 手番側から見た評価値（センチポーン相当。勝率 ≒ sigmoid(評価値/400)） |
| パラメータ数 | 約119万（第1層 4×768×384。Int16 で ×255、出力層は Int16 で ×64 に量子化）。v2 は約30万 |
| ファイルサイズ | 2,372,400バイト（gzip圧縮後 1,577,136バイト ≒ 1.5MB）。v2 は 602,912バイト（約390KB） |

### king buckets（玉の位置で入力を分ける、HalfKA 風）— 2026-11-09 準備、2026-11-11 に4区分を v3 として採用（上の「評価関数 v3」）

ユーザーの判断（2026-11-09）：中間層は 384 のまま、第1層を自玉の位置の区分ごとに持つ方式で強くする（見込み 同じ持ち時間で +30〜60 Elo）。エンジン・学習器・自動の手順（`KB=4 tools/nnue/run.sh`、`tools/TRAIN.md` の「9.」）を用意し、ユーザーの Mac で学習・対局してから採用を決めます。（2026-11-09 の時点では本番の `nnue.bin.gz`・`engine.wasm`・`engine_mt.wasm` は変えず、2026-11-11 に反映。）

| 項目 | 内容 |
|---|---|
| 区分（既定 4） | 自分の側から見た自玉の升で：1・2段目の f〜h筋 ／ 1・2段目の a〜c筋 ／ 1・2段目の d・e筋 ／ 3段目より前。中盤のよくある玉の動き（Kg1・Kh1・Kg2・Kf1）は同じ区分なので、計算し直しが少ない。8区分（1段目と2段目を分け、前を2つ）・16区分（1段目は筋ごと）・32区分（全升、左右反転あり）も選べる（`engine.c` の `NN_KB` は読める区分数の上限、ネットのファイルが実際の区分数を持つ） |
| ファイル | W1（区分×768×384）・B1・W2・B2 の後ろに16バイトの末尾（`CKB1`・区分数・384・0）。区分なしの v1・v2 には末尾がなく、そのまま読める。4区分 2,372,400バイト（gzip 後 約1.5MB）、8区分 4,731,696バイト（約3.1MB）。今は 602,912バイト（約0.39MB） |
| 学習の出発点 | v2 を全区分に写す（4・8・16 は左右反転なしなので、出発点は v2 と完全に同じ評価。学習器の検証損失も v2 と同じ値から始まることを確認） |
| エンジン | 玉が同じ区分の中で動いたときは差分更新。区分が変わったときはその視点だけ、区分ごとに覚えておいた前回の計算結果からの差分で作り直す（Finny テーブル。int16 の和なので結果は全部計算と同じ）。差分更新は視点ごとに遅延 |
| 確認（この作業環境） | ①区分なしの v2 で、新しい `engine.c` の通常版・マルチスレッド版の wasm とネイティブ版が今の配信版と同じ評価・同じ探索（12局面×30万局面の最善手・評価値・深さ・局面数が一致）②v2 を4・8区分に写したネットで、区分の仕組みを通っても v2 とまったく同じ探索（差分更新の誤りがあれば木が変わる）③学習器（Python の整数計算）とエンジンの評価が4・8・16・32区分で一致、色を入れ替えた局面で同じ評価④全部計算と毎回照合するテスト版（`-DNN_VERIFY`）で自己対局・対局が通る⑤小さいデータ（自己対局34万局面）で学習が収束（v2 からの学習で検証損失 0.00425 → 0.00395、区分なしの同じ学習は 0.00393）し、一致確認と対局まで `run.sh` が自動で回る |
| 速さ（wasm SIMD、Node.js、24局面×15万局面×4回、同じ探索になるネットで交互に） | 今（区分なし）100% → 4区分 **約97%**、8区分 約95%。ネイティブ版ではほぼ同じ |
| wasm の大きさ | 通常版のメモリ 401 → 444ページ（8区分 480）。マルチスレッド版の宣言 1041 → 1069ページ（8区分 1105。プールの `initial` 1152 のままで足りる）、スレッドごとの TLS 412KB → 426KB |

- 採用するとき（Claude 側）：区分に対応した `engine.c` で `engine.wasm`・`engine_mt.wasm` を作り直し、ページの読み込みを `nn_load(長さ)` に（今の `nn_size()` は区分なしの大きさのまま。区分なしのネットはこれまでどおり `nn_ptr()` に入れて `nn_enable(1)` で読める）、キャッシュ番号、ブラウザでの一致確認、`nnue.bin.gz` の差し替え、レベルの見直し。
- 見つけたこと：`engine.wasm` のスタックがリンカの既定の 64KB で、深い探索ではそれを超えて静的なデータの領域に入っていた（配信中の版は、試した局面では大きなスタックの版と同じ結果）。`tools/build-wasm.sh` を 1MB・先頭配置（あふれたら止まる）に直した。次に `engine.wasm` を作り直すときに入る（マルチスレッド版はスレッドごとに 2MB の枠があるので関係なし）。

### マルチスレッドの見直し（2026-11-09、チェッカー・モリス・タフルの置換表の件を受けた点検）
- **見つかった問題**（モリス・タフルと同じ種類）：①共有の置換表が「1キー1項目」の24バイトの構造体で、欄（キー・値・静的評価・深さ・種類・手）を順に書いていた。2つのスレッドが同時に同じ所へ書くと、ある局面のキーに別の局面の値・深さ・上下限が付いた項目ができ、それを正しい値として使いうる。②置き換えは本探索で常に上書き、静止探索も別の局面の項目を上書きしていたので、スレッド数倍の浅い項目が深い項目を追い出す（表を Mac 並みに埋めた条件では 2・4スレッドでも**速くならなかった**：×0.86／×0.95）。③主スレッドは自分の結果だけで答えていた。④補助の1つおきに1手深く始める「深さのずらし」。
- **確認して問題なかったもの**：停止（`gStop`・`ctl[0]`）、局面・ヒストリー・キラー手などはスレッドごと（`TLS`）、置換表・評価関数・表は共有、表の年齢は主スレッドだけが進める、補助は主スレッドが終われば止まる（`mt-helper.js` は `think(0,0,64,0)` を繰り返す）、プールの `initial`（512 ≥ 宣言 401。新しい表では下のとおり上げた）、ネットの有効フラグは共有。
- **変更（`engine_mt.wasm` だけ。通常版 `engine.wasm` は同じ設定のビルドで cmp 一致＝1スレッドのレベルの指し手は不変）**：
  - 置換表を 4項目のバケット（64バイト）× 2^20 = 64MB（項目数 4倍）に。1項目は `{ key ^ w, w }`（w＝値・静的評価・手・深さ・種類・年齢・使用中）で、読むときに XOR で照合（壊れた項目は使わない）。置き換えは同じキー → それ以外はバケットで最も浅い／古い（前の探索なら深さ −16）項目。年齢は主スレッドが探索ごとに進める。
  - 各スレッドが終えた反復（深さ・値・手）をルートの鍵（局面・手数・除外した手）付きで共有し、主スレッドは最も深い結果で答える（同じ深さなら主スレッド、手はルートの合法手で除外していないか確かめる。候補手の検討ボックスで手を除外しているときは補助の結果を使わない）。深さの上限があるとき、補助が先に届いたら主スレッドも終える。

  - wasm の宣言が 1041 ページになったので、プールの `initial` を 1152 に（`app.js`・`pro/pro.js`・`bench.html`。512 のままだと LinkError でスレッドが起動しない）。`engine_mt.wasm?v=2`、`pro/` は `?v=3`。計測ページのため `engine.js` に `newgame`（表を空に）を足した（`?v=20261109nn2`、大百科の `atlas/games/chess.js` も同じ版）。

### マルチスレッド v2（YBW と Lazy SMP の併用、2026-11-10）

**原因（作業機の「本当に同時」のシミュレーション `tools/mtsim/`：256局面ごとに全スレッドの歩調をそろえ、置換表への書き込みは次の同期までほかのスレッドに見えない。`bench.html` と同じ12局面（A）と、乱数の種を変えた12局面×2（B・C）。1スレッドが150万局面で届く深さまでの時間、12局面の合計の比）**
- 今の Lazy SMP は 8スレッドで ×2.6（A ×2.58・B ×2.54・C ×2.68）で、Mac の ×2.53 と同じ。全スレッドが同じ根を読み、置換表だけで助け合うので、主スレッドが読む木そのものは小さくならない（同じ深さまでの時間は主の木で決まる）。
- 全部の補助を YBW（リバーシ v4.1 と同じ作り）にしても 8スレッド ×2.3〜2.8 で、Lazy SMP と変わらなかった。①補助の手の空きが 25〜39%（分割できる節が足りない）、②局面数が1スレッドの ×1.6〜2.3 に膨らむ（チェスは LMR・枝刈りが強く、カットが予想される節で2手目以降を並べて読むとほとんど無駄になる。予想カット節で分けない・分割の深さ 7 にしても ×1.6〜2.1）。補助が空いている間に根を Lazy SMP で読ませる形も、分割点に戻るのが遅れて ×2.1。

**方式（`engine_mt.wasm`・`mt-helper.js`・`pro/mt-worker.js`）**
- **補助1番だけ YBW、2番以降は今までどおり Lazy SMP**。YBW の補助は `mt_idle` で主の分割点の手を取り、主の木を直接分け合う。Lazy SMP の補助は根を自分で繰り返し読み（自分の履歴の表：`mt_lazy(1)`、その読みは分割しない）、置換表を埋め、主の深さに先に届けば主を終わらせる（今までどおり）。2スレッドでは YBW だけ。
- YBW の作りはリバーシ v4／v4.1 と同じ：最初の手を読み終えた節の残りの合法手を分割点（共有メモリに128個）に出し、主と補助が1手ずつ取って同じ枝刈り・LMR・PVS で読む。カットで分割点に停止の印（下のスレッドは時計の確認で抜ける）。持ち主は補助が抜けるまで自分の分割点の下を手伝い、待つ間は印を付けて下のスレッドに分割させる。取る手のないスレッドは読みかけの手を二度読み（先に終わった方を使う：遅いコアに止められない）。分割点の数の変数は専用のキャッシュライン。
- チェス向けの点：分割は残り深さ **7以上**、**予想カット節では分けない**（PV 節と ALL 節だけ）。補助は分割点の局面・千日手を見るための局面の鍵（最後の不可逆な手まで）・子が読む手前の手と静的評価・キラー手を写し、NNUE のアキュムレータは作り直す。主と YBW の補助は**履歴とカウンター手の表を共有**（補助が主の手の順で読むように。Lazy SMP の補助は自分の表）。
- 1スレッドは変わらない：分割は手の空いた補助がいるときだけ。通常版の `engine.wasm` は変えていない（`-DMT` なしの前処理後のソースが一致、配信中の版のまま）。`engine_mt.wasm` の1スレッドは12局面の深さ13・15で局面数・手が変更前と全一致（`tools/mtsim/wasm1.js`）、速さも同じ（誤差の内）。同じ深さでの最善手は1スレッドと 2〜14スレッドで変更前と同じだけ一致（8スレッド B・C 19/24、A 12/12）。
- wasm の宣言 1079ページ（プールの `initial` 1152 のまま）。`engine_mt.wasm?v=3`・`mt-helper.js?v=2`・`app.js`、`pro/` は `?v=4`。

## 対局設定の Pro モード（2026-11-08）
対局設定の「AIの強さ」の PRO ボタン（`shared/proset.js`、addendum「対局設定の Pro モード」）。項目：思考の制限（時間 0.1〜60 秒／深さ 1〜30／局面数 1千〜1億）、スレッド数（時間制限のときだけ、マルチスレッドがオンのとき）、定跡、手のばらつき（なし／小 25cp／大 70cp のノイズ。Lv.1〜12 の既定はそのレベルのノイズ・うっかり）、評価関数（NNUE／手作り＝`nn_enable(0)`）。変えた値は `think` の `cfg`（LEVELS と同じキー＋`hand`）で engine.js に渡す。レート戦では使わない。戦績は `ai:pro`。コンテンプト（引き分け回避）は engine.c にないので出さない。AI戦では AI は投了しないので「AIの投了」もなし。
- 先読み（2026-11-11、既定オフ、`shared/ponder.js`）：AI が指した直後から人の手番中もスレッドのプールで読む。engine.js の読み筋（`res_ptr` の [9]）の2手目（予想手）を指した後の局面を読み、予想どおりならその読みを置換表から引き継ぎ、外れても置換表は残る。AI 自身の手も同じプール（置換表）で読む。着手・待った・新規対局・終局・タブ非表示で即停止。

### 強さの推定（方法と結果）
1手数秒〜20秒の対局を十分な数こなすのはこの作業環境（2コアを他の作業と共用、負荷4〜9）では無理なので、隣り合うレベルに相当する「時間2倍の対局」を短い方から測り、長い方は外挿しました。
- 計測：ネイティブ版（`engine.c`）・1スレッド、**時計はプロセスの CPU 時間**（`CLOCK_PROCESS_CPUTIME_ID` に置き換えたビルド）、時間指定はページと同じ0.55倍／上限。ブラウザの1スレッド（約60万局面/秒）に局面数を合わせるため、ネイティブ版（この機械で CPU 時間あたり約100万局面/秒）にはページの時間の0.6倍を与えました。開始局面はランダム8手から評価±60cp 以内のもの、同じ局面で先後入れ替え、評価±10ポーン以上が6手続いたら判定。#1166 の計測（同じ方法、時間0.1〜0.8秒）も合わせています。

- **1段階あたりの推定（自己対局）**：Lv.18→19 約 +180、19→20 約 +140、20→21 約 +130（±70）、21→22 約 +110（±150、局数が少ない）、22→23 約 +95、23→24 約 +85、24→25 約 +70（外挿、±50程度）。**Lv.21 は Lv.20 より約 +130 強く、Lv.25 は Lv.20 より約 +490（誤差込みで +350〜+600）**。旧配置（1段階 +35〜55、Lv.25 は Lv.20 の +200）と比べて1段階の差は約2〜3倍です。目標の「1段階 +100〜150」は Lv.22 までは届き、Lv.23〜25 は時間を2倍にしても伸びが減るため +70〜95 程度と見込みます（20秒以内では、これ以上広げると5段階に分けられません）。
- 限界：Lv.20→21・21→22 の計測は16局・10局と少なく、区間が広い（Lv.22 以上は計測なし）。自己対局の差は人間や他のエンジンとの対局より大きく出がちです。ネイティブ版と WebAssembly 版の速さの比（0.6倍）は目安。複数コアの PC では Lv.18〜25 のすべてが同じように強くなり（2スレッドで +80 Elo 前後、上の「最強解析」）、レベル間の差は大きくは変わりません。
