# Model Card: コナネ AI（探索 v3 と学習した評価関数 `net-<盤>.bin.gz`）

コナネの AI は、探索エンジン `core.c`（WebAssembly：1スレッドの `core-wasm.js`、複数スレッドの `core_mt.wasm`）の αβ 探索に、
形勢の評価を組み合わせています。評価は今は**手作りの評価**（双方の跳べる手の数・跳べる石の数の差＋手番）で、
**学習した評価関数（盤の大きさごとの小さなネット）の仕組み**を 2026-11-20 に入れました（学習本番はこれから。下の「Mac での学習」）。

- **ゲーム**: https://core-calmdust.github.io/aicoding/konane/
- **バージョン**: 探索 v3（2026-11-20）。学習した評価：ネット未配置（`engine.js` の `NETV` がすべて空＝手作り評価）
- 仕様の詳細：`claude/konane-spec.md`「探索 v3・学習した評価の仕組み」

## 使う所
| レベル・機能 | 探索 | 評価 |
|---|---|---|
| Lv.1〜23（人が遊ぶレベル。エンジンの Lv.1〜20） | 今まで通り（深さ・局面数・時間で決まる v2 以前） | 手作り |
| 天上Ⅰ〜Ⅲ（エンジンの Lv.21〜23、5秒・10秒・20秒） | **v3** | **学習した評価（その盤のネットがあれば）**、なければ手作り |
| 分析・ヒント・コーチ・検討 | **v3** | 同上 |

人が遊ぶレベルの手は変えていません（前のビルドと、3つの盤・1,960回の探索で手・評価値・深さ・局面数が一致）。

## 探索 v3
v2（逆フューティリティ・フューティリティ・LMR の対数表・ヒストリー・IIR、2026-11-13）とビットボードに足したもの：
- 探索をまたいで残る置換表（4項目のバケツ・世代つき。前は70万件で全部消していた。複数スレッドでは Praline の共有表を同じく世代つきで）
- ルートの PVS と aspiration window（±40、外れたら2倍）

### 計測（v3 対 v2、8×8、ネイティブ `tools/nnue/kn match`、序盤4手ランダム・先後入れ替え、引き分けなし）
| 条件 | 結果 | Elo（95%区間） |
|---|---|---|
| 1手2万局面、200局 | +118 −82 | +63（+15〜+114） |
| 1手0.1秒、200局 | +107 −93 | +24（−24〜+73） |
| 1手0.1秒、200局（別の序盤・popcnt あり） | +101 −99 | +3（−45〜+52） |
| 部品：aspiration・PVS だけ（2万局面、200局） | +103 −97 | +10 |
| 部品：置換表だけ（2万局面、200局） | +98 −102 | −7 |

局面数固定では勝ち越し、時間固定は合わせて 400局で +208 −192（約 +14、誤差の内）。部品ごとでは差が出ず、両方そろえたときだけ局面数固定で伸びる。
作業機は共用2コアでほかの計算も動いていたため、時間固定の結果は揺れが大きい。天上の基準値（`RT_LV`）は据え置き（ネットを入れたら測り直す）。

### 組合せゲーム理論（CGT）について
コナネは組合せゲーム理論で研究されているゲーム（Ernst「Playing Konane Mathematically」1995 など：局面を独立な部分に分け、各部分の値の和で勝敗を決める）。
Müller の decomposition search（囲碁の終盤）と同じく、盤が互いに影響しない区画に分かれた終盤なら完全に読める見込みがあるが、
コナネの区画は跳びで簡単につながり、値の計算（標準形・温度）も重いので今回は入れていない（今の探索は終盤を勝ち・負けの値で読み切っている）。

## 学習した評価関数（仕組み）
| 項目 | 内容 |
|---|---|
| 入力 | 2·n² ＋ 56（8×8 で 184）＝自分の石 n² ＋ 相手の石 n² ＋ 跳べる手の数（自分・相手 各16段階）＋ 跳べる石の数（各12段階）。黒の目と白の目（白は筋を左右に折り返し、自分の石がいつも同じ色のマスに来る形）の2組 |
| 構造 | 入力 → 64（2視点、手番側が先）→ clipped ReLU → 16 → clipped ReLU → 1。盤の大きさ（6×6・8×8・10×10）ごとに1つ |
| 数値 | すべて整数（int16 の1層目、int32 の和）。WebAssembly とネイティブで同じ値。1層目は差分更新（動いた石と跳び越えた石の分だけ足し引き）。数の段階の4行は評価のときに足す |
| 出力 | ロジット × K（K はデータから求める評価の尺度。手作り評価と同じ単位になり、探索の枝刈りの幅がそのまま使える） |
| ファイル | `KNN1`（8×8 で約28KB、gzip 後 約13KB）。`konane/net-<盤>.bin.gz` に置き、`engine.js` の `NETV` に版を入れると有効 |
| 学習データ | このエンジン自身の自己対局（探索 v3・手作り評価、1手8千局面、序盤2〜8手ランダム・途中2%ランダム）。外部のエンジンは使わない |
| 教師 | 0.7 × σ(探索値 / K) ＋ 0.3 × 勝敗。盤の色を保つ4つの対称（そのまま・180°・2本の対角線）のどれかで毎回回して学習 |
| 学習器 | `tools/nnue/train.c`（C、Adam、検証用 3%） |

### 作業機での仮ネットの確認（採用しない）
8×8 の自己対局 約20万局面（1手5千局面、5,000局）で 12エポック学習した仮ネット。**サイトには置いていません**（学習本番は Mac）。
| 確認 | 結果 |
|---|---|
| 差分更新と盤全体からの計算の一致（`kn nncheck`、探索中の全評価） | 不一致 0（122万回） |
| エンジンの値と学習器の整数ネットの値（`nnfeat.h`）の一致 | 不一致 0 |
| WebAssembly（SIMD・SIMD なし・core_mt.wasm 1スレッド）とネイティブの一致（`tools/check_nn.js`：評価値と、空の置換表からの探索の手・値・深さ・局面数） | 一致 |
| 量子化（整数）と float の差 | 平均 7.3（評価の単位。跳べる手1つ＝34） |
| 勝敗の予測（検証局面の交差エントロピー） | 仮ネット（読まずに）0.603、先生の探索値 0.569 |
| 仮ネット 対 手作り評価（探索 v3 どうし、1手2万局面、200局） | +147 −53（+177 Elo、+126〜+237） |
| 同じ持ち時間（1手0.1秒、200局） | +113 −87（+45 Elo、−3〜+95） |
| Node（wasm）の対局（1手2万局面、10局） | +7 −3 |
| ブラウザ（headless Chrome、1スレッドの Worker／分離あり・2スレッドの core_mt.wasm）で天上Ⅰの手・分析 | 動作（`nn: 1`）、エラーなし |

ネットの評価は手作り評価より重い（局面数／秒 約0.7倍。gprof で nnEval 13%・差分更新 8%）ので、局面数固定の差がそのまま時間固定には出ない
（アマゾンズと同じ注意）。20万局面でも時間固定で勝ち越したので、Mac の本番（約2000万局面）のネットは天上と分析を強くする見込み。

## 推論の高速化（2026-11-20、値は同じ）

- **wasm SIMD の `nnEval`**（`core.c`）：1層目は中間層＋4つの数の行を int32 のレーンで足し（前の int の和と同じ。int16 のあふれなし）、0〜127 に切って int16 に詰め、2層目の 16 個の和を `i32x4.dot_i16x8` で（整数の和なので同じ）。SIMD なし・ネイティブは前のループ（差分更新 `accMove` は前からコンパイラが SIMD にしている）。
- **確認**：`tools/check_nn.js`（仮ネット s8、40局面：SIMD・SIMD なし・core_mt.wasm 1スレッドとネイティブの評価・手・値・深さ・局面数が一致）、`kn nncheck`（差分更新の一致）、旧版と新版の探索（`E.probe`、12局面×3）がネットあり・なしで一致、ブラウザ（headless Chrome、仮ネットを置いて）で Lv.21 が1スレッド・マルチスレッドともネットで動作。
- **速さ**（wasm SIMD、`E.probe` 20万局面を旧・新交互に同じプロセスで、CPU 時間）：ネットあり **約 790k → 1,040k 局面/秒（+30%）**、ネットなしの約 0.55 倍 → 0.72 倍。SIMD なし・ネットなしは変わらず。
- **時間固定の対局**（wasm、`tools/duel.js t 50`、1手50ミリ秒、v3＋仮ネット対 v3 手作り評価、s8、80局、仮ネット＝自己対局 約3.2万局面・先生3千局面）：旧 36.2%（−98 Elo）→ 新 47.5%（−17 Elo）。仮ネットは小さく弱いので目安。

## Mac での学習（`konane/tools/nnue/`）
```bash
bash konane/tools/nnue/run.sh                                     # 既定：約2000万局面（8×8 50%・10×10 30%・6×6 20%）
WORK="/Volumes/Orico A 8TB/konane-nnue" bash konane/tools/nnue/run.sh   # データを外付けに
ROUNDS=2 bash konane/tools/nnue/run.sh                            # 2周目（1周目のネットを先生に）
```
ビルド → 全コアで自己対局 → 学習（3つの盤を同時に）→ 確認（差分更新と学習器の値の検査、手作り評価との対局）→ 採用ファイル（`$WORK/r1/adopt/`）。
途中で止めても続きから。時間の目安（M4 Pro 14コア）：自己対局 約2〜4時間、学習 約30〜60分、確認 約15〜25分。手順の詳細は `tools/nnue/README.md`。

## 採用の基準
1. 差分更新の検査と学習器の値の検査で不一致 0。
2. 同じ持ち時間（1手 0.1秒、探索 v3 どうし）で今の評価（1周目は手作り、2周目以降は前のネット）に 200局で勝ち越し、勝率の片側95%の下限が 50% を超える（`run.sh` が `-> adopt` と書いた盤だけ）。
3. サイトに入れる前に `node konane/tools/check_nn.js <kn> <adopt フォルダ>`（SIMD・`KN_NOSIMD=1`・`KN_MT1=1`）で WebAssembly の一致を確かめ、ブラウザで天上の手・分析を確かめ、
   天上の基準値（`app.js` の `RT_LV` の 24〜26、大百科の RATING）を測り直す。トップページの紹介文に「NNUE搭載」と学習量を書く（共通ルール）。
