# レーティング戦（AI とのレート対局）のレーティング表

新しい対局の「レーティング戦」では、AI の各レベルに **盤の大きさごとの固定レーティング** を割り当て、プレイヤーのレーティング（端末ごと、`localStorage` の `dots-rated-v1`）との Elo 計算で増減させます。オンライン対戦のレーティングとは別物です。実装は `rated.js`。

## 決め方

- 3×3 と 4×4 の AI はレベル同士を実際に対戦させて測りました（各組 16〜40 局・先後交互、`engine.js` の `chooseMove` を Node で実行）。
  勝率 s から差 = 400·log10((1−s)/s)、勝率 0 のときは +400 で打ち切り。
- 3×3 では Lv.6 以上が互いに 50%（どれも完全読み）なので同じ値。4×4 は Lv.9・10 が完全読み（最上位）。
- 4×4 の Lv.8→9 は測っていない（Lv.9 以上は WebAssembly の解析器を使うため）ので +100 の仮置き。
- 5×5 は Lv.1〜8 が未測定の **暫定値**（4×4 の目盛りを基に少し低め）。Lv.9・10 は 5×5 用 WebAssembly 解析器の導入後に実測：Lv.10 は Lv.8 に 100 局 82%（+264）→ 1780+264 ≈ 2040、旧 Lv.10 にも 100 局 83%。Lv.9 は旧 Lv.9 に 40 局 87.5% で、Lv.10 との差を従来どおり −70 として 1970。
- 3×3 の上限は 1600。3×3 は最善でも先後で結果が決まる小さな盤なので、完璧に指しても 1600 前後で頭打ちになるようにしています。

## 計算とルール

- プレイヤーの初期値 1000。K = 48（最初の10局）、以降 K = 24。期待値 E = 1 / (1 + 10^((相手R − 自分R) / 400))。勝ち 1・引き分け 0.5（4×4 のみ起こりうる）・負け 0。
- 相手の選び方：目標 = 自分の R + ずらし幅（80% は ±100 以内、10% は +150〜+300 の格上、10% は −150〜−300 の格下）に、選んだ盤の表でいちばん近いレベル（同値なら低いレベル）。ダイアログに今回の相手（レベル・R・格上／互角／格下）を表示し、その相手で始めます。盤を変えると選び直し。
- 先後はランダム。対局中は待った・ヒント・形勢（読み）表示・評価グラフ・分析は使えません。終局後は振り返りできます。
- 対局中に別の対局・レッスン・詰めドット・棋譜読込へ移ると確認のうえ中断＝負け。再読み込みしても続きから再開し、結果は対局 ID で 1 回だけ記録します。

## 保存形式

`dots-rated-v1`（同期対象）

```json
{ "r": 1049, "n": 5, "w": 2, "l": 3, "d": 0,
  "hist": [ { "id": "mvf1ley4wpb8t", "t": 1792401542769, "sz": 3, "lv": 3, "or": 980, "s": 0, "d": -31, "r": 1049, "why": "end" } ] }
```

- `r` 現在のレーティング、`n` 局数、`w`/`l`/`d` 勝・負・分
- `hist` 直近 100 局（古い順）。`id` 対局ID、`t` 時刻(ms)、`sz` 盤、`lv` AIレベル、`or` AIのR、`s` 得点(1/0.5/0)、`d` 増減、`r` 対局後のR、`why` `"end"` または `"abandon"`
- 同期のマージ案：`hist` を `id` で和集合して `t` 順に並べ、`r`/`n`/`w`/`l`/`d` は最後（`t` 最大）の記録を持つ側の値を使う。

`dots-rated-cur-v1`（端末内のみ・同期不要）：盤上のレーティング戦 `{ id, n, human, lv, or, my, tag, done? }`

## 本編のマルチスレッド（2026-11-09）
addendum「本編のマルチスレッド」（全タイトル対応）。エンジンは JavaScript（＋共有しない wasm の解析器）なので共有メモリは使わず、オプションの「マルチスレッド」（`shared/mtworkers.js`、PC は自動でオン、スマホ・タブレットはオンにするまでオフ）で Worker の数を決める。
- **Lv.9・Lv.10（時間で考える、レート戦も）**：エンジンの Worker が補助の Worker を起動し、完全読み（勝敗の読み切り）のルートの手を分担・競争する（`chooseMoveAsync`、もとは補助3つまで固定）。補助の数はページが `mt`（`min(論理コア数 − 1, 7)`、オフで0）で渡し、必要に応じて増やす。補助の締め切りは主の時計で渡す（`until`：起動の遅れた補助が1手を遅らせない）。
- **終局後の振り返り**：局面ごとに Worker で並列（オンで最大7、オフで1）。2コアで 48局面 28.3秒 → 15.3秒（1.85倍）。
- **解析（ヒント・形勢・コーチ・検討ボックス）は、ページが分離されているときだけ置換表を共有して分担する（2026-11-09）**：全部の手の正確な値は互いに木の大半を共有するので、別々の置換表で手を分けても速くならなかった（5×5 の6局面、CPU時間で 2 Worker 1.03倍・4 Worker 1.13倍・8 Worker 1.42倍）。そこで `dots/sw.js`（`shared/mtworkers.js` の共有モード：mtengine.js と同じ軽い分離。Chrome / Edge の PC は自動、Safari・Firefox はオプションをオンにしたときだけ COOP モード＝ログイン・オンライン対戦は止まる。選択は全ブラウザで `aicoding-mt`）で分離し、エンジンの Worker と補助が SharedArrayBuffer の置換表（64MB、ロックなし：Int32×4 の XOR 照合）を共有して、正確に解く局面（5×5 は安全な手が15以下）の全部の手を分担する（`engine.js` の `allShared`／`allShare`：主が先に最善手の値を読み（S.all と同じ）、その間から補助は原子的なカウンタで手を取り合って全幅で解く。時間切れは共有の合図で全員止まり、いつもの推定へ）。値は1スレッドの S.all と全部一致（`dots/tools/mtshared.js`）。作業機の見積もり（各 Worker の局面数、いちばん多い Worker を時間とみなす、5×5 の3局面）：2スレッド 1.92倍、4スレッド 3.56倍、8スレッド 5.59倍（仕事の総量は1スレッドの1.00〜1.02倍）。分離できないときは今まで通り1スレッド。4×4 の wasm 解析器（`x4`）は1スレッドのまま。ページは解析の依頼に `mt`（`MTWorkers.shared` のときだけ補助の数）を付ける。
- **Mac の実測と直し（2026-11-09）**：ユーザーの Mac（14コア、Chrome 157）で解析（共有）が 2・4・8スレッド 0.99・1.00・0.99倍、14スレッドだけ 1.51倍、AI Lv.10 は 2.80 → 2.41・2.33・2.37・2.39秒、振り返りは 1.94・3.70・6.48・10.19倍。原因：補助はエンジンの Worker が作る入れ子の Worker で、そのスクリプトの読み込みは親の Worker を通る。親が同期で解いている間は補助が始まらず、新しい Worker の最初の解析（計測ページは局面ごとに新しい Worker、ページでは最初の1回）は主だけが読んでいた（作業機で補助の局面数 0 を確認）。直し：補助は作ったときに `ping` に答えるまでを準備とし（`getPool` の `ready`）、解析は読み始める前に準備を最大 `min(3秒, 時間/4)`、AI（Lv.9〜）は最大1.5秒待つ。直したあと作業機で2つの Worker の局面数がほぼ半分ずつ（3106k/3188k 等）、値は1スレッドと全部一致。分担のしかたの見直し（全 Worker でまず最初の手を読む等）も試したが、局面数の見積もりで今の方式（8スレッド 6.33倍）より悪かった（5.70倍）ので今のまま。AI Lv.10 は補助が wasm の解析器の勝敗読みを競争する方式で、計測ページでは補助が温まってから測っているため今回の直しでは変わらない見込み（方式は今回は変えていない。最初の1手だけは準備待ちで補助が効くようになる）。
- **AI Lv.10 の見直し（2026-11-10、Mac の bench-all-3：1スレッド 2.67秒 → 2〜14スレッド 2.33〜2.41秒、同じ手 2〜4/6）**：
  - **補助は働いている**：AI の手は `chooseMoveAsync` → `chooseW5Async`（5×5、wasm の解析器）で、補助（入れ子の Worker）が勝敗の読み切り（`sliced`）を手ごとに分担している（局面の結果・作業機の局面数で確認）。
  - **時間の見方**：Lv.10 は時間（5秒）で打ち切る方式で、計測の6局面のうち3つ（安全な手 24・22・20）はどのスレッド数でも勝敗が決まらず、いつも約4.5〜5秒を使い切る（補助の分だけ「深く読む」＝決まった手が増えるだけ。5秒で証明できた手は 0〜3/約30 と少ない）。平均の時間はこの3局面で決まるので、スレッドの効果は見えない。同じ手の一致が下がるのも、決まらない局面で手の順（`rand`）と証明できた手が変わるため。→ **計測ページは、決まった手（読み切り・勝ち／引き分けの証明）の時間と、決まらない局面で証明できた手の数を分けて出す**（`stat`：エンジンの返事に `{ n, lost, draw, helpers }` と `outcome` を付けた。指し手は変わらない）。
  - **決まる局面で速くならなかった原因**：①スレッドがあるときも、主の Worker は最初に発見的探索（`H.best`、時間の 15〜35%＝0.75〜1.75秒の固定）をしてから自分の分担を読んでいたので、補助が先に全部の手を証明しても1手の時間が縮まなかった（局面4：全部の手が負け → 1スレッド 1.32秒、2〜14スレッド 1.34〜1.36秒）。②補助は置換表を共有しない（wasm の解析器は Worker ごとのメモリ）ので、手を分けても同じ部分木を何度も解く：局面4 の28手の証明は1スレッド 352万局面、2つに分けると 217万／284万、4つに分けても 173〜224万（仕事の総量 2.3倍）。
  - **直し（スレッドがあるときだけ。1スレッドの `chooseW5` は変えていない）**：主は自分の分担を先に読み、発見的探索の時間を残せる間は補助の答えを待つ。全部の手が決まれば（勝ち・引き分け・全部負け＝点差の最善）発見的探索をしない。決まらなければ、負けと証明された手を除いて発見的探索（その間も補助は続ける）、最後にもう一度補助の答えを見る。決まったら補助を止める（分離できたページでは共有の合図 `stop` を `sliced` が見る）。補助の答えは1手の時間を過ぎて待たない（前は `pool.run` の締め切り＝時間＋2秒まで待ちうる）。
  - **見込み（作業機の局面数から。Mac の wasm 約750万局面／秒として）**：局面4 は 1.32秒 → 約0.6〜0.7秒（固定の 0.75秒がなくなる分。補助が増えても②のため 2〜3スレッド以上はほとんど同じ）。決まらない局面は今まで通り5秒。②を直すには wasm の解析器（`solver5.c`）の共有メモリ版（置換表を Worker 間で共有、モリスの `engine_mt.wasm` と同じ作り）が要る。JS の共有の解析器（`SharedSolver`）は1スレッドで wasm の約5.5倍遅く（局面4：wasm 0.93秒・352万局面、JS 5.1秒・1347万局面）、代わりにはならない。**限界**：作業機は共用2コアで常に高負荷のため、時間ではなく局面数で判断（headless Chrome で計測ページが動き、2スレッドで指し手が返ることは確認）。
- 計測ページ `dots/bench.html`（Lv.10 の1手の時間・読み切り・1スレッドと同じ手、振り返りの時間、解析（5×5 の終盤4局面の全部の手の正確な値：共有の置換表で分担、1スレッド＝非共有と比べて同じ値か）を 1・2・4・8…論理コア数で）。作業環境（共用2コア）では Lv.10 の差は出ない（1手 2.96秒 → 2.89秒、読み切り 3/6 → 2/6）。正式な効果はユーザーの Mac で測る。
