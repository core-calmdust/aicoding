# Model Card: Nine Men's Morris AI (`engine.wasm` + `evalnet.bin`)

ナイン・メンズ・モリスのAIの仕組みと強さの計測結果です。

- **ゲーム**: https://core-calmdust.github.io/aicoding/morris/
- **作成**: core-calmdust（AIコーディングによる制作）
- **バージョン**: v2（2026-10-20）

## 構成

| 部分 | 内容 |
|---|---|
| 探索 | `engine.c` を WebAssembly にビルドした `engine.wasm`。αβ探索（PVS）、置換表、キラー手・ヒストリーによる手の並べ替え、取る手だけの静止探索、後半の手を浅く読む枝刈り（LMR）。盤面はビットボードで表現しています。 |
| 評価関数 | `evalnet.bin`（ナインのみ）。入力71（各点の自分/相手の駒・持ち駒の数・飛べるか・配置中か）→ 中間64（ReLU）→ 出力1。約4,700パラメータ。トゥエルブ・シックスは手作りの評価関数を使います（トゥエルブは 2026-11-14 に自己対局の結果で重みを調整、下の「評価関数の Texel 調整」）。 |
| 使う場面 | Lv.8〜10 の対局、対局中の形勢表示・ヒント、対局後の分析。Lv.1〜7 は従来の JavaScript 版（読む深さとゆらぎで強さを調整）。WebAssembly が使えない環境でも JavaScript 版で動きます。 |

## 学習

- 自己対局（序盤の数手はランダム）で約15万局面を集めました。
- 各局面の教師値は、その局面を約0.04秒読んだ探索の評価値（重み0.7）と、対局の勝敗（重み0.3）を合わせたものです。
- 盤の対称性（回転・反転・内外の入れ替えの16通り）でデータを増やし、二乗誤差で学習しました。

## 計測（自己対局・先後入れ替え・序盤4手ランダム）

| 比較 | 持ち時間 | 結果 |
|---|---|---|

合計で、同じ持ち時間の旧AIより Elo でおよそ300程度強くなったと見ています（各80局前後の計測なので幅があります）。

## 試したが採用しなかったもの

- **終盤データベース（初回）**：駒が少ない移動段階を後退解析で解いた（旧ツール `tools/mdb.c`、対称なし・50手ルールなし）。対局では勝率が変わらず（100局で51%）配信しなかった。→ 2026-11-14 に `tools/solve.c` の値（50手ルール込み・対称で縮小）で作り直して採用（下の「終盤データベース」）。`mdb.c` は削除。
- **評価関数の2周目**（新しいAI同士の対局データで再学習）：持ち時間によって結果が逆になったため不採用。

## 本編のマルチスレッド（2026-11-09、全タイトル対応）
2026-11-08 には「完全解析で引き分け・持ち時間2倍でも強さが変わらない」として対象外にしたが、addendum の全タイトル対応（判断はユーザーの Mac の実測）で対応した。強さより**速さ**（同じ時間でより深く・分析が早く確定する）のため。
- `engine.c` を `-DMT` で作った `engine_mt.wasm`（ビルドは `engine.c` の先頭）。置換表・盤の形・学習評価は共有、局面・履歴・キラー手・手の一覧などはスレッドごと（`TLS`）の Lazy SMP。手の一覧 `buf`・`scb`（1MB）は各スレッドの枠（4MB）の TLS の直後に置く。（補助の深さのずらし・置換表は下の「見直し」で変更。）**通常版 `engine.wasm` は1バイトも変わらない**（元のソースと同じ設定のビルドを cmp で確認）。
- 盤の形（ナイン・シックス・トゥエルブ）は共有なので、補助（`mt-helper.js`）は主スレッドが `set_geometry` を終えたこと（`geo_key()`、最後に書く）を待ってから読む。
- 使うもの：分析・ヒント・コーチ（深読み＝Lv.9）・検討ボックス（`cands` を流しながら）、時間で考える Lv.9・Lv.10（シックス以外の Lv.11 も、レート戦も）、PRO のスレッド数（どの思考の制限でも）。Lv.1〜8（深さ・ノイズ）とシックスの完全解析（データベース）は1スレッド。情報行に「· NNN nps」。
- 計測（作業環境：共用2コア）：同じ深さまで主スレッドの局面数 1スレッド 1607万 → 2スレッド 1097万（12局面、**局面数換算 1.47倍**）、最善手 10/12 一致。最上位レベルは足さない（Lv.9 対 Lv.10 が持ち時間2倍で 4勝16分0敗）。正式な効果はユーザーの Mac で `morris/bench.html` を測る。

### マルチスレッドの見直し（2026-11-09、Mac の実測から）
- **Mac の実測（M4 Pro 14コア＝高性能10＋高効率4、Chrome、`bench.html` 3秒）**：局面数／秒は 2・4・8・14スレッドで ×1.99／×3.93／×6.99／×9.38 なのに、同じ深さまでの時間は ×1.23／×0.50／×1.30／×1.52、平均の深さは 16.17 → 16.4 程度でほぼ伸びず。4スレッドの局面9 で深さ20 まで31秒（1スレッド1.4秒）、14スレッドの最善手の一致 9/12。
- **原因**：共有の置換表が「1つのキーに1項目・常に置き換え」で、項目を6つの配列に分けて順に書いていた。スレッド数倍の浅い項目が深い項目を追い出すので、補助が読んだ結果が主スレッドに残らず、同じところを読み直していた（作業機のシミュレーションで表を Mac と同じくらい埋まる大きさにすると、主スレッドが深さ15 までに読む局面数が 1スレッド 1.52億・2スレッド 1.44億・4スレッド 1.56億＝**速くならない**。Mac と同じ傾向）。また2つのスレッドが同時に書いた項目は、ある局面のキーと別の局面の値・深さが組み合わさりうる。局面9（引き分けの局面）の外れ値もこの置換表の不安定さによるものと見ている（作業機でも深さ20 までの主スレッドの局面数が 2スレッドで1スレッドの2.5倍になる回があり、新しい表では出ない）。
- **確認して問題なかったもの**：置換表・盤の形・学習評価はスレッド間で共有（TLS ではない）、局面・履歴・キラー手・手の一覧はスレッドごと（競合なし）、停止（`gStop`・`ctl[0]`）、補助は主スレッドが盤の形を設定するのを待つ。ベンチの測り方（毎回 `newgame` で表を消す、最初にウォームアップ、補助は先に起動済み）も妥当。ヒストリーの値は補助で消されないが、増え方は約4.6万/秒で桁あふれまで十数時間かかるので問題にならない。
- **変更（`engine_mt.wasm` だけ。通常版 `engine.wasm` は同じ設定のビルドで cmp 一致＝1スレッドの指し手は不変）**：
  - 置換表を、4項目のバケット（64バイト）× 2^20 = 64MB（項目数 4倍）に。1項目は `{ key ^ w, w }`（w＝値・手・深さ・種類・年齢）で、読むときに XOR で照合（壊れた項目は使わない）。置き換えは同じキー→それ以外は浅い／古い（前の探索）項目。年齢は主スレッドが探索ごとに進める。
  - 各スレッドが終えた反復（深さ・値・手）を共有し、主スレッドは最も深い結果で答える（同じ深さなら主スレッド）。深さの上限があるとき、補助が先に届いたら主スレッドも終える。
  - 補助の深さのずらし（奇数番は1手深く始める）はやめ、全スレッド 1, 2, 3… と読む。Stockfish 式に補助ごとに深さを飛ばす方式も試したが、主スレッドの局面数換算で遅かった（表を埋めた条件で 4スレッド ×1.77、ずらしなし ×2.88）。
  - プールの `initial` を 1152 ページに（表が大きくなり wasm の宣言が 1027 ページになったため。512 のままだとスレッドが起動しない）。`engine_mt.wasm?v=2`。
- **作業機での確認（共用2コア・負荷が高いので、主スレッドが同じ深さまでに読む局面数を時間とみなす。12局面、深さ15）**：
  - 実際の大きさの表：旧 1スレッド 6640万 → 2スレッド 4560万（×1.46）・4スレッド 2700万（×2.46）。新 1スレッド 4590万 → 2スレッド 2780万（×1.65）・4スレッド 1500万（×3.05）。旧の1スレッド比では ×2.4／×4.4。
  - 表を Mac 並みに埋めた条件（項目数を1/16）：旧 ×1.05／×0.97 → 新 ×1.52／×2.88。
  - 局面9 の深さ20：旧 1スレッド 748万、2スレッド 472万〜1856万、4スレッド 478万〜998万 → 新 1スレッド 291万、2スレッド 154万〜281万、4スレッド 102万〜176万（3回）。
  - headless Chromium で `bench.html`・対局ページが分離・スレッド起動まで動くこと（2スレッド）を確認。
- **見込み（Mac）**：同じ深さまでの時間 2スレッド ×1.5〜1.7、4スレッド ×2.5〜3、8・14スレッドはそれ以上（表の大きさが効く分）。ベンチの「1スレッド」は `engine_mt.wasm` の1スレッドで、表が大きくなった分すでに通常版より速いので、通常版との差は表の比より大きい。要再計測：`morris/bench.html`。

### マルチスレッドの見直し その2（2026-11-10、Mac の bench-all-2 から）
- **Mac の実測（M4 Pro 14コア、Chrome 157、`bench.html` 3秒、上の直しの後）**：局面数／秒は 2・4・8・10・14スレッドで ×2.02／×4.06／×7.42／×8.56／×9.63 なのに、同じ深さまでの時間は ×1.34／×1.51／×1.51／×1.49／×1.70、平均の深さは 17.08 → 17.8 程度。同じ作りのチェス（×2.5〜3.0）・チャンギ・シャンチー・将棋より低く、上の見込み（4スレッド ×2.5〜3）にも届かなかった。
- **確かめて原因でなかったもの**：終盤データベースは未配布（`engine.js` の `EGDB_URL` が空）で探索から引かない。シックスの完全解析 DB は JS（`perfect.js`）で完全解析レベル・解析の注釈だけ、探索は使わない。置換表の大きさ（作業機で 1/16 にしても下の結果は同じ）。補助の履歴（`histT`、補助は `newgame` で消えないが 3秒の探索で最大約100万＝キラー手の 2^26 まで数十回分）。繰り返し・引き分けと置換表の相性は局面9（引き分けの局面）だけ 2スレッドで遅くなる形で出るが、全体の原因ではない。ベンチの測り方（毎回表を消す、深さ D は1スレッドが3秒で終えた深さ）と、補助が深さの上限 D に先に届いたら主も終える仕組みも正しく動いている。wasm（node のスレッド）とネイティブのビルドで1スレッドの局面数は同じ（局面1 の深さ16 まで 1095万）。
- **原因**：全スレッドが同じ木を同じ順に同じ速さで読むため、同じ部分木を**同時に**読み、どのスレッドも相手の結果を置換表から受け取れない（終わる前に自分も同じ所を読み終える）。今までの作業機のシミュレーション（主スレッドの局面数を時間とみなす、2コアで交代に動く）は、スレッドが交代で動くので後から入ったスレッドが先のスレッドの読み終えた部分木を必ず使え、楽観的だった（同じ作り方のネイティブ版でも 4・8スレッド ×2.55／×4.88）。全スレッドを 1024局面ずつ足並みをそろえ、**置換表への書き込みがほかのスレッドに見えるのをその回の終わりまで遅らせる**（＝本当に同時に動く）シミュレーション `tools/mtsim/`（`gen.py`・`sim.c`）にすると、直す前の engine_mt.wasm で 2・4・8スレッド ×1.22／×1.43／×1.71（4局面、256局面ずつでも ×1.33／×1.53／×1.87）と **Mac の実測と合った**。
- **直し（`engine_mt.wasm` だけ。通常版 `engine.wasm` は同じ設定のビルドでコード・データの全セクションが一致＝1スレッドの指し手は不変。`engine_mt.wasm` の1スレッドの局面数も前と同じ）**：Kerrigan の「simplified ABDADA」（busy marks）。各スレッドは、残り深さ 3（`BUSY_D`）以上の節点で読む手の局面に印（`busyT`、2^15 項目の共有表、64ビット＝局面の鍵＋スレッド番号）を付け、読み終えたら消す。2手目以降の手で、その局面にほかのスレッドの印があれば後回しにして、残りの手を先に読む（後で読むときにはたいてい置換表に結果がある）。ルートの手も同じ。1スレッドでは自分の印しかないので読みは前と同じ。後回しは節点ごとに最大32手。`engine_mt.wasm?v=3`。
- **作業機での確認（共用2コア、上の「本当に同時」のシミュレーション、12局面、深さ D は1スレッドの1300万局面＝Mac の3秒）**：直す前 ×1.22／×1.43／×1.71（4局面）→ 直した後 2・4・8スレッド **×1.65／×2.87／×4.79**（幾何平均 ×1.68／×2.96／×4.85。印も同じように遅れて見えるとした控えめな条件。印がすぐ見える条件では 4局面で ×1.82／×3.36／×6.02）。`BUSY_D` 2・5 も試したが 3 と差は小さい（4・8スレッド ×2.36／×4.58、×2.95／×4.28）。ルートの後回しはわずかに良い（×1.83／×2.88 → ×1.90／×3.10）。node の実スレッド（wasm、2スレッド、主の局面数）でも 2局面 ×1.52 → ×2.01。1スレッドと違う最善手になる局面は前の方式と同程度（12局面中 局面1・6 などで、前の方式でも別の手になっていた所）。
- **見込み（Mac）**：同じ深さまでの時間 2スレッド ×1.6前後、4スレッド ×2.5〜3、8スレッド ×4前後（性能コア）。14スレッドは高効率コアの分だけ伸びが鈍る。**限界**：作業機は共用2コアで負荷が高く（ほかのセッションの計算が常に2つ動いている）、実時間では測れないので、すべて局面数のシミュレーション。シミュレーションの「遅れて見える」は Mac の挙動を再現するための模型で、遅れの大きさ（1024・256局面）で多少変わる。要再計測：`morris/bench.html`（`bench-all.html`）。

### マルチスレッド その3：YBW（2026-11-11、リバーシ v4 / v4.1・シャンチー「その3」の方式）
- **きっかけ**：busy marks の後、同じ作りのシャンチー・将棋・チェス・リバーシは Mac で 8スレッド以上の伸びが止まり、Young Brothers Wait の分割探索で直った。モリスは busy marks 版の Mac の数字がまだ無いが、同じ形になる見込みなので入れる（モリスは完全解析で引き分けで、AI の強さは時間2倍でもほとんど変わらないため、主に分析・ヒント・検討ボックスの速さ）。
- **変更（`engine_mt.wasm` だけ。通常版 `engine.wasm` は前後の `engine.c` を同じ設定でビルドしてバイト一致＝1スレッドのレベルの指し手は不変。`engine_mt.wasm` の1スレッドの読みも前と同じ：シミュレーションの1スレッドだけの実行で12局面の局面数・手・深さが前後で一致）**：
  - 補助は根を読まず `mt_idle` で分割点を待つ（`mt-helper.js`。盤の形が揃ってから `mt_idle(250, …)`＝手の空いたとき 250ms ごとに戻り局面数を nps の表示へ）。`mt_idle` の無い古い wasm なら前の Lazy SMP のまま。
  - `search()` の残り深さ 3（`SPLIT_D`、`mt_split`）以上の節で最初の手を読んだ後、手の空いた補助がいれば（または上で待つ持ち主がいれば）残りの手を分割点（`SPt`、128個）に出す。手は1スレッドのループと同じ順（busy marks で後回しにしていた手は最後）、LMR も1スレッドと同じ。null window → 読み直しも同じ。カットで分割点に停止の印。根も分割点（2手目以降）。
  - 補助は分割点の局面と繰り返しの判定用の履歴を写す。v4.1 と同じく、待つ持ち主の印・読みかけの手の二度読み（遅いコアのスレッドが上を止めない）・分割点の数の変数は専用のキャッシュライン。置換表・busy marks・盤の形・ネットはそのまま。
  - `engine_mt.wasm?v=4`・`mt-helper.js?v=2`（`index.html`・`bench.html`）。
