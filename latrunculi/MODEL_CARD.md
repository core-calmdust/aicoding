# Model Card: ルドゥス・ラトルンクロルム AI（`core.c` → `core-wasm.js`・`core_mt.wasm`、`engine.js`）

ラトルンクロルム（latrunculi/）のAIの仕組み・強さの計測結果・学習した評価関数（NNUE）の作り方です。仕様の正本は `claude/latrunculi-spec.md`。

- **ゲーム**: https://core-calmdust.github.io/aicoding/latrunculi/
- **作成**: core-calmdust（AIコーディングによる制作）
- **バージョン**: v3（2026-11-20：C／WebAssembly 化・マルチスレッド・NNUE の仕組み）

## 構成

| 部分 | 内容 |
|---|---|
| ルールと探索 | `core.c`（C）を WebAssembly にビルド（`tools/build-core.sh`）。`core-wasm.js` に SIMD 版と SIMD なし版の2つ（動く方を使う）。αβ（PVS）、置換表、反復深化＋アスピレーション、キラー手・ヒストリーでの手の並べ替え、LMR（log×log）、null move（動かす段階）、静止探索（挟む手）。評価はビットボードで計算。 |
| マルチスレッド | `core_mt.wasm`（`-DMT`）。Praline（`shared/praline/`）の Young Brothers Wait：探索の各節点とルートで、最初の手を読んだあと残りの手を空いたスレッドで分担し、置換表は共有メモリに1つ。分離されたページ（Chrome の PC は自動）で、時間で考える Lv.19・20・分析・ヒント・コーチ・PRO のスレッド数で使う。分離できないページは今までの `shared/mtsplit.js`（ふつうの Worker でルートを分担、各 Worker の探索は WebAssembly）。 |
| 予備 | `engine.js` の JavaScript の探索（WebAssembly が使えない環境、ページ本体）。**WebAssembly と同じ手・同じ値・同じ局面数**（下の「一致の検査」）。 |
| 評価関数 | 手作りの特徴の重み付き和（駒・裏返った駒・狙われた駒・動ける向き・並び・中央・隅・手持ち・取り合いなしの手数×駒得 ほか15特徴、置く段階と動かす段階で別の重み。自己対局の勝敗へのロジスティック回帰＝Texel 法、ルールごと）。 |
| 学習した評価（NNUE） | 仕組みは完成、**ネットはまだ採用していない**（`engine.js` の `NETS` が空の間は手作り評価のまま）。ネットは「手作り評価への補正」を学ぶ形（下の「NNUE」）。学習はユーザーの Mac で `tools/nnue/run.sh`。 |
| 置く段階の定跡 | `book.js`（最初の数手、探索で決める Lv.10〜 だけ）。 |

## 一致の検査（ルールと探索）

- `node tools/check_rules.js`：3つのルールでランダムな対局と盤（裏返った駒を含む）約2.5万局面について、合法手（同じ順番）・`hasMove`・勝敗判定（終わり方まで）・評価値、各局面の手を指したあとの盤・裏返り・手持ち・取った数・往復禁止の記録・取り合いなしの手数・手番・ハッシュを、`engine.js` と `core.c` で比べる。ネットについては、ランダムな小さなネットで JavaScript の値と `core.c` の値、`core.c` が1手ごとに差分で更新した中間層と作り直した中間層（差分更新の一致）を比べる。**すべて一致**。
- `node tools/check_wasm.js`：3つのルールの対局の局面で Lv.12・15・18（局面数で決まるレベル）と Lv.2・6・9・11（深さ／局面数）の手を JavaScript と WebAssembly（SIMD／SIMD なし）で読ませ、手・値・深さ・局面数を比べる。**234探索すべて一致**（ネットを入れた状態でも117探索一致）。
- ブラウザ（headless Chrome）：単体ページの AI 同士（Lv.15 対 Lv.19、`core_mt.wasm` の2スレッド）、フル機能版、大百科の3D卓の対局で AI が指し、コンソールエラーなし。Worker の答えは Node の同じ探索と一致。

## 速さ

| | 局面／秒（作業機・共用2コア、Lv.12・15・18 の平均） |
|---|---|
| JavaScript（旧） | 約6万 |
| WebAssembly（SIMD） | 約95万（約16倍） |
| WebAssembly（SIMD なし） | 約80万 |

評価をビットボードにしたこと（同じ値、約6倍速い）が大きい。ネット（H=128）を入れると約0.7倍、H=64 で約0.8倍。

## 強さの計測

自己対局（`tools/match.js`：同じ序盤（ランダムな最初の置き方）を先後入れ替えて2局、1手の時間を同じに）。

| 比較 | 条件 | 結果 |
|---|---|---|
| WebAssembly 版 vs 旧 JavaScript 版（seneca） | 1手0.1秒、80局 | 50勝23分7敗（76.9%、約 +209 Elo） |
| WebAssembly 版 vs 旧 JavaScript 版（piso） | 1手0.1秒、60局 | 38勝19分3敗（79.2%、約 +232 Elo） |
| 同上（3つのルールとも） | 局面数固定（Lv.10〜18） | 同じ手を指す（局面数・手が一致）＝50% |
| 初版の WebAssembly（評価がビットボード前、約3倍速）vs 旧 JS（seneca） | 1手0.1秒、60局 | 70.8%（約 +154 Elo） |

- 局面数で決まるレベル（Lv.1〜18）は前と**同じ手**を指す（局面数・手が一致するため）。強くなるのは時間で考える Lv.19・20（同じ時間で約16倍の局面、分離されたページではさらにスレッド数倍）と分析・ヒント・コーチ。
- 学習しない探索の追加（反転の早い打ち切り（reverse futility）・後半の手の打ち切り（LMP）・置換表の手がない節点を浅く（IIR）・置く段階の LMR を強く）を試したが、どれも勝ち越さなかったので採用していない（下の「試したもの」）。

## レベル表（レート戦の基準値 RT_LV）

Lv.1〜18 は変わらない（同じ手）。Lv.19・20 は同じ時間でより深く読むので上げた：Lv.19 2802 → **2950**、Lv.20 2852 → **3000**（同じ時間の旧 JS 比 +209〜232 Elo（1手0.1秒）。長い持ち時間では引き分けが増えて差が縮むので、各 +148 と控えめに）。大百科の `RATING` も同じ。下のレベルの手触り（Lv.1〜9 の深さとノイズ、Lv.10〜18 の局面数）はそのまま。

## NNUE（学習した評価関数）

### 仕組み

- **入力**（手番側と相手側の2視点、各366）：64マス×4状態（自分の動ける駒・自分の裏返った駒・相手の動ける駒・相手の裏返った駒。白の視点は上下反転）、自分／相手の手持ち（0〜24）、自分／相手の取った数（0〜24）、取り合いなしの手数÷6（0〜9）。
- **形**：(366 → H) ×2視点 → 1（SCReLU：0〜1 に切って2乗）。既定 H=128。量子化は W1・B1 ×127、W2 ×64（int16）。
- **手作り評価への補正（residual）**：エンジンの値 ＝ 手作り評価 ＋ ネットの出力×SCALE。小さなデータで「手作り評価をまねる」ネットを作ると、駒の価値を半分ほどに見積もって駒を捨てて負けた（15万局面で 0〜5%）。補正の形にすると同じデータで同じ局面数の対局 **60%（+70 Elo、60局）**。
- **差分更新**：`core.c` は中間層を手ごとに差分で更新（置く・動く・裏返る・取る・手持ち・取った数・手数の段の変化）。JavaScript の予備は毎回作り直して同じ整数を計算する。
- **ファイル**：`"LTN1"`, H, 366, SCALE, FLAGS（1＝補正）, W1, B1, W2（int16）, B2（int32）。`latrunculi/nets/` に置き、`engine.js` の `NETS.<ルール>` にファイル名を書くと切り替わる（空の間は手作り評価）。

### 学習の手順（ユーザーの Mac）

```bash
bash latrunculi/tools/nnue/run.sh
```

ビルド → 全コアで自己対局（既定 2,000万局面＝3ルール合計、先生はこのエンジン自身が1手1万2千局面読んだ値。外部エンジンは使わない） → 学習 → 確認（差分更新の一致、手作り評価との対局：局面数固定 200局・1手0.1秒 200局） → 採用ファイル `~/latrunculi-nnue-work/adopt/lt-<ルール>-<日付>-r<周>.nnue`。途中で止めても再開できる。周回（`ROUNDS=2`：採用されたネットを先生に次のデータ）、データ置き場（`DATA=...`、外付け可）は `tools/nnue/README.md`。時間の目安は Mac mini（M4 Pro）で自己対局 1〜2時間、学習 10〜20分×3、確認 30〜60分。

### 採用基準

1. `nncheck`：差分更新と作り直しの中間層が全局面で一致（不一致があれば不採用）。
2. 手作り評価との対局で、**局面数固定と時間固定の両方で 55% 以上**（各200局、同じ序盤を先後入れ替え）。`run.sh` はこれを満たすネットだけを `adopt/` に出す。
3. サイトに入れる前に Claude が同じ対局を `tools/match.js`（WebAssembly のエンジン）で確かめ、`tools/check_wasm.js` をネットありで通し、レベル表を測り直す。

### 作業機での試し（仮ネット、採用しない）

- seneca 15万局面（先生は1手2千局面）、H=64、8周：`nncheck` 一致、局面数固定（3千）60局で **60.0%**、1手30ミリ秒 60局で 49.2%（ネットの分だけ遅い）。データが少なく先生も浅いので、Mac の本番（約130倍のデータ、6倍深い先生）で上回ることを期待している。
- 同じネットを `nets/` に置いた形（ブラウザの Worker が取得して読み込む）で、Worker の手・値・局面数は Node の同じ探索と一致。

## 試したもの（採用しなかったもの）

| 試したもの | 結果（seneca、1手1万局面、100局） |
|---|---|
| reverse futility pruning（深さ3まで、余裕 90×深さ） | 50.5%（+3 Elo、誤差 ±51） |
| late move pruning（深さ3まで、静かな手） | 48.0% |
| IIR（置換表の手がない深さ5以上を1手浅く） | 50.0% |
| 置く段階の LMR を強く（20手目以降は2手浅く） | 49.0% |
| ネットを「手作り評価をまねる」形で学習 | 0〜5%（駒の価値を低く見積もる） |
| ネットを動かす段階だけに使う（まねる形） | 12〜28% |

`tools/nnue/ltn.c` の `smatch`（探索の設定どうし）・`nmatch`（ネット対 手作り評価）で再現できる。
