# Model Card: Shogi evaluation (`weights.bin.gz`)

将棋 SHOGI の AI が局面の良し悪しを判断するための評価関数（学習済み重み）です。
探索エンジン `engine.js` と組み合わせて、ブラウザ上（Web Worker）で動作します。

- **ゲーム**: https://core-calmdust.github.io/aicoding/shogi/
- **作成**: core-calmdust（AIコーディングによる制作）
- **バージョン**: v1（2026-10-18）

## モデル概要

| 項目 | 内容 |
|---|---|
| 種類 | 玉位置つき駒配置（KP）＋持ち駒の線形評価関数（Bonanza系の KKP/KP に近い古典的手法） |
| 入力 | 先手玉・後手玉それぞれの視点から見た、全駒の配置と持ち駒 |
| 出力 | 手番側から見た評価値（センチポーン相当。勝率 ≒ sigmoid(評価値/600)） |
| パラメータ数 | 115,921（Int16、1/8センチポーン単位） |
| ファイルサイズ | 約232KB（gzip圧縮後 約150KB） |

評価値 = Σ（先手玉視点の特徴の重み）− Σ（後手玉視点の特徴の重み）＋ 手番ボーナス。
後手玉視点は盤を180°回転して先手と同じ表を共有し、さらに玉が右半分にいるときは左右反転して表を共有します。

### 入力特徴（玉位置つき駒配置）

各手番側の視点（後手番は盤を180°回転）で、さらに自玉が盤の左半分に来るよう左右反転して正規化します。

| 特徴 | 内容 | 数 |
|---|---|---|
| KP | 自玉の位置（45通り）× 駒の種類（自分/相手 × 14種）× 升（81） | 102,060 |
| KH | 自玉の位置 × 持ち駒（自分/相手 × 7種 × 枚数を温度計表現で最大18） | 11,340 |
| P | 駒の種類 × 升（玉位置に依らない） | 2,268 |
| H | 持ち駒（玉位置に依らない） | 252 |

## 学習データ

[コンピュータ将棋対局場 Floodgate](https://wdoor.c.u-tokyo.ac.jp/shogi/) で公開されている棋譜（CSA形式）を使いました。

| 年 | 対局数（両者R3000以上） | 学習局面数 |
|---|---|---|
| 2021 | 54,852 | 4,704,050 |
| 2022 | 43,522 | 3,623,853 |
| 2023 | 56,228 | 4,783,001 |
| 2024 | 48,018 | 4,292,581 |
| 2025 | 59,893 | 4,847,586 |
| 合計 | **262,513** | **22,251,071** |

- 結果が投了・千日手・入玉宣言・時間切れで決着した対局のみ。開始5手までの局面は除外。

- Floodgate の棋譜には、対局したエンジン自身が出力した**評価値**（`'**` コメント行）が多くの指し手に記録されています。これを教師値として利用しました（先手から見た値であることを、最終的な勝敗との一致率 98.7% で確認）。
- 教師値 = 0.7 × sigmoid(評価値 / 600) + 0.3 × 最終的な勝敗。
- 取る手の直前の局面と、王手がかかっている局面は除外（静かな局面のみ）。
- Floodgate の棋譜には明示的な利用ライセンスの表記がないため、**棋譜データそのものはこのリポジトリに含めていません**。公開しているのは、棋譜から学習した重みと、序盤の指し手の頻度統計（`book.json`）だけです。
- 貴重な対局場と棋譜を長年公開してくださっている Floodgate の運営者の皆様、参加エンジンの作者の皆様に感謝します。

## 定跡（`book.json`）

両者レート3500以上の対局の序盤30手から、局面ごとの指し手の頻度と勝率を集計したものです（出現12回以上の局面、勝率38%以上の手のみ）。棋譜そのものは含みません。

- 集計対象: 2025年の両者R3500以上 39,514局 → 6,088局面（約600KB、gzip後 約100KB）

## 学習方法

- 損失: 予測勝率 sigmoid(評価値/600) と教師値の交差エントロピー。
- 最適化: Adam（特徴ごとの疎な更新）、ミニバッチ256、6エポック（後半2エポックで学習率を減衰）。
- 初期値: 駒の価値だけの評価（歩90〜龍1395）。
- 検証: 各年の末尾2%の局面（＝学習に使っていない対局）で検証。

| モデル | 検証KL（低いほど良い） |
|---|---|
| 駒の価値のみ（初期値） | 0.210 |
| 線形KP（2024〜2025年のみで学習） | 約0.12 |
| **線形KP（2021〜2025年、採用版）** | **0.1175** |
| 小型NN（同じ特徴→32×2→32→32→1、参考） | 0.1117 |

小型NN（NNUE風）は精度ではわずかに上でしたが、JavaScript では1局面の評価が約10倍遅く、同じ持ち時間の対局では線形モデルに勝率25%と負け越したため、採用していません。

## WebAssembly 版の探索

ブラウザでは、`engine.js` の探索部分を C に移植して WebAssembly にした `engine.wasm`（ソース `engine.c`）を使います。移植時には、指し手・評価値・読んだ局面数まで JavaScript 版と完全に一致することを48局面で確かめました。その後の探索の改良（上記）は WebAssembly 版だけに入っているため、現在は JavaScript 版より強くなっています。同じ持ち時間で約1.6倍の局面を読めます。WebAssembly が使えない環境では、自動的に JavaScript 版で動きます。

## 最強解析（複数スレッド、2026-11）
- `pro/`：PC の複数の CPU コアで同時に読む解析ページ。対局ページの「最強解析」ボタンから、表示中の局面まで（平手の手順）を新しいタブで開きます。
- エンジンは同じ `engine.c` を `-DMT` で作った `engine_mt.wasm`（`tools/build-wasm-mt.sh`、NNUE 512）。共有メモリの上で複数スレッドが同じ局面を読む Lazy SMP です。置換表・NNUE の重み・定跡以外の表を共有し、局面・履歴・キラー手などはスレッドごと（`TLS`）。補助スレッドは1つおきに1手深い深さから読み始めます。通常版の wasm 3種は1バイトも変わりません。
- 共有メモリ（SharedArrayBuffer）にはページの「クロスオリジン分離」が必要です。GitHub Pages ではヘッダーを設定できないため、`pro/coi-sw.js`（Service Worker）が `pro/` の中だけ COOP / COEP を付けます。対局ページ（オンライン対戦・ログイン）は対象外で影響しません。分離できないブラウザでは、通常のエンジン（1スレッド）で動きます。
- 確認：同じ深さまでの時間は 2スレッドで約2.05倍速。2スレッド対1スレッド、1手0.3秒・先後入れ替えで30局 → 18勝12敗（得点率0.600、約 +70 Elo。局数が少ないので幅は大きい）。


## 本編のマルチスレッド（2026-11-08）
- 対局ページでも `engine_mt.wasm` の複数スレッドを使います（共通部品 `shared/mtengine.js`・`shared/mt-sw.js`、addendum「本編のマルチスレッド」）。`sw.js` がページに `Document-Isolation-Policy` を付け、Chrome / Edge（PC）は COOP なしで分離（ログイン・オンライン対戦はそのまま）。Safari・Firefox などはオプション「マルチスレッド」で COOP / COEP モード（その間ログイン・オンライン対戦は停止）。スマホはオンにするまで1スレッド。
- 主スレッドは `engine.js?…&mt=1`（同じワーカー API、共有メモリの `engine_mt.wasm`・NNUE 512）、補助は `mt-helper.js`（同じ局面を `root_search` で読み続ける）。
- 対象：コーチ・ヒント（`coach`）、評価の読み（`think` 時間指定）、検討ボックス（`mpvLoop`）。本将棋のみ（変則将棋は別エンジン）。**六段までの AI の段級は局面数で決めているので1スレッドのまま**（どの端末でも同じ強さ）。時間で考える七段〜九段（2026-11-08 追加、下の「最上位の段階」）だけは AI の手もプールの全スレッドで読みます（レート戦も）。
- 計測（この作業環境：2 vCPU の Linux・headless Chromium 153。独立した2ワーカーでも合計速度は1.37倍どまりのため、深さの伸びはほぼ出ない）：時間3秒の読みで 1スレッド 約47万 nps → 2スレッド合計 約55万 nps。複数コアの PC での効果は上の最強解析の計測（2スレッドで同じ深さまで約2.05倍速）が目安です。

### マルチスレッドの見直し（2026-11-09、チェッカー・モリス・タフルの置換表の件を受けた点検）
- **見つかった問題**：①共有の置換表が「1キー1項目」の12バイト（`{ key, move, data }`）で、3つの欄を順に書いていた。2つのスレッドが同時に書くと、ある局面のキーに別の局面の手や値・深さ・上下限が付いた項目ができうる（照合もキーの上位32ビットだけ）。②1項目の置き換えで、スレッド数倍の浅い項目が深い項目を追い出しやすい。③主スレッドは自分の結果だけで答えていた。④補助の1つおきに1手深く始める「深さのずらし」。
- **確認して問題なかったもの**：停止（`gStop`・`ctl[0]`）、局面・ヒストリー・キラー手などはスレッドごと（`TLS`）、置換表・評価関数・表は共有、表の年齢は主スレッドだけが進める、補助は主スレッドが終われば止まる、継続履歴（`contH`）はわざと共有（書き込みが失われても害はない）、NNUE の有効フラグは共有。
- **変更（`engine_mt.wasm` だけ。通常版 `engine.wasm`・`engine_simd.wasm`・`engine_simd512.wasm` は同じ設定のビルドで cmp 一致＝1スレッドの段級の指し手は不変）**：
  - 置換表を 4項目のバケット（64バイト）× 2^20 = 64MB（項目数 4倍）に。1項目は `{ key ^ w, w }`（key＝64ビットのハッシュ全体、w＝値・手・深さ・種類・年齢・使用中）で、読むときに XOR で照合。置き換えは同じキー → それ以外はバケットで最も浅い／古い項目。
  - 各スレッドが終えた反復をルートの鍵（局面・手数・ルートの手）付きで共有し、主スレッドは最も深い結果で答える。深さの上限に補助が先に届いたら主スレッドも終える。深さのずらしはやめた。

## レーティング戦（ひとりで遊ぶレート対局）のレーティング表

新しい対局の「レーティング戦」では、AIの各段階に固定のレーティングを割り当て、プレイヤーのレーティング（端末ごとに保存、`localStorage` の `shogi-rated-v1`）とのElo計算で増減させます。オンライン対戦のレーティングとは別物です。

尺度は将棋倶楽部24に近い形で、1級ごとに100点（15級 = 400〜499 … 1級 = 1800〜1899、初段 = 1900〜2099、以降200点ごとに1段）としました。各段階の値はその段級位の帯の中央です（入門150・初心300・15級450 … 1級1850・初段2000・二段2200。一覧は上の「段級位表示の19段階」の表）。

- プレイヤーの初期値は 900（24 10級前後）。K = 48（最初の10局）、以降 K = 24。期待勝率は 1 / (1 + 10^((相手R − 自分R) / 400))。
- 相手の選び方：目標 = 自分のR + ずらし幅（80%は ±100 以内、10%は +150〜+300 の格上、10%は −150〜−300 の格下）に最も近い段階（19段階）。開始時に「今回の相手：9級（R 1050・互角）」のように表示（差が150を超えると格上・格下）。

- 強さは読む局面数で決まるため、端末の速さにはほぼ左右されません（初段・二段のみ思考時間の上限あり）。段級位には ±1級程度の誤差があります。

## ファイル形式

```js
const buf = await (await fetch('weights.bin.gz')).arrayBuffer();
const raw = await new Response(new Blob([buf]).stream().pipeThrough(new DecompressionStream('gzip'))).arrayBuffer();
// Web Worker に {type: 'weights', buffer: raw} を送ると engine.js が読み込みます
```

## 探索の高速化 その2（2026年11月）

`engine.c` の探索まわりを見直し、同じ時間で読める局面数が約2.4倍になりました（全ビルド共通。`engine_mt.wasm` の各スレッドも同じ）。プロファイル（ネイティブ版の callgrind と Node.js の wasm プロファイル）で時間のかかっていた所を順に削りました。

- 王手をかけられた局面: 全部の指し手（打ち駒を含め平均約190手）を作って並べてから合法手を探していたのを、玉の移動・王手した駒を取る手・合駒だけを作るようにしました（指し手生成・並べ替え・選択の大半が消えます）。
- 王手の判定: 指した直後の「王手になったか」を、全方向の利き調べではなく、動いた駒の利きと空いた筋（開き王手）だけで判定。指す前にも同じ判定ができるので、枝刈りで「王手になる手だけ読む」所では王手にならない手を指さずに飛ばします。局面ごとに結果を覚え、子局面で再計算しません。
- 合法性: ピンの判定を「玉と動かした駒を結ぶ線の先に相手の飛び駒があるか」だけに。王手回避もこの判定で、指す前に非合法手を捨てます。
- 1手詰め（全局面で実行）: 王手にならない候補と、玉に取られる（ほかに守りのない）接触王手は、指さずに除外。
- 長い指し手リストの選択（同点の扱いを含め同じ順番）を16手ごとのブロックで高速化、打ち駒の生成をビットマスク化、利き調べを方向ごとのマス表で、置換表の3配列を1つの構造体に、出力層の和を（重みが小さいことを読み込み時に確かめて）int32 のままに。

- 王手回避の生成だけを元に戻したテストビルド（`-DFULL_EVASIONS`）は、変更前と指し手・評価値・局面数まで完全に一致（中盤83局面で深さ7、序盤100局面で深さ8、線形評価版も83局面で深さ6）。それ以外の変更は結果を変えません。
